# Изменение ценового контекста покупателя, v1

Новый контракт для proshop-server. В `origin/master` сервера
`f9e06921dd8716c0f5b4e02201756414554ac5b9` события изменения membership нет.
События товара/прайса не содержат покупателя и не заменяют этот контракт.

- Тема: `<KAFKA_TOPIC_PREFIX>.pricing.buyer.context-changed`, без префикса —
  `pricing.buyer.context-changed`. Схема имён сервера: домен.сущность.событие.
  Тему создаёт сервер установки; площадка подписывается только после появления темы.
- Ключ: JSON-массив `[tenantId, buyerId]`; порядок изменений одного покупателя магазина сохраняется.
- `x-tenant`, если передан, совпадает с магазином ключа и тела.
- Публикация через транзакционный outbox после изменения условий. Событие не содержит цен и контактов.

| Поле | Требование |
|---|---|
| `version` | Обязательно, целое `1`, версия контракта |
| `tenantId` | Обязательно, идентификатор продавца |
| `buyerId` | Обязательно, UUID аккаунта покупателя площадки, тот же, что в pricing/contexts |
| `clientId` | Необязательно, строковый id клиента магазина для диагностики; не используется для поиска покупателя |
| `revision` | Обязательно, положительное int64, монотонная ревизия pricing магазина (`writeFence`) |
| `at` | Обязательно, время изменения в RFC 3339 UTC |
| `reason` | `group_changed`, `terms_changed`, `membership_removed`, `configuration_changed` |

Пример: [price-context-changed.v1.json](examples/price-context-changed.v1.json).
При изменении состава группы, её активности или конфигурации каналов сервер публикует событие
для каждого затронутого `marketplace`-субъекта. Один `clientId` без `buyerId` недостаточен:
существующая pricing-модель различает субъекты `customer` и `marketplace`, общей связи нет.
Не угадывать покупателя по телефону или email. Если изменение затрагивает только customer-субъекта,
событие площадке не нужно, пока сервер явно не установил связь с marketplace-субъектом.

Площадка удаляет весь кэш покупателя, включая токен текущей загрузки, без постоянной таблицы
«покупатель × продавец». До новой загрузки страница показывает публичные цены. Ответ старой
загрузки после сброса отбрасывается проверкой токена в Redis/памяти. Поздняя ревизия события
может лишь дополнительно удалить кэш: событие никогда не назначает персональный профиль.

Inbox — существующий `processed_events`, ключ `<полный topic>:<partition>:<offset>`.
В транзакции: отметить inbox, удалить запись из кэша. При ошибке удаления транзакция откатывается,
Kafka повторяет сообщение; при падении после DELETE до коммита повторный DELETE безопасен.
После KAFKA_MAX_ATTEMPTS действует штатный parking attempts_exhausted, доступен операторский replay.
Коммит Kafka — после успешного сценария. Повтор того же offset — без нового сброса.
Повторная публикация на другом offset безопасно удалит кэш ещё раз.

Неизвестный покупатель: удалить возможный кэш, отметить inbox и исход `unknown_buyer`;
не создавать покупателя или связь с клиентом. Неверный контракт/ключ/магазин — штатный parking
и метрика consumer; ошибка БД/Redis — штатный retry, без успешной отметки inbox.
При недоступном общем Redis локальные резервные записи других процессов ограничены TTL;
немедленный общий сброс завершается после восстановления Redis и повторной доставки.
