# Массовое одобрение модерации — первый круг, 19.11.2026

Уточнения контракта, исправления проверки и актуальные проверки второго круга —
[в отчёте доработки](moderation-bulk-review-2.md).

**Как работало до изменения.** `GET /operator/moderation/cases` читает очередь
с фильтрами и offset-пагинацией. Единственное действие одобрения —
`POST /operator/moderation/cases/{caseId}/allow`: обязательные `expectedVersion`
и заметка, необязательный `Idempotency-Key` с окном 24 часа. В одной транзакции
сценарий читает дело, товар, вердикт и участника, проверяет текущую ревизию и
публикацию, вызывает доменные `Case.Decide` / `Verdict.Decide`, сохраняет аудит,
счётчик участника и три задачи outbox. Каждый следующий товар повторяет этот путь.
Все пути ниже имеют префикс `/api/v1`.

`Participant.ApproveOffer` повышает участника после
`MODERATION_PROBATION_OFFERS` одобрений, `SetTrust` меняет доверие вручную.
Оба перехода уже ставили `moderation.tenant.reevaluate` в существующий outbox.
Воркер проходил все проекции магазина и переоценивал правила: при исчезновении
испытания автоматический вердикт становился `allowed`, дело — `superseded`.
Поэтому полного отсутствия автоматического закрытия в свежем master нет.
Но это не одобрение дела: записи `allow` в журнале решений нет, а переоценка
ходит по каждому товару и может обновлять основания смешанных дел.
При остановленном или отстающем воркере одного доверия недостаточно для немедленной
видимости товаров. Другие ограничения магазина и карточки также продолжают действовать.

В панели очередь показывала по шесть дел на странице без выбора строк;
одобрение выполнялось только из карточки дела с заметкой и контролем конфликта.
Страница участника позволяла менять доверие, но массового действия для товаров не было.

**Что добавлено.** `POST /operator/moderation/cases/bulk-allow` принимает общую
заметку и ровно один способ выбора:

```json
{
  "cases": [
    { "id": "00000000-0000-4000-8000-000000000001", "expectedVersion": 1 }
  ],
  "note": "Проверено оператором"
}
```

```json
{
  "selector": {
    "tenantId": "t1",
    "reasons": ["moderation.probation"]
  },
  "note": "Проверен магазин"
}
```

Не более 200 идентификаторов, без дубликатов; отбор также читает не более 200 дел.
`Idempotency-Key` обязателен, ограничен оператором и видом действия.
Таблица `moderation_bulk_idempotency` хранит исходный результат 30 суток;
ключ имеет формат `unixMilliseconds:nonce`, старый ключ отвергается независимо от очистки;
блокировка ключа, решения и результат фиксируются атомарно. Повтор тела возвращает
прежний результат; другое тело с тем же ключом — `409 IDEMPOTENCY_KEY_REUSED`.

Ответ содержит `approved`, `skipped`, `details: [{id, reason}]`, `hasMore`,
`nextAfter`. Для следующей страницы нужно передать `selector.after = nextAfter`
с новым ключом. После полной страницы возможен заключительный пустой запрос.
Причины пропуска: `changed`, `already_decided`, `other_reasons`, `not_found`,
`participant_changed`. Ожидаемые конфликты отдельных дел не откатывают соседние;
ошибка инфраструктуры откатывает всю текущую страницу и допускает безопасный повтор.
Список идентификаторов означает явное одобрение выбранных оператором дел,
включая дела с несколькими причинами. Поле `selector.reasons` ограничивает весь набор причин. Со второго круга пустой
`selector` означает всю очередь, а `tenantId`, `source`, `reason` повторяют фильтры панели.

Права и principal берутся из того же HTTP middleware. Дела читаются одним
запросом после упорядоченных блокировок товаров и вердиктов; записи дополнительно
сохраняют CAS-проверку исходных версий и статусов. Вердикты, дела, журнал решений
и outbox записываются наборами. История вердиктов сохраняется прежним триггером.
Участники читаются и блокируются одной выборкой; каждый затронутый участник
обновляется один раз на страницу. Доменные `ApproveOffers` / `ApproveOffer`
используют одинаковое правило повышения и одну запись журнала о переходе.

Повышение из одиночного или массового одобрения, а также ручное повышение
теперь ставит `moderation.tenant.allow_trusted`. Один вызов воркера обрабатывает
максимум 200 дел тем же `BulkAllow`. Доверие повторно проверяется под блокировкой;
продолжение с курсором записывается в outbox в транзакции страницы.
Исполнитель автоматического решения — `system`, заметка указывает переход в доверенные.
Только единственный ключ причины `moderation.probation` допускается к этому пути;
дела с другими причинами сохраняют статус и основания. Общая переоценка остаётся
для изменений правил, таксономии и возврата на испытание.

`GET /operator/moderation/cases/bulk-count?tenantId=t1&reasons=moderation.probation`
даёт число дел, магазинов и дел с другими причинами для подтверждения с тем же предикатом. Это число на момент
чтения, а не блокировка всей очереди. UI выбирает строки или страницу, показывает
подтверждение с количеством, общую заметку, прогресс, итог с причинами пропусков
и обновляет список. Действие испытания доступно в фильтре по магазину и на странице
участника. После потери ответа панель сохраняет тело и ключ незавершённой страницы;
завершённые страницы повторно не учитываются. При выходе из сессии поздние ответы
игнорируются, следующие страницы не отправляются.

**Масштаб и замеры.** Реальные SQL-команды посчитаны pgx tracer в
`TestBulkApprovalQueryCount`, на 200 одобрениях одного магазина, без достижения порога,
без словарной причины. Триггерные записи внутри PostgreSQL не являются отдельными
запросами клиента и одинаково сохраняют историю в обоих путях.

| Путь | SQL без BEGIN/COMMIT | Транзакции | Всего с BEGIN/COMMIT |
|---|---:|---:|---:|
| 200 одиночных с ключами | 2800 | 200 | 3200 |
| 200 явных идентификаторов | 12 | 1 | 14 |
| Страница 200 по магазину | 13 | 1 | 15 |

В 12 входят: ключ и кэш (2), блокировки товаров и вердиктов (2), дела (1),
участники (1), обновление участника (1), вердикты / дела / аудит / outbox (4),
сохранение результата (1). Отбор добавляет один SELECT страницы.
Для T магазинов без повышений — `11 + T` или `12 + T` запросов соответственно.
Каждое повышение добавляет запись журнала участника; задачи повышения включены
в общий INSERT outbox. Повтор готового результата делает только два SELECT.
Подтверждение числа — отдельный COUNT. Фоновая страница дополнительно проверяет
доверие отдельным чтением; при продолжении добавляет одну задачу outbox.

Миграция 62 добавляет пять индексов `CONCURRENTLY`, без переписывания таблицы; все включены в восстановление прерванного DDL:
точный частичный индекс испытания `(tenant_id, id)` и общий индекс открытых дел
магазина, общий индекс открытой очереди по id и индекс по источнику и id, GIN по ключам причин открытых дел. Ключи причин извлекает immutable-функция; исторический текст не влияет
на выборку. Пустые и прежние JSON-null причины безопасно дают пустой набор.
Страница использует keyset, не OFFSET; память и блокировки ограничены 200 делами.

Запущен `EXPLAIN (ANALYZE, BUFFERS)` на 402 делах (401 чистое испытание),
без отключения seq scan. Получен следующий план; время зависит от локальной среды:

```text
Limit (actual rows=200 loops=1)
  -> Index Scan using moderation_case_probation on moderation_cases
       Index Cond: ((tenant_id = 't1') AND
         (id > '00000000-0000-0000-0000-000000000000'::uuid))
```

Это проверка формы плана и количества SQL, не нагрузочный тест на миллионах товаров.

**Проверки запуском.** Go: build, vet, vet с тегом integration, make lint,
`go test -race ./...`. PostgreSQL: отдельные базы через pgtest с миграциями с нуля;
200 дел, сохранение счётчика одной версией, повтор и конкурентный повтор ключа,
гонка операторов, изменённая версия и ревизия, снятие публикации и удаление,
исключение смешанных причин, три страницы отбора, план и счётчик SQL;
фоновое одобрение после одиночного / массового достижения порога и ручного доверия,
продолжение outbox. Регрессия JSON-null проверяется прежним `TestModerationM4Storage`.
Прерывание и повтор concurrent-построения обоих новых индексов проверены
расширением `TestInterruptedConcurrentIndexMigrationRecovers`.
Полный прогон PostgreSQL завершился успешно (431,848 с):
`go test -race -count=1 -tags integration ./internal/infrastructure/postgres/...`.
Использованы заданный `TEST_DATABASE_URL` на 127.0.0.1:25499 и локальный
`TEST_REDIS_URL=redis://127.0.0.1:26399/0` для существующей проверки кэша магазина.
Дополнительно целевые тесты, старая регрессия модерации и Redis-кэш прошли
с отдельным временным Redis-контейнером; контейнер остановлен и удалён.
После завершения pgtest проверено: временных `marketplace_test_*` баз нет.

Панель: `yarn typecheck`, `yarn lint`, `yarn test --maxWorkers=4` — 480 passed,
один ранее отключённый тест; `yarn build` (предупреждение Vite о размере chunk).
Playwright — 10 passed, desktop 1440×1000 и mobile iPhone 13:
выбор всех с клавиатуры, подтверждение, пустая выдача, прогресс, сетевая ошибка,
повтор страницы с прежним ключом, hover/focus, защита от Escape при обработке,
страница участника и пять её существующих состояний. Скриншоты до/после сняты
на одинаковых фикстурах и времени; оболочка сохранена, колонка выбора и новое
действие участника добавлены намеренно. Браузер использовал моки и перехваченные
локальные HTTP-ответы; связка с живым Go API, Kafka и поисковым индексом не прогонялась.
Стенд kind и его операторский токен не использовались.

**Выкат.** Сначала миграция 62; дождаться окончания concurrent-построения и проверить
валидность индексов. Затем обновить API и воркеры вместе, включая регистрацию
нового вида outbox, после этого панель. Обычные действия прежней панели совместимы;
экспериментальная кнопка bulk первого круга требует обновления вместе с контрактом ключа.
Новые задачи нельзя оставлять на обработку старым воркерам. Для уже доверенных
магазинов без нового перехода автоматического backfill нет: оператор использует
новое действие отбора. Одобрение не отменяет прочие требования видимости магазина,
карточки и обновление поискового индекса через outbox. Откат панели/API не требует
удалять журнал и результаты идемпотентности; перед откатом воркеров нужно завершить
или сохранить новые задачи для совместимой версии.
