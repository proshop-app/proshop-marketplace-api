# Поставка таксономии Proshop

С 22.11.2026 исходники таксономии и выпуски сопровождаются в
[uno-reference-data](https://github.com/proshop-app/uno-reference-data).
Площадка закрепляет номер, SHA-256 файла и Git-коммит источника в
[`release.lock.json`](../internal/infrastructure/taxonomydata/release.lock.json).
Договор JSON v1 описан в [uno-reference-data](https://github.com/proshop-app/uno-reference-data/blob/5598ef0d1ea9443aebc2376067d3f5969e9cd625/README.md#договор-артефакта-с-загрузчиком-площадки).
Текущий артефакт — `releases/taxonomy-v17.json`. Значения закрытых словарей,
палитра и подтверждённые пулы выбора собираются из реестра при публикации. Рабочий снимок хранится в PostgreSQL.

## Сборка и проверка

```bash
make taxonomy-artifact UNO_REFERENCE_DATA_DIR=/path/to/uno-reference-data
# Или из уже сохранённого файла:
make taxonomy-artifact TAXONOMY_BUNDLE=/path/to/taxonomy-v17.json
go run ./cmd/taxonomy check
go run ./cmd/taxonomy check --export
```

По умолчанию Make берёт `../uno-reference-data`. Подготовка требует Python 3
и использует только стандартную библиотеку. Она сверяет SHA-256 точных байтов
и атомарно помещает файл в игнорируемый Git `taxonomy-bundle.json` рядом с
`release.lock.json`. Перед прямым `go build`, `go vet`, `go test` или `docker build`
нужно подготовить файл. Цели `make build`, `make test`, `make lint`, `make dev`,
`make image` и `make taxonomy-image` делают это сами. В CI отдельное задание
берёт JSON из `releases/` закреплённого коммита Uno и передаёт проверенный файл
остальным заданиям. Для закрытого Uno нужен `UNO_REFERENCE_DATA_TOKEN` с
правом `contents: read` на этот репозиторий.

`go:embed` включает файл в загрузчик. Загрузчик повторно сверяет SHA-256,
проверяет формат, номер, ссылки и разворачивает схемы до подключения к БД.
Площадка собирает отдельный образ загрузчика через
`make taxonomy-image TAXONOMY_IMAGE=proshop-marketplace-taxonomy:uno-17`.
Docker запускает проверку собранного бинарника на этапе сборки. В рабочем
окружении загрузчику нужен только PostgreSQL для команд, меняющих снимок.
`check --review --direction accessories` выводит матрицу листьев выбранного
направления. `check --export` выводит развёрнутый JSON до разрешения словарей.

## Выкат поставки 17 поверх 15 или 16

1. Опубликовать закреплённый коммит Uno. Обновить API площадки и загрузчик
   до версии с защитным пределом 4096 определений. Проверить историю головы
   по запросу ниже. Если оператор правил голову, передать согласованный
   `--expected-version` при применении.
2. Выполнить миграции, `reference-bootstrap` и `reference-apply`. Импортировать
   из закреплённого checkout `taxonomy/reference/verticals-v17.json` и при
   переходе с 15 также `taxonomy/reference/size-markings-v2.json` через
   `marketplace reference import --file <путь>`. До применения проверить
   виды и подтверждённые значения закрытых словарей, включая значения с
   поисковыми выражениями, а также пулы выбора страны и размерных маркировок.
   Пакеты Uno содержат кандидатов для приёмки.
3. Выполнить `taxonomy apply`. Идентификаторы, адреса и родительство категорий
   сохранены. Ссылки на схемы изменились, подтверждение замены дерева не
   требуется. Проверить `X-Taxonomy-Version` четырёх частей для поиска,
   дождаться перепроверки карточек и обработки outbox.
4. Обновить проекции сервера магазина и включить писатели поиска с отбором
   плоских полей по `facet` до подачи расширенных проекций в новые индексы.
   Собрать и активировать новое поколение площадки, пересобрать алиасы
   магазинов. Проверить бюджет маппинга и выдачу фильтров после переключения.

Для исправления уже опубликованной 17 нужен следующий выпуск Uno с сохранением
глобальных кодов. Прямой откат к 15 или 16 конфликтует с правилом об их сохранении.

Части API сохраняют `ETag` и условный GET. Сервер магазина сверяет
`/api/v1/taxonomy/version` перед загрузкой. Для поиска отдельная задача —
сверять версию, загружать четыре согласованные части при её смене и сохранять
последний согласованный снимок при гонке публикаций.

## Выкат поставки 16 поверх 15

1. Опубликовать закреплённый коммит Uno с `taxonomy-v16.json` и контрольной суммой.
   Применить `reference-bootstrap`. Импортировать из того же checkout пакет
   `taxonomy/reference/size-markings-v2.json` штатной командой
   `marketplace reference import --file <путь>`. Проверить подтверждённый пул стран.
2. Провести редакционную приёмку размерных кандидатов и сверить хранимые
   маркировки и наличие `brand`. Пакет размеров приходит со статусом `candidate`.
   В незаполненной сетке любая указанная маркировка получает `taxonomy.dictionary_value`.
3. Применить `taxonomy apply` после миграций и подготовки словарей. При правках
   головы использовать штатный `--expected-version` после сверки. Дерево 15 и 16
   совпадает, подтверждение замены и таблица переносов не нужны. Дождаться
   перепроверки карточек и обработки поискового outbox.

Обязательное поле `brand` использует `taxonomy.required`. Площадка скрывает
карточки с ошибками публикации и показывает причины в операторской диагностике.
В опубликованный пул входят точные канонические строки со статусом `confirmed`.
Фоновая сверка публикует новую версию таксономии при изменении этих пулов и
ставит перепроверку затронутых категорий, если изменился допуск или проекция.

Снимок `/api/v1/taxonomy/attributes` содержит `selectionValues` по кодам словарей.
Для полного снимка потребитель сопоставляет их с `/api/v1/taxonomy/dictionary-sources`
по общей версии. В схеме отдельного раздела `attributes[].valuesMeta` уже раскрыт
для его сетки. `name` и `hint` адресованы продавцу, `displayName` с запасным
`name` — покупателю. Для поиска `searchTermsByValue` из пула выбираются по
фактическому значению, а `covers` передаётся в `facetValues` контракта оферт.
Форма метаданных и остальных ответов описана в [OpenAPI](../api/openapi.yaml).

## История выката JSON-артефакта поставки 15

1. Сначала принять и опубликовать коммит Uno из `release.lock.json`, в котором
   находятся `taxonomy-v15.json` и `taxonomy-v15.sha256.json`. Площадка использует
   SHA-256 JSON `5647c7733c2d892823c9e7941335942fc4a48143638c94348353dff131f86e55`.
2. Перед заменой образа на существующем стенде однократно прочитать голову и
   последнюю операцию поставки. Сопоставить `head_version` с `published_version`
   и зафиксировать возможные правки оператора по снимку.

   ```sql
   SELECT h.version AS head_version, r.release, r.checksum,
          r.published_version, r.rolled_back_version
   FROM taxonomy_head AS h
   LEFT JOIN LATERAL (
       SELECT release, checksum, published_version, rolled_back_version
       FROM taxonomy_releases
       ORDER BY release DESC
       LIMIT 1
   ) AS r ON true
   WHERE h.singleton;
   ```

3. При активной поставке 15 сверить отсутствие отката и старый checksum
   `d634b123343dff3bc5b3766d48eb14ebf0aa08dcb8b42bc1b2a280e8f81dfb5f`.
   Обновить образ загрузчика и пропустить job `apply` для этого обновления.
   Версия головы и правки оператора сохраняются. При несовпадении сверить историю
   и снимок до любых операций записи. Если выпуск 15 был отменён, нужен новый выпуск.
4. Для первой установки 15 применить миграции, зарегистрировать словари,
   загрузить выпуски значений с необходимыми `confirmed`, затем применить
   таксономию и запустить API. Для существующей головы, требующей явного
   согласования версии, передать `--expected-version` из API после сверки.
   На стенде с более старой поставкой согласовать переназначение карточек по
   `categoryMigration`, включая ручной выбор для `split`.

   ```bash
   make migrate
   make reference-bootstrap
   make reference-apply
   go run ./cmd/taxonomy apply --confirm-category-replacement
   ```

   Перед прямым запуском команды подготовить артефакт и передать `DATABASE_URL`
   через окружение. На стенде Job загрузчика запускается после миграций и
   подготовки реестра. Пакет `deploy/reference/bootstrap.json` и исторические
   каталоги словарей нужны для комплектности 15. Их метаданные происхождения
   входят в checksum выпусков справочников.

Журнал 15 использует `manifest.checksum` из проверенного JSON. Тем самым и
YAML-загрузчик, и JSON-загрузчик распознают ту же пару номер + checksum.
С поставки 16 Uno выпускает манифест без этого поля, журнал использует SHA-256
JSON-артефакта. Обычные правки дерева, атрибутов, схем и привязок идут через Uno.
Операторские команды остаются для согласованных аварийных исправлений с CAS.

## Повторы и обновление

Номер поставки независим от версии опубликованного снимка. Первая поставка
на пустом словаре версии 0 создаёт снимок версии 1. Повтор той же поставки
не меняет данные и версию, включая последующие правки оператора. Блокировка
строки снимка сериализует одновременные загрузки и операторскую публикацию.
Снимок и отметка поставки фиксируются одной транзакцией.

Публикация выпуска, откат и операторская загрузка части не читают товары.
Вместе с новой версией сохраняются задания `taxonomy_revalidation` по категориям,
у которых изменились эффективные атрибуты, схема, путь или политика модерации.
Неиспользуемая схема и неизменившаяся часть не запускают обход каталога.
Перед запуском обновлённого API нужна миграция 52; индекс исходной категории
строится `CONCURRENTLY`, без запрета записи товаров. Это единственная операция
выкатки, которая читает существующий каталог целиком.

Фоновый цикл работающего `marketplace serve` проверяет до 50 товаров одной категории
за транзакцию, затем уступает базу на 100 мс. Если API остановлен, задания ждут его
запуска. Блокировка головы удерживается только на время этой страницы, не всего
каталога. Курсор, счётчик `processed`, изменения карточек и outbox фиксируются
вместе. После сбоя незавершённая страница повторяется; уже сохранённая не повторяется.
Задание сначала получает короткую аренду в отдельной транзакции. Временная ошибка
или отмена страницы откатывает товары и курсор, но не аренду: до её окончания
обработчик может брать другие категории. Выбор идёт по времени готовности;
успешная страница уступает очередь более старым готовым заданиям. Время постановки,
аренды и возврата в очередь задаёт только `now()` PostgreSQL; часы приложения
используются для времени проверки карточек, а не для готовности заданий.
Несколько реплик разбирают разные задания через `FOR UPDATE SKIP LOCKED`.
Сохранение страницы проверяет токен аренды. Порядок блокировок страницы —
голова таксономии, задание, товары по `(tenant_id, product_id)`.
Публикация новой версии одним запросом закрывает незавершённые старые задания
тех же категорий; задания других категорий сохраняются.
Каждая страница берёт текущую версию: незавершённый старый выпуск не может вернуть
карточке старую проверку после нового выпуска или отката.

В переходный период покупатель продолжает видеть прежнюю проверенную карточку
и её прежнюю категорию/атрибуты в индексе. Новое дерево и правила запросов доступны
сразу; удалённая категория больше не принимается как фильтр поиска. Карточка
обновляется или скрывается после перепроверки и доставки outbox. Продавец/оператор
видит последнюю сохранённую диагностику и её `version`, которая может отставать
от текущей версии таксономии. Новое событие товара сразу проверяется по текущей
версии. Общая блокировка головы при приёме сохраняется до фиксации товара,
inbox и outbox: публикация не может вклиниться в эту транзакцию.

Каждая сохранённая страница пишется на Debug. На Info выводятся завершение
категории и прогресс каждые 100 страниц процесса (`pages`, `version`, `category`,
`tenantId`, `productId`, накопленный по категории `processed`, `done`). Для миллиона
карточек это около 200 периодических записей Info плюс завершения категорий.
Состояние переживает рестарт в БД:

```sql
SELECT version, count(*) AS categories, count(*) FILTER (WHERE done) AS completed,
       sum(processed) AS processed
FROM taxonomy_revalidation
GROUP BY version ORDER BY version DESC;
```

`processed` считает просмотренные строки, включая уже проверенные событием;
это не количество доставленных документов поиска. Отдельного полного `COUNT`
товаров для процентов прогресса нет. Категории, которых изменение не касается,
могут сохранять прежнюю версию диагностики до следующего события: их правила
не изменились. Карточки без исходной категории не обходятся: смена таксономии
не может исправить отсутствие блока площадки.

Постоянная ошибка разбора карточки, данных модерации или записи конкретной строки
не останавливает категорию. Ошибка данных PostgreSQL изолируется через savepoint
и деление неудачной пачки; успешные карточки сохраняются, курсор идёт дальше.
Конфликт версий, недоступность БД и отмена контекста требуют повтора страницы.
Класс SQLSTATE 22 и ограничения NOT NULL, FK, CHECK считаются постоянными ошибками
данных; уникальность 23505, сериализация 40001 и deadlock 40P01 требуют повтора
всей страницы, без продвижения курсора и регистрации постоянного отказа.
При непроверенной карточке сохраняется последняя проверенная публикация.
Диагностика доступна оператору через
`GET /api/v1/operator/taxonomy/revalidation-failures?limit=50`, с курсором
`afterTenant`/`afterProduct` последней строки. По умолчанию — 50, максимум — 100 записей,
диагностика ограничена 2048 символами. Один SQL на страницу, полного
`COUNT` нет. Ответ содержит `items` (магазин, товар, ревизию источника,
версии товара/таксономии, этап ошибки и время) и `next`: пару `tenantId`/`productId`
последней строки полной страницы или `null` для неполной страницы. Эту пару
передают в `afterTenant`/`afterProduct`; после последней полной страницы возможен
завершающий пустой ответ. Например: `{"items": [...], "next": {"tenantId": "t1", "productId": "p50"}}`.
Это форма `items` + `next` из `respondList` истории покупок; у существующих списков
модерации оператора другой контракт (`items`/`total`/`limit`/`offset`).
Старая ошибка не показывается после
смены ревизии источника или успешной проверки по соответствующей версии.
Просто отставшая `Publication.Version` без записи ошибки не означает непроверенную карточку.

Таблица хранит одну текущую ошибку на `(tenant_id, product_id)`, повтор заменяет её.
После смены ревизии источника или успешной повторной проверки запись сразу исключается
из ответа. Физически её удаляет существующая retention-задача: при запуске API и затем
раз в `RETENTION_INTERVAL` (по умолчанию час), вместе с отказами удалённых товаров.
Обход идёт страницами по PK таблицы отказов, с точечным чтением товаров; весь каталог
не сканируется, повторного чтения начала таблицы после каждой пачки нет.
Актуальная ошибка хранится до исправления без TTL: срок не превращает непроверенную
карточку в проверенную. Отдельной истории отказов таблица не накапливает.

### Стоимость страницы и пропускная способность

Определение и правила получаются через снимки единого `postgres.NewUnitOfWork`
с проверкой версии и блокировкой головы; отдельного механизма снимков нет.
Определение и скомпилированный контекст `Check` общие для страницы. Правила
модерации читаются один раз, участники — одним запросом по нужным `tenant_id`,
оценки/открытые дела/сигналы — одним запросом без повторного чтения карточек.
Товары, оценки, дела и outbox сохраняются отдельными пакетными UPDATE/INSERT.
Общее решение модерации принимает только загруженные значения и возвращает
изменённые оценку/дело и отложенные наблюдения. Приём события читает и сохраняет
их явно, страница использует пакетные входы и запись; подмен репозиториев нет.
Историческое доказательство ручного допуска читается до решения; правила
переноса ручного решения остаются общими с приёмом события.

Для непустой изменившейся страницы с модерацией без ошибок: SQL =
`10 + I(P>0) + I(Q>0) + I(V>0) + I(C>0) + I(Tcold) + I(Q>0 && Rcold)`.
Здесь `P` — опубликованные карточки, `Q` — опубликованные карточки известных
участников, `V`/`C` — изменённые оценки/дела, `I` равно 1 при истинном условии.
`Tcold`/`Rcold` означают отсутствие текущей версии таксономии/правил в снимках UoW.
Это 14 клиентских SQL для создания 50 оценок и 50 дел при прогретых снимках,
16 при обоих холодных; включая BEGIN/COMMIT двух транзакций — 18 и 20 обращений.
При прогретой таксономии без модерации — 9 SQL, без изменившихся карточек — 5,
пустой опрос — 1. Запись диагностики добавляет один INSERT на страницу.
Триггер истории дополнительно сохраняет по строке на изменённую оценку:
для 50 новых оценок это ещё 50 INSERT внутри PostgreSQL, без сетевых обращений.
Штатные SAVEPOINT/RELEASE включены в число; постоянная ошибка записи добавляет
ROLLBACK и рекурсивные SAVEPOINT/RELEASE при делении пачки.
Синхронных обращений к поиску или другим сервисам на странице нет: доставка — outbox.

Повторный замер после переноса на снимки UoW из PR #59 и выделения общего
решения модерации, на PostgreSQL 16.15:

10 категорий, 8 скалярных полей, probation и создание дел модерации,

## Откат

До каждой поставки БД сохраняет исходный снимок. Откат выполняется образом
отменяемой поставки:

```bash
docker run --rm --env DATABASE_URL proshop-marketplace-taxonomy:uno-4 rollback
```

Откатывается только последняя поставка без последующих правок оператора.
Данные восстанавливаются с новой возрастающей версией; повтор безопасен.
Понижение тега образа не откатывает БД. Повторный rollout отменённой поставки
завершится конфликтом; для продолжения выпускается новая версия поставки.
Откат также проходит проверку эволюции глобальных кодов: нельзя удалить код,
изменить его тип или единицу. Если предыдущий снимок нарушает это правило
(включая пустой снимок до первой поставки), откат завершится конфликтом.
В таком случае нужна новая корректирующая поставка с сохранением кодов.

Миграция `00026_taxonomy_releases.sql` добавляет отдельную таблицу истории.
Её снятие не является откатом каталога и удаляет историю поставок. CLI не
печатает `DATABASE_URL` или необработанные сообщения драйвера.

`reference apply` с одними начальными 19 словарями недостаточен для новой
поставки: отсутствующий или закрытый словарь отклоняет её целиком.
Запуск API не импортирует пакет и не изменяет реестр самостоятельно.

Открытый словарь даёт подсказки, но не ограничивает допустимые строки.
Прежние, новые и неизвестные значения сохраняются в карточках и поисковых
фасетах как строки, без замены на UUID, смены написания или требования
наличия в реестре. GTIN, ISBN, модели, совместимость и другие поля без
подходящего пула остаются свободными.

Четыре импортируемых пула намеренно не привязаны глобально: `size` содержит
только буквенные размеры одежды при многозначном общем атрибуте; `age`
содержит группы одежды, а атрибут используется также книгами и средствами
гигиены; `protection_class` объединяет несопоставимые стандарты кресел,
СИЗ, IP и электробезопасности; `plant_species` из исходного `plant-name`
смешивает виды, роды и культивары. Для них нужны отдельные контекстные
атрибуты или проверенная фильтрация исходных данных. Discovery-only пулы
с отношениями вида/производителя не привязываются.

Откат `taxonomy rollback` образом поставки 7 восстанавливает её сохранённый
исходный снимок с новой возрастающей версией. Обычная публикация не может убрать
существующую базовую ссылку; отдельная команда
[remove-hint](taxonomy-hints.md#исправление-ошибочной-прежней-привязки) допускает
точечное исправление с историческим доказательством и CAS. Реестр, подтверждения оператора и исходные
товарные строки при этом сохраняются. Ограничения последней поставки,
контрольной суммы и отсутствия последующих операторских публикаций действуют
как раньше; смена одного словаря другим и изменение закрытого enum запрещены
даже при откате. Повтор отменённой поставки запрещён — для продолжения
выпускается следующий номер.


Правила источников подсказок по категориям публикуются отдельно:
[taxonomy-hints.md](taxonomy-hints.md). Они сохраняются поставкой без явного
поля `dictionaryBindings`, проверяются вместе с итоговыми схемами и не
изменяют контрольную сумму уже выпущенной поставки 7.

Коды, типы, фасеты, схемы, категории, привязки словарей и покрытие не меняются.
Это данные таксономии, а правила получения и поиска выражений универсальны.
Ранее выпущенная поставка 7 и её SHA-256
`decda65915fef151263a07f57be16b7ac9a32e866b4f533e6b1920e4b8f261d5`

целой поставкой. Нужно скачать её `attributes` и версию, добавить только

словаря. После публикации карточки перепроверяются и синхронизируются через outbox.
Магазинам нужны обновлённый снимок таксономии и переиздание поисковых проекций:

## Поставка 10: замена дерева с подтверждением оператора

Это ломающая поставка категорий. Решение владельца разрешает заменить коды
и адреса: рабочих магазинов нет, стендовые товары переназначаются. Требование
сохранять старые категории не действует; типы, единицы и прежние базовые
словари глобальных атрибутов защищены по-прежнему.

В историческом выпуске сопровождались шесть YAML-файлов: attributes, schemas, categories,
dictionary-bindings, category-migration и manifest. Первые пять входят в SHA-256
в таком порядке; перед байтами каждого файла идут его имя и нулевой байт.
Для старых комплектов без двух дополнительных файлов остаётся прежняя сумма
трёх файлов. Неизвестные поля и YAML-ссылки запрещены.
`manifest.replaceCategories: true` обязан соответствовать наличию миграции.
`fromRelease`/`toRelease` и каждый адресат таблицы проверяются; отдельный тест
сверяет её с неизменяемыми 1085 листьями поставки 9.

Наследование разворачивает Go. Проверки текущего загрузчика без БД:

```bash
make taxonomy-artifact
go run ./cmd/taxonomy check
go run ./cmd/taxonomy check --review > .scratch/taxonomy/leaf-schema-review.txt
go build ./...
go vet ./...
go test ./...
```

`check --review --direction accessories` ограничивает матрицу направлением;
неизвестное направление — ошибка. `check --export` выдаёт JSON с номером,
контрольной суммой и развёрнутым определением для внешней проверки.
Проверочные материалы магазинов хранятся в соседнем `demo-shops/taxonomy-fit`,
в комплект и тесты Go не включаются.

Перед применением оператор сохраняет текущий снимок, словари и назначения
товаров, проверяет [миграцию](taxonomy-release-10-migration.md), устанавливает
отдельную поставку недостающих словарей и сверяет текущую версию снимка.
`apply` требует явного подтверждения замены категорий. Цель `make dev`
передаёт его автоматически для одноразовой среды:

```bash
go run ./cmd/taxonomy apply --confirm-category-replacement --expected-version N
```

`N` — прочитанная версия снимка, а не номер поставки. Для пустой БД параметр
expected-version не требуется, подтверждение замены всё равно явное.
CLI отказывает без флага до подключения к БД; доменный план также проверяет
подтверждение. Флаг не обходит CAS и не разрешает ломать атрибуты. Повтор
подтверждённой поставки остаётся идемпотентным.

Поставка передаёт явный список dictionaryBindings: операторские правила
не переносятся на удалённые ветки молча. Нужно заранее согласовать их с
новыми путями. Переназначение карточек не происходит по первому адресу из
split; прежние неизвестные категории/поля при перепроверке скрывают карточку
до исправления. После переназначения обновляется индекс через обычный outbox.

Поставка 10 ещё не выпущена и не применена этой работой; пересборка её
непринятого черновика не является изменением опубликованного релиза.
После принятия номер и байты фиксируются. Следующее изменение — новый номер,
новый манифест и, если нужно, новая миграция соответствующего выпуска.

Простой rollback к поставке 9 не удалит добавленные глобальные атрибуты:
защита эволюции его отклонит. Для возврата дерева нужна корректирующая поставка,
сохраняющая все глобальные определения, с обратным планом назначений. История
БД сама по себе не восстанавливает исправленные вручную карточки магазинов.

## HTTP-загрузка поставки 10 — доработка 7

Порядок шагов поставки 10: **attributes → schemas → categories**. Разрыв дерева требует
явного `replaceCategories=true` только в PUT categories и свежего If-Match.
Лимит каждого тела — 2 МиБ. Новые метаданные и extends принимаются декодером;
API выдаёт развёрнутые схемы. Семь совместимых ключей схем нужны на промежуточном шаге.
Три PUT — три самостоятельные транзакции без записи истории CLI-поставок.
Точные действия, closed/confirmed-предусловия, правила dictionaryBindings и
судьба прежних карточек описаны в
[taxonomy-release-10-import.md](taxonomy-release-10-import.md).
