# Поставка каталога uno

Категории, атрибуты и привязки поставляются с загрузчиком в Docker target
`taxonomy`. Данные встраиваются в бинарник; запуск API, Kafka, Redis и
OpenSearch для загрузки не нужен. После установки рабочий источник —
постоянная PostgreSQL маркетплейса. Магазины получают данные через API.

Покрытие начальной поставки — [29 направлений](taxonomy-coverage.md).
Имена узлов, адреса категорий и целевой вид дерева — [taxonomy-structure.md](taxonomy-structure.md).
Переход данных на YAML и одну версию набора — [taxonomy-data.md](taxonomy-data.md).
Исходные файлы в `internal/infrastructure/taxonomydata/data/`:

- `attributes.yaml` — общие определения атрибутов;
- `schemas.yaml` — привязки и обязательность;
- `categories.yaml` — дерево категорий;
- `manifest.yaml` — номер поставки, SHA-256 файлов и счётчики покрытия.

Это данные маркетплейса; в движке магазина товарных констант нет. API отдаёт
полную схему каждой конечной категории без наследования полей от родителей.

## Проверка и установка

Проверка без БД и сборка отдельного образа:

```bash
make taxonomy-check
go run ./cmd/taxonomy manifest
make taxonomy-image TAXONOMY_IMAGE=proshop-marketplace-taxonomy:uno-4
docker run --rm proshop-marketplace-taxonomy:uno-4 check
```

Для загрузки оператор задаёт `DATABASE_URL` в своём окружении. Значение
передаётся по имени переменной и не входит в аргументы, образ или исходники:

```bash
make migrate
make reference-apply
docker run --rm --env DATABASE_URL proshop-marketplace-taxonomy:uno-4 apply
```

Адрес БД должен быть доступен из выбранной Docker-сети. Запуск из исходников
после миграций — `make taxonomy-apply`. `make dev` выполняет оба шага
последовательно после миграций и `reference-apply`, перед запуском API. В Kubernetes Job `marketplace-taxonomy`
запускается после `marketplace-migrate` и применения поставок словарей.
Закрытые словари должны уже содержать confirmed-записи; иначе публикация отклоняется. Локально и в production используется
один сохранённый образ; для production его можно закрепить по дайджесту.

## Повторы и обновление

Номер поставки независим от версии опубликованного снимка. Первая поставка
на пустом словаре версии 0 создаёт снимок версии 1. Повтор той же поставки
не меняет данные и версию, включая последующие правки оператора. Блокировка
строки снимка сериализует одновременные загрузки и операторскую публикацию.
Снимок, отметка поставки и одна задача `taxonomy.products.revalidate` фиксируются
одной транзакцией. Это относится также к загрузке частей (`LoadPart`) и откату.
Публикация не читает каталог: видимость существующих товаров обновляется асинхронно.
Новые события товаров сразу проверяются по текущей версии.

Подмена суммы, понижение номера или повтор отменённой поставки приводят
к отказу. Новая поставка автоматически применяется только к последнему
неизменённому результату загрузки/отката, сохраняя правки оператора от
неявной замены при upgrade приложения.

Если были правки оператора, сначала прочитать и сохранить текущий снимок
через API, сопоставить его с новой поставкой и подготовить итоговые данные.
После проверки можно явно разрешить замену именно прочитанной версии:

```bash
docker run --rm --env DATABASE_URL proshop-marketplace-taxonomy:uno-4 apply --expected-version 5
```

5 в примере — исходная версия из API. Если оператор успеет опубликовать
другую версию, команда откажется её затирать. Это полная замена снимка,
а не автоматическое слияние.

Следующая поставка: изменить исходные YAML и перечень покрытия, создать
новый манифест, проверить и выпустить новый образ:

```bash
go run ./cmd/taxonomy manifest --release 4 --write
make taxonomy-check
make test
make lint
```

Уже выпущенный номер и его содержимое не меняются. Манифест проверяется до
подключения к БД; неизвестные ссылки, пустые схемы и неполное покрытие — ошибки.

## Фоновая перепроверка

Обработчик outbox читает по 200 товаров по курсору `(tenant_id, product_id)`;
один вызов — одна транзакция и одна пачка. Курсор и признак завершения
хранятся в `taxonomy_revalidation` вместе с версией освежения сводок
`cards_version` и признаком `cards_dirty`, фиксируются атомарно с товарами и побочными задачами.
Блокировка прогресса сериализует повторных обработчиков даже после
истечения аренды outbox. Порядок блокировок: голова таксономии, затем
прогресс. Голова заблокирована лишь на время пачки.

Новая публикация заменяет payload ещё не взятой задачи, сбрасывает курсор,
но сохраняет `cards_version` и прежний `cards_dirty`. Если прежний проход
не завершён, сразу устанавливает `cards_dirty = true` в транзакции публикации,
даже если ещё не было первой пачки: другие задачи уже могли построить сводки
по промежуточной голове. Дедуп сохраняет ранний `next_at` (`LEAST`)
и не меняет взятую задачу. Устаревший обработчик завершает работу без
изменений. После сбоя повторяется та же задача после паузы, с последнего
зафиксированного курсора. Удалённые товары и товары с
`Publication.Version >= N` пропускаются.

Номер проверки сам по себе не меняет публикацию: неизменный товар не
сохраняется, его `Publication.Version` может отставать от головы.
При изменении `Published`, `Issues` или эффективной политики модерации
сохраняется публикация, ставится задача статуса, вызывается `Evaluate`
и ставится синхронизация предложения. Изменения ID, пути, полного имени
категории и проверенных атрибутов также сохраняются и синхронизируются,
но сами по себе не запускают модерацию. Политика сравнивается со снимком
`verdict.TaxonomyVersion`, а при отсутствии вердикта — `Publication.Version`.
Решение оператора текущей ревизии исключает повторную оценку и сохранение
только из-за смены политики; изменения самой публикации сохраняются.
Конфликты товара и вердикта повторяются в той же транзакции.

LRU сервиса хранит до 16 версий: только дерево ID/Name/Parent и эффективные
политики категорий, без атрибутов, схем и словарей исходного `Definition`.
Каждая пачка сравнивает полные деревья ID/Name/Parent версий `cards_version` и N.
Добавление, удаление, переименование или перенос любого узла освежает сводки
всех магазинов прохода. При отличии деревьев или `cards_dirty` ставится одна
`StoreCardTask` на магазин за проход с задержкой `STORE_CARD_REFRESH_DELAY`.
Завершение записывает `cards_version = N` и сбрасывает `cards_dirty`: все задачи
поставлены, их выполнение остаётся асинхронным. Замещение незавершённого прохода
устанавливает `cards_dirty` независимо от курсора и отличий деревьев, поэтому
откат освежает сводки даже при возвращении к исходному дереву.

`icon`, `slug`, `Title` нелистовых категорий, параметры фасетов и названия атрибутов
сами по себе задач не создают. Версия товара растёт при сохранении,
защищая индекс от устаревшей записи.

Незавершённый проход атомарно ставит отдельную строку продолжения с
`next_at = now`, доступную сразу. Общий цикл outbox не изменён: полная
пачка задач выполняется без паузы, неполная ждёт `OUTBOX_POLL_INTERVAL`.
При одном продолжении и малом числе побочных задач скорость ограничена
примерно `200 / (OUTBOX_POLL_INTERVAL + время пачки)` товаров/с.
При интервале 1 с и малом времени пачки это около 200 товаров/с:
100 тысяч — около 8,3 минуты, миллион — около 83 минут. Время запросов,
конкуренция и повторы увеличивают срок; заполненные пачки outbox могут
убрать паузу. Это оценка, а не результат нагрузочного измерения.

Журнал пачки содержит версию, курсор, число товаров и признак завершения;
ошибка содержит версию. Стандартные метрики outbox учитывают новый тип
задачи. Глобальная задача использует пустой `tenant_id`; квоты, аренда,
`FOR UPDATE SKIP LOCKED` и повторы с экспоненциальной паузой работают
через общий диспетчер.

## Откат

До каждой поставки БД сохраняет исходный снимок. Откат выполняется образом
отменяемой поставки:

```bash
docker run --rm --env DATABASE_URL proshop-marketplace-taxonomy:uno-4 rollback
```

Откатывается только последняя поставка без последующих правок оператора.
Данные восстанавливаются с новой возрастающей версией; повтор безопасен.
Понижение тега образа не откатывает БД. Повторный rollout отменённой поставки
завершится конфликтом; для продолжения выпускается новая версия поставки.
Откат также проходит проверку эволюции глобальных кодов: нельзя удалить код,
изменить его тип или единицу. Если предыдущий снимок нарушает это правило
(включая пустой снимок до первой поставки), откат завершится конфликтом.
В таком случае нужна новая корректирующая поставка с сохранением кодов.

Миграция `00026_taxonomy_releases.sql` добавляет отдельную таблицу истории.
Её снятие не является откатом каталога и удаляет историю поставок. CLI не
печатает `DATABASE_URL` или необработанные сообщения драйвера.

## Поставка 3: полные имена и адреса

Поставка 3 вводит необязательный `title` и обязательный `slug`, короткие имена
и новое дерево из принятого владельцем черновика. Выбыли 23 прежних листа
и разделы `clothing.underwear`, `clothing.sports`; правила деления и переноса —
в [решениях по устройству дерева](taxonomy-structure.md#целевой-вид-дерева--как-у-озона).
Карточки в выбывших категориях получат `taxonomy.category_unknown` и скроются,
пока магазин не выберет новую категорию.

Первое присвоение адресов снимку поставки 2 разрешено. После этого адрес
существующего `id` нельзя менять или отдавать другому `id`. Откат поставки 3
к снимку без адресов завершится конфликтом и потребует корректирующей поставки
с сохранёнными адресами.

## Поставка 4: нормализованный YAML-набор

В образ встроены только attributes.yaml, schemas.yaml, categories.yaml и
manifest.yaml. Манифест считает атрибуты со словарём (`dictionaries: 19`),
а не дублирующиеся значения: 29 направлений, 1282 узла, 1085 листьев,
142 схемы, 219 атрибутов. SHA-256 включает имена трёх файлов с нулевым
разделителем и точные байты каждого файла в порядке attributes, schemas, categories.

Команда `go run ./cmd/taxonomy manifest` проверяет исходные файлы на диске.
`--release N --write` записывает новый манифест; изменение данных с прежним
номером запрещено. Следующая после 4 поставка выпускается с `--release 5 --write`.
Команда `check` проверяет встроенный комплект, обе проверки работают без БД.

Снимки остаются в прежнем JSONB, миграций нет. Поставка 4 заменяет текущий
снимок целиком, старые снимки не преобразуются. Откат к снимку старого
развёрнутого формата (без глобальных атрибутов и схем) — конфликт.
Откат к нормализованному снимку сохраняет именно его Values, не подставляет
текущие значения реестра. Действуют ограничения эволюции: код нельзя удалить,
type, unit и dictionary неизменны. Нужные исправления выпускаются новой поставкой.

CLI `load` и `make taxonomy-load` удалены; оператор загружает отдельные части
через API с If-Match. Старый PUT целого документа удалён.

## Поставка 5: короткие имена направлений

Имена десяти направлений длиннее 20 символов переносились на две строки в
меню витрины. Поставка 5 даёт им короткое `name` для меню, а прежнее имя
переносит в `title` для заголовка страницы: «Посуда и кухня» — «Посуда и
товары для кухни». У направления «Оборудование» полное имя — «Оборудование
и средства защиты»: рабочая одежда с поставки 3 живёт в «Одежде». Адреса
`slug` не меняются. Атрибуты, схемы и остальное дерево — как в поставке 4.
