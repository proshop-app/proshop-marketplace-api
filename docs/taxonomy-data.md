# Данные таксономии: YAML, одна версия, потребители

Решения владельца 2026-11-05. Документ описывает, в каком виде хранятся и
загружаются категории, атрибуты и схемы, кто их правит и как они доходят до
сервера магазина. Имена, адреса и устройство дерева —
[taxonomy-structure.md](taxonomy-structure.md), выпуск поставок —
[taxonomy-releases.md](taxonomy-releases.md).

## Почему меняем

- Админка маркетплейса загружает таксономию YAML-файлом. Сейчас это один
  документ, где у каждой категории расписаны все атрибуты. На дереве поставки 3
  такой файл весит 2,47 МиБ, около 100 тыс. строк, а лимит загрузки — 2 МиБ
  и в админке, и в бэкенде.
- Строгая схема проверки в админке не знает `title` и `slug`. После поставки 3
  загрузка через админку не проходит ни с каким файлом.
- Значения 16 закрытых списков (цвет, пол, сезон, размеры, материалы) хранятся
  дважды: в атрибутах таксономии (`values`) и в реестре справочников
  маркетплейса. Копии могут разойтись.
- Сервер магазина раз в минуту скачивает дерево целиком (около 1,8 МиБ JSON),
  даже если версия не менялась.

## Решения

1. **Все данные — YAML, три файла:** `categories.yaml`, `attributes.yaml`,
   `schemas.yaml`. Атрибут описан один раз, схема ссылается на атрибуты,
   категория — на схему. Один формат для поставки в образе (начальные данные
   стенда и разработки), для загрузки и для выгрузки в админке.
2. **Одна версия на весь набор.** Загрузка любого из трёх файлов или правка
   схемы даёт новую версию всех трёх частей. Ссылки проверяются вместе:
   категория — на существующую схему, схема — на существующие атрибуты.
   История и откат — как сейчас.
3. **Админка маркетплейса, раздел «Таксономия»:** вкладки «Категории»,
   «Атрибуты», «Схемы». На каждой — просмотр, «Загрузить YAML» и «Скачать
   YAML». Схемы правятся в админке: состав атрибутов и обязательность решаются
   здесь.
4. **Значения — в словарях реестра.** Атрибут со списком значений ссылается
   на словарь маркетплейса (`dictionary: color`) и не держит значений у себя.
   Закрытые словари — 16 списков с теми же кодами, что у атрибутов; открытые —
   бренд, страна, материал (сейчас это свободные строки).
5. **Все атрибуты схемы по умолчанию обязательны.** Необязательные
   перечисляются в схеме явно.
6. **Сервер магазина забирает данные сам, по версии.** Он сверяет версию и
   скачивает категории, атрибуты и схемы, только если версия сменилась.
   Определения атрибутов сервер кладёт в platform, магазины берут их оттуда.
   Дерево категорий движок магазина запрашивает у маркетплейса, как сейчас.
7. **Схемы дорабатываются по содержанию** отдельной поставкой: в них много
   неточностей (см. ниже).

## Формат

Реализовано в поставке 4. Данные — три YAML-файла, рядом — manifest.yaml.

```yaml
# attributes.yaml
- code: color
  name: Цвет
  type: enum
  dictionary: color        # значения — в словаре реестра
  facet: true
- code: power
  name: Мощность
  type: number
  unit: Вт
  facet: true

# schemas.yaml
outerwear:
  attributes: [brand, gtin, model, country, size, gender, age, color, fabric_composition, season]
  optional: [brand, gtin, model, country, gender, age, color]         # всё остальное обязательно

# categories.yaml
- id: clothing.women-jackets
  name: Куртки
  title: Куртки женские
  slug: kurtki-zhenskie
  schema: outerwear
```

- Закрытый словарь (`color`) — значение карточки обязано входить в сохранённый
  список `Values` версии таксономии. Открытый словарь (`brand`) — значение любое, новое попадает
  в кандидаты, как сейчас собирает реестр.
- `enum` обязательно ссылается на закрытый словарь, `string` может ссылаться на
  открытый. У других типов `dictionary` запрещён. `valuesMeta` допустим только
  у enum; его ключи проверяются по подтверждённым значениям словаря.
- Входные файлы не содержат `values` и `required`. Разбор строгий: неизвестные
  поля, повторные ключи, несколько документов, якоря и ссылки YAML запрещены.
- При применении поставки и загрузке части словари проверяются в транзакции
  публикации. Закрытые списки непустые, берутся канонические confirmed-значения
  по `metadata.order` (при равенстве — по каноническому имени).
  Значения записываются в JSONB-снимок; проверка карточек, фасеты и варианты
  используют снимок без обращения к реестру.
- Изменение содержимого словаря вступает в силу со следующей версией таксономии.
  Автоматической перепубликации в этом шаге нет. Ссылку `dictionary`, тип и
  единицу существующего кода менять нельзя; глобальный код нельзя удалить.
- `taxonomy check` без БД проверяет структуру и ссылки внутри набора.
  Существование и вид словарей проверяются только при применении.
- Перевод нынешних данных в YAML механический: обязательность не меняется,
  нынешние необязательные атрибуты попадают в `optional`. Что действительно
  обязательно, решает доработка схем.

## API

Набор публикуется атомарно; все ответы чтения несут одну версию.

- `GET /api/v1/taxonomy/version` — одна версия набора; есть.
- `GET /api/v1/taxonomy/categories` — дерево: `id`, `name`, `title`, `slug`,
  `schema`, без расписанных атрибутов.
- `GET /api/v1/taxonomy/attributes` и `GET /api/v1/taxonomy/schemas` — новые.
- `GET /api/v1/taxonomy/categories/{id}/schema` — собранная схема категории
  для формы магазина; есть.
- ETag `"taxonomy-<version>"` и 304 — на всех ручках, как сейчас.
- `GET /api/v1/operator/taxonomy` — весь нормализованный набор в JSON.
- `GET /api/v1/operator/taxonomy/{part}` — YAML одной части; `part` —
  `categories`, `attributes` или `schemas`. Выгрузка не содержит вычисляемых
  значений, без правок пригодна для обратной загрузки.
- `PUT /api/v1/operator/taxonomy/{part}` — YAML до 2 МиБ, обязательный
  `If-Match: "taxonomy-<version>"`. Часть соединяется с двумя текущими,
  проверяется весь набор и публикуется версия +1 с перепроверкой карточек.
  Устаревшая версия — 409 по общей таблице ошибок; отсутствие/неверный
  If-Match или YAML — 400. Доступ — существующая авторизация оператора.
- Старый PUT целого документа удалён. CLI `taxonomy load`, цель
  `make taxonomy-load` и прежний `taxonomy/example.yaml` удалены:
  части загружаются через API, полный пример формата находится здесь.
- Публичные части возвращаются как `{version, categories|attributes|schemas}`;
  глобальные атрибуты содержат `dictionary`, `values`, `valuesMeta`,
  а собранная схема добавляет `required = !optional`.

Витрина берёт `attributes` из дерева для фасетов (`src/shared/sdk/facets.ts`)
и переходит на новые ручки вместе с этим изменением.

## Сервер магазина

- Клиент `src/infrastructure/marketplace-taxonomy` начинает обновление при первом
  обращении и раз в 60 секунд (`MARKETPLACE_TAXONOMY_REFRESH_MS`) спрашивает
  версию. Сейчас `refresh()` по умолчанию скачивает дерево всегда
  (`forceCategories = true`). Нужно скачивать категории, атрибуты и схемы только
  при смене версии или по ETag.
- Определения атрибутов из маркетплейса сервер кладёт в platform, магазины
  получают их оттуда. Значения словарей сервер уже берёт из реестра
  маркетплейса — `docs/reference-consumer.md` в proshop-server.

## Недочёты схем

Найдены при просмотре схем поставки 3; список владельца добавится сюда.

- У 64 из 142 схем обязателен один атрибут. Бренд и модель не обязательны нигде.
- `brand`, `gtin`, `model`, `country` есть во всех 142 схемах. При обязательности
  по умолчанию нужно решить, где они уместны.
- В 9 схемах два размера: свободная строка `size` и типизированный `size_clothing`,
  `size_shoes_eu` или `size_kids_height`.
- Пол задан категорией, а в 15 схемах есть ещё атрибут `gender`.
- «Возрастная группа» (`age`, свободная строка) — в 11 схемах, в том числе во
  взрослых.
- Детские носки, колготки, термобельё и купальники получили взрослую сетку
  размеров: схемы `underwear` и `swimwear` ссылаются на `size_clothing`.
- «Назначение» (`purpose`) — свободная строка, обязательная в 32 схемах.
- Из 219 атрибутов 104 — свободные строки; для фасетов нужны словари или числа.

## Порядок работ

1. **marketplace-api — выполнено (поставка 4).** YAML трёх файлов в поставке, одна версия, ссылки на
   словари, обязательность по умолчанию, ручки частей, загрузка и выгрузка YAML
   оператором.
2. **marketplace-admin.** Вкладки «Категории», «Атрибуты», «Схемы», загрузка и
   выгрузка YAML, редактор схем.
3. **proshop-server.** Скачивание по смене версии, приём атрибутов и схем,
   определения атрибутов в platform.
4. **Доработка схем** по содержанию — отдельной поставкой, с приёмкой
   владельцем, как дерево.
5. **Витрина.** Фасеты на новых ручках.
