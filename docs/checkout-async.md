# Асинхронное оформление

Решение владельца 18.11.2026: у покупки один ПВЗ (служба, код и город).
Площадка параллельно передаёт его каждому магазину; сроки остаются отдельными по группам.
Предварительное правило общих служб собрано в Checkout.CommonCarriers: пересечение
служб оставшихся магазинов. Без общей службы покупатель видит подключения магазинов
и может убрать магазин. Выбор другого пункта после начала создания заказов запрещён.
Покупателю доставка бесплатна; реальный тариф хранится расходом продавца в заказе
магазина. До подтверждения можно выбрать частичный состав: товары заранее
исключённой группы остаются в корзине и не входят в total. После подтверждения
состав и сумма не меняются без нового согласия: окончательный отказ возвращает
покупку в draft, группа получает причину, её известный/возможный заказ отменяется
по ключу. Заказы остальных групп сохраняются. После нового confirm повтор orders
использует прежние ключи и создаёт только ещё не созданные заказы.

Перед созданием покупки, подтверждением, записью намерения и каждым HTTP создания
площадка пакетно читает живые проекции предложения (один SELECT с JOIN участника,
реестра и модерации). Перед кассой и подтверждением оплаты повторяется та же проверка
для awaiting_payment. Отсутствие службы ПВЗ исключает только соответствующую группу.
Проверка CheckoutAvailable использует живую SQL-проекцию; дублирующее чтение индекса не требуется. Если готовность отозвана после
потерянного ответа создания, группа отклоняется с cancel-by-checkout: возможный заказ
магазина не остаётся без сверки.

Плата покупателя за доставку равна нулю. Дата покупки не передаётся серверу;
совместимость с прежним правилом цены отсутствует. Несовместимый договор
выкатывается за одну остановку оформления, см. README. Покупки со старой ненулевой
платой отменяются штатным POST `/api/v1/checkout/{id}/cancel` и оформляются заново.
Миграция 00058 удаляет старые столбцы цены участника без переписывания таблицы;
NOWAIT сразу отказывает при занятой таблице, после освобождения её нужно повторить.

После Create → Quote → Confirm запрос `POST /api/v1/checkout/{id}/orders` обновляет
расчёт доставки по единому выбранному ПВЗ покупки. Сервер проверяет свои настройки внутри quote. Изменившийся расчёт возвращает draft и DELIVERY_CHANGED.
При успехе намерение, контакт, неизменный снимок, списание корзины и outbox по каждой группе
фиксируются одним CAS и одной транзакцией. HTTP возвращает creating_orders.
Повтор возвращает текущий снимок. PAYMENT_STUB=false по-прежнему закрывает создание до записи.

Outbox использует существующие аренду, SKIP LOCKED и лимит на магазин.
Отдельный исполнитель выбирает checkout.create_order по виду: пул 16, максимум 2 активных вызова
на магазин. Завершённые задачи не ждут окончания остальных задач пачки.
checkout.expire_creation использует отдельные 4 места того же исполнителя и ставится при намерении
с availableAt = creationDeadline. checkout.poll_order имеет третью полосу: 4 места, не больше 1 на магазин.
checkout.cancel_order имеет собственную полосу: 4 места, не больше 1 на магазин.
Она не занимает места создания или регулярной сверки; медленная отмена не задерживает их.
Общий диспетчер исключает все четыре вида. Холостой опрос очереди — раз в 200 ms.
После результата исполнитель сразу делает одно взятие в его полосе, если есть свободное место
и ограждение допускает вызов. Задачи могли поступить уже после предыдущего взятия.
Штатный опрос обнаруживает новую работу во всех полосах.
Единственный путь создания — обработчик checkout.create_order; HTTP и Resume заказы не создают.
Resume выполняется с ORDERS_SYNC_INTERVAL (по умолчанию 30s) одной репликой установки: общий
интервал `orders-resume` в job_leases берёт первая реплика после его истечения, остальные проход
пропускают. Страница: до 100 созревших групп по индексу `checkout_groups_next_work` в порядке срока
(курсор — срок и покупка), их покупки — по ключу `FOR NO KEY UPDATE SKIP LOCKED`; занятую событием
или покупателем покупку проход пропускает до следующего. Задачи checkout.poll_order и отмены —
одной пачкой outbox, затем возврат товаров. Покупка, которую не удалось разобрать (строка не
читается, домен не сохраняет её), исключается из страницы с записью в журнал (`checkoutId`,
магазины) и откладывается на 10 минут; откатившаяся страница разбирается по одной покупке.
Событие статуса, пришедшее раньше сохранённого ответа создания (ответ потерян и сохранится повтором
или поздно; при самом создании сервер статус не публикует, только на переходах), подтверждается
сразу: состояния хранятся при группе (`EarlyOrders`, по одному на номер заказа, старшая ревизия
перекрывает младшую того же номера; не больше четырёх номеров — пятый вытесняет самый давний) и
состояние своего номера применяется той же транзакцией, что сохраняет ответ создания. Хранит
только группа, чьё создание заявлено и не истекло, — статус всей покупки не в счёт. Отказ при
привязке пишется в журнал и в `checkout_events_total{event="early_order_rejected"}`. Цена — одна запись покупки на событие,
как у обычного события; приём Kafka не ждёт и не повторяет. Ответ после срока создания: группа уже
оставлена, ранняя отмена не подменяет её итог, отмену ведёт сценарий площадки. Ответ не пришёл
никогда: исход даёт отмена по ключу — нынешнее состояние магазина, раннее снимается.
Запись покупки ждёт блокировку её строки не дольше `statement_timeout` класса пула (оформление,
приём и заказы — 2 с, фон — 10 с; транзакции записи покупки — миллисекунды). Срыв срока — ошибка
сервера без класса: покупатель получает внутреннюю ошибку и повторяет действие, приём Kafka
повторяет сообщение с паузой и после `KAFKA_MAX_ATTEMPTS` таких сбоев откладывает его в отравленные.
Создание заказа назначает страховочную проверку в действующий срок оплаты + PaymentExpiryGrace (2 минуты), а не сразу.
До этого срока неоплаченный заказ не опрашивается: оплату и отмену сообщает событие магазина.
Если событие потерялось, после срока с запасом выполняется один GET. Ответ awaiting_payment или отказ
оставляет проверку незавершённой. Успешный ответ обнуляет PollFailures; следующая задержка равна
времени после действующего срока оплаты + PaymentExpiryGrace, ограниченному снизу 30 секундами и сверху OrderSlowPoll
(30 минут). Сетевые и протокольные отказы увеличивают PollFailures: повторы через 30, 60, 120, 240 секунд,
после пятого отказа — 30 минут и seller_unreachable. Успешное ожидание оплаты не считается отказом.
Неизвестный исход отправленной оплаты (PaymentPending) проверяется не раньше чем через 30 секунд
после ClaimPayment (PaymentOutcomeDelay): запрос оплаты должен успеть завершиться до страховочного GET.
FinishPayment снимает проверку при оплате или переносит на срок с запасом при доказанном отсутствии оплаты.
Оплаченный или терминальный статус снимает проверку в той же транзакции; возврат в корзину остаётся
самостоятельной работой. Старый next_work_at после обновления исправляется первым проходом Resume;
повторного выбора покупки без созревшей работы нет.
Оплаченный заказ не опрашивается: его статусы приходят событием магазина
`orders.order.marketplace-status-changed`, а раз в сутки (константа OrderReconcileInterval)
площадка сверяет исполняемые заказы (полученные не сверяются) одним запросом на страницу заказов магазина —
`docs/server-contract.md`, «Событие статуса заказа» и «Сверка статусов пачкой».
Причина и отслеживание приходят вместе со статусом, дополнительные GET при расхождениях не нужны.
Исполнитель пробует запустить сверку при старте и затем каждый час. `ScheduledWork` при запуске
занимает общий для всех реплик интервал в 24 часа; отказ отдельного магазина его не сокращает.
В первом круге решение о досрочном прерывании из-за молчания принимается после запуска сверки
как минимум 32 магазинов. При 24 истёкших сроках без единого ответа исполнитель дожидается
начатых вызовов и проверяет условие снова. В конце первого круга достаточно 24 истёкших сроков
без ответа. Открытый размыкатель сервера прерывает проход сразу.
Прерванный недоступным сервером проход записывает итог до прерывания и возвращает интервал:
следующая часовая попытка повторяет сверку. Повторы не ответивших в срок магазинов — кругами после
остальных, без пауз в строю (`docs/server-contract.md`, «Сверка статусов пачкой»).

Срок — именованная константа CreationTimeout (15 секунд) в application/checkout.
Срок сохраняется при намерении и не продлевается повтором или перезапуском.
HTTP создания ограничен min(остаток срока, 5 секунд, существующий PLATFORM_API_TIMEOUT).
Бюджет вызова магазина сценарий передаёт данными (`ports.WithPlatformCallBudget`), а не сроком
контекста: срок вызову ставит только `platformguard`, поэтому его истечение — зависание магазина
и идёт в счёт размыкателя. Так устроены создание, опрос, отмена, stub-payment, расчёт доставки и
список ПВЗ; payment-hold и команды покупателя идут в строгом бюджете ограждения. Отмена запроса
покупателем, остановка процесса и истечение срока самого обработчика — решение вызывающего,
в счёт размыкателей не идут и в метриках дают исход `canceled`; `timeout` — только срок ограждения.
Ожидание места в ограждении и сам вызов ограничены бюджетом каждое: срок, по которому судят
магазин (и `x-marketplace-deadline-ms`), отсчитывается от начала его вызова. Конец ожидания места —
нейтральный `queue_timeout`: места могла занять чужая нагрузка, это не вина магазина. Поэтому вызов
целиком занимает до двух бюджетов. Создание из outbox ждёт место в общей очереди класса
`checkout` в пределах бюджета вызова и срока создания. У вызова создания тот же класс в метриках
и журнале. Создание передаёт крайний момент — срок создания
(`ports.WithPlatformCallDeadline`): ожидание места и вызов не идут дальше него, заголовок срока несёт
фактический остаток, а место, полученное к сроку, возвращается без вызова сервера (`deadline_passed`,
нейтрально): такой заказ всё равно закрыла бы задача срока. У опроса, отмены, stub-payment, расчёта и
ПВЗ крайнего момента нет: отмену и опрос надо довести до магазина, срок оплаты решает сервер
(`ORDER_PAYMENT_EXPIRED` с учётом payment-hold), расчёт и ПВЗ ограничены запросом покупателя.
Аренда попытки — min(два бюджета, остаток до срока создания) плюс 100 ms; штатный повтор создания —
через 1 секунду.
Остальные ошибки задач используют нарастающую паузу общего диспетчера.
Обработчик задачи исполнителя ограничен сроком «два бюджета вызова + 5 секунд записей» (до 15 с) —
это предел для опроса и отмены, у которых нет крайнего момента; создание кончает вызов к сроку создания,
аренда задачи фиксирована на 30 с от начала взятия. В срок входят взятие (до 5 с), обработчик,
запись полученного итога без отмены (до 3 с) и отметка задачи (до 5 с).
Цена: задачу упавшего процесса другой процесс берёт через 30 с, после срока создания; её группу
к этому времени закрывает задача срока (отдельная полоса) — creation_expired и отмена по ключу.

При зависшем магазине первый вызов ждёт 5 с; после PLATFORM_FAILURE_THRESHOLD (5) таких вызовов
размыкатель магазина открыт на PLATFORM_OPEN_INTERVAL (5 с), вызовы отклоняются сразу, место полосы
освобождается за миллисекунды. Отказ размыкателя несёт момент допуска (`ports.PlatformRejected`,
конец интервала, а пока идёт единственная проба — её строгий срок): задача создания откладывается
до него, а если допуск позже срока создания — завершается, группу закроет задача срока. Отмена
откладывается так же (общее правило исполнителя). Опрос после отказа уже ждёт доменную паузу от 30 с.
При открытом размыкателе сервера исполнитель пропускает взятие задач создания. После интервала
можно взять одну задачу для пробы, когда полоса создания свободна. Для пробы исключаются магазины
с открытым размыкателем или недавним таймаутом. Ответ любого магазина, включая начатый до размыкания
вызов, подтверждает доступность сервера и закрывает его размыкатель.
После строгого таймаута исполнитель на PLATFORM_OPEN_INTERVAL ищет кандидата также с конца очереди.
Когда такой кандидат есть, места получают магазины без недавних таймаутов, открытого размыкателя
и уже запущенного создания. При отсутствии кандидата выполняется обычное взятие.
Окно общего размыкателя (PLATFORM_FAILURE_MIN_CALLS, PLATFORM_FAILURE_PERCENT) учитывает строгий
таймаут, если у магазина закрыт размыкатель, за PLATFORM_FAILURE_WINDOW это его первый таймаут
и пока шёл вызов другие магазины не ответили. Строгие таймауты влияют только на долю отказов.
Таймаут короткого чтения (отзывы, сверка, 300 ms) учитывается только размыкателем магазина.
Запись итога повторяет только конфликт версии и unavailable с паузой от 20 ms до 1s и журналом.
Для полученного успешного ответа используется отдельный контекст завершения на 3 секунды.
Успех принимается, пока конкурентная задача не закрыла группу, даже при записи после срока.
Временный seller_unreachable не исключает группу. После срока активной попытке
даётся завершить короткую аренду, затем покупка возвращается в draft с прежним
составом и суммой. Группа получает creation_expired; новое подтверждение не продлевает срок.
Возможный заказ сверяется отменой по ключу, чтобы освободить резерв; сама группа при этом
не исключается и её товары ещё не возвращаются. Здоровые заказы сохраняются.
POST `/api/v1/checkout/{id}/groups/{tenantId}/remove` — явное решение покупателя:
убрать группу, вернуть её товары в корзину и потребовать нового подтверждения суммы.
Повтор удаления безопасен. До конца окна можно подождать автоматических повторов либо убрать
магазин; после конца окна — убрать его и продолжить с остальными или отменить покупку.
Автоматического уменьшения состава при seller_unreachable нет.
При остановленном исполнителе чтение остаётся честным снимком базы: до восстановления фонового
прохода оно может ещё показывать creating_order. Ни GET, ни часы браузера не создают локальный итог.

GET `/api/v1/checkout/{id}` читает только свою базу. Витрине следует показывать прелоадер
и опрашивать раз в 1s, прекращая опрос ожидания при creationComplete=true.
Поле группы creationStatus: creating / created / unconfirmed / rejected; причина отказа — reason.
Полный жизненный статус status сохраняется отдельно: creating_order — создаётся; awaiting_payment — создан; unconfirmed — не подтверждён;
price_changed/delivery_unavailable/rejected с reason — отказ. Временный seller_unreachable
ещё не итог; createExhausted означает окончательный отказ. При draft/confirmed
опрос ожидания создания останавливается; покупатель видит причину и подтверждает заново.

Единая касса доступна только после итога всех групп и только за awaiting_payment.
При изменении подтверждённого состава оплата закрывается до нового confirm/orders.
Перед кассой и оплатой отзыв готовности снимает группу, ставит cancel-by-checkout
и возвращает draft с новой суммой. Остальные заказы не создаются повторно.
Временная ошибка магазина требует повтора, а не исключения.
Полный публичный путь начинается с `/api/v1`. Отмена повторяема, закрывает оплату и возвращает
товары; группа с возможным заказом получает cancellation_requested.
Если попытки создания не было, группа сразу получает rejected с reason=buyer_cancelled. cancelled означает подтверждённую отмену магазина.
До подтверждения заказ и резерв остаются у магазина. creationStatus остаётся created у ранее созданного заказа.
Проведение платежа фиксирует PaymentStarted до внешних вызовов: после этого отмена отклоняется,
включая неопределённый результат платежа. Достоверное отсутствие оплаты всех групп (после неопределённой попытки — через сверку)
снимает блокировку; токен попытки не позволяет старому ответу снять защиту новой оплаты.
Безопасный повтор платежа и сверка восстанавливают итог.

Кабинет GET `/api/v1/orders` выбирает только покупки с хотя бы одним orderId до пагинации.
Созданные неоплаченные заказы остаются видны после ухода со страницы: awaiting_payment — «не оплачен»;
если другая группа ещё создаётся, кабинет уже показывает awaiting_payment,
но creationComplete=false продолжает закрывать оплату; GET самой покупки остаётся creating_orders.
Намерение, не породившее ни одного известного заказа, документом кабинета не становится.

Возврат в корзину сохраняет добавленные после оформления позиции, возвращает каждую группу один раз.
При переполнении сохраняется остаток returnRemaining и повторяется через минуту; returnFailed
не блокирует оплату других созданных заказов. Скидки и промокоды сохраняют прежние правила.

Команда cancel-by-checkout описана в [действующем контракте](server-contract.md#отмена-по-ключу-оформления).
При окончательном отказе после неоднозначной попытки или отмене покупателем запись группы и задача
checkout.cancel_order фиксируются одной транзакцией. Флаг CancellationQueued запрещает повторную
постановку, в том числе во время аренды или backoff. Возврат товаров окончательно
снятой группы изолирован от HTTP отмены. Сбой HTTP и 503 повторяются с нарастающей паузой общего диспетчера.

Команда использует ключ создания, поэтому отсутствие orderId не мешает отмене.
Ответ cancelled или absent снимает reconciliationRequired: группа cancellation_requested
становится cancelled; группа unconfirmed сохраняет итог создания unconfirmed.
Сервер навсегда закрывает ключ и освобождает резерв существующего неоплаченного заказа.
Поздний ответ создания не возвращает подтверждённую отмену на сверку и не открывает оплату.
ORDER_CHECKOUT_CANCELLED при создании — окончательный отказ, повторов POST нет.

При ORDER_NOT_CANCELLABLE сохраняются orderId, статус магазина и причина
order_not_cancellable:<status>; группа остаётся на сверке и видна оператору в
`/api/v1/operator/checkouts?stuck=true`. Отмена не повторяется; GET отслеживает известный заказ
до delivered, returned или cancelled, после чего сверка снимается. Журнал и метрика cancellation_refused содержат магазин.
Обычное ожидание подтверждения отмены больше не использует GET до cancelled.

Пока команда не подтверждена, заказ и резерв могут оставаться у магазина до expiresAt;
повторное оформление возвращённых товаров может получить OUT_OF_STOCK.
Покупки с незавершённым созданием на момент первого выката нужно закрыть вручную на стенде.

На группе сохраняются cancellationAttempts и cancellationLastErrorCode, доступные оператору.
Некорректный ответ, расхождение orderId и absent при известном заказе прекращают повторы
команды и оставляют группу на сверке с причиной; сеть и 503 повторяются.
Покупки «на сверке без заказа» до этой версии команду отмены не получат и закрываются вручную.
Клиент включается только после полной выкладки сервера магазина: старый под не читает запрет создания.

Поле payableTotal в состоянии покупки и кабинете — сумма кассы в рублях; при недоступной оплате — 0.

GET `/api/v1/payment-stub/{id}` только читает состояние. Он и GET покупки добавляют
`paymentHold` из текущей проекции без записи в покупку. Перед POST открытия кассы и
подтверждения оплаты готовность проверяется заново; оплаченные группы не проверяются.
POST `/api/v1/checkout/{id}/groups/{tenantId}/cancel-order` и
`/api/v1/checkout/{id}/groups/{tenantId}/return-request` при успехе возвращают тот же
актуальный снимок, что GET покупки, включая `paymentHold` и `payableTotal`.
Это действует и для повтора, который обходится без команды магазину.
Решение владельца 18.11.2026: Pending и временная приостановка публикации сохраняют
уже созданный неоплаченный заказ, состав, сумму и исходный expiresAt. `paymentHold`
равен `moderation_pending` либо `publication_paused`; после срока — `payment_expired`.
GET покупки возвращает 200 со снимком: payableTotal включает только доступные неоплаченные группы.
Здоровые группы оплачиваются после удержания, приостановленная остаётся до своего действующего срока. Возвращение товара
разрешает доплату; истечение отменяет только её заказ обычным механизмом магазина. Когда неоплаченных
групп не осталось, общий статус paid. Отказы Pay/ConfirmPayment сохраняют актуальный снимок.
Окончательный Rejected требует пересмотра состава. При уже оплаченной группе общий статус остаётся
результатом rollup; confirmationRequired запрещает доплату до нового Confirm. Оплаченные, отправленные,
доставленные и возвращённые группы не отменяются RemoveGroup, ReviewGroups или Cancel.


Если план устарел во время маршрутизации или расчёта тарифа, сервер проверяет суммарный
свободный остаток всех активных складов без маршрутизации и расчёта перевозчика.
Есть остаток (включая заказ, собираемый с довозом из частей) — сохраняет
409 `DISPATCH_ORIGIN_CHANGED` с поколением `data.dispatchReviewRevision`, нет — прежний
окончательный `OUT_OF_STOCK` только при суммарной нехватке. Пересчёт выбирает ближайший
полный склад, а при отсутствии полного — ближайший с довозом.
Площадка сначала сохраняет draft и `delivery_requoted`,
снимает старую задачу создания, затем делает один расчёт для неизменного ПВЗ. Успешный
расчёт передаёт `dispatchReview` и открывает только это поколение попытки магазина.
Покупатель видит причину «Доставка пересчитана: товар отправится с другого склада»
и новый срок; цена доставки остаётся 0. Только новое подтверждение и orders разрешают
создание с прежним ключом. При сбое расчёта можно повторить его для того же ПВЗ либо
убрать магазин. Фонового повтора создания до согласия нет; остальные заказы сохранены.
Потеря 409 до записи draft безопасна: повтор сервером возвращает тот же сохранённый отказ;
потеря ответа расчёта после записи draft оставляет покупку на подтверждении.

Общий справочник перевозчика загружается независимо от состава первого запросившего.
В процессе до четырёх загрузок, до 32 ожидающих уникальных ключей; бюджет включает очередь.
Источники перебираются с ротацией по подходящим магазинам, после ошибки выбирается следующий.
Класс catalog не занимает места магазина и не влияет на его размыкатель. Пустой город
кэшируется 30 секунд, отказ — 5 секунд; положительный справочник сохраняет прежний TTL.

Переход на один ПВЗ — одна остановка оформления и миграция 00060. Draft/confirmed без
созданных заказов сбрасывают выбор и расчёты: покупатель выбирает единый пункт заново.
Старые поля Delivery из JSONB групп удаляются; суммы и ключи заказов не меняются.
Перед переключением покупки с разными ПВЗ и уже начатым созданием завершаются или
отменяются штатной командой; новые заказы после переключения используют только checkouts.delivery.

При записи намерения площадка сохраняет в `groups[].ExpiresAt` срок оплаты
PaymentWindow = 10 минут от записи, усечённый до миллисекунд. Команда создания
передаёт его в обязательном `paymentDueAt` и принимает ответ только при точном
совпадении `expiresAt`. Фоновый повтор и повтор с неизвестным исходом сохраняют
срок своей попытки.

После нового согласия живые неоплаченные заказы задают срок новым группам.
Если исходный срок живого заказа истёк, создание возвращает `checkout.payment_expired`
до вызова магазина. После `DISPATCH_ORIGIN_CHANGED` без живых неоплаченных заказов
новое намерение получает свежий срок. Ответ `MARKETPLACE_PAYMENT_DUE_INVALID` завершает
попытку создания отказом и возвращает товары в корзину.

POST открытия кассы (Pay) после проверки готовности параллельно отправляет
payment-hold всем готовым группам без удержания. Магазин однократно устанавливает
paymentHeldUntil = max(now + 5 минут, paymentDueAt), никогда не сокращая исходный срок.
Магазин сохраняет и возвращает удержание с точностью до миллисекунды.
Успешные результаты сохраняются в JSON
order_progress одной транзакцией покупки, даже если другой магазин отказал.
При любом отказе касса не открывается; повтор обращается только к группам без
сохранённого удержания. Истёкший срок — payment_expired, остальные отказы —
payment_unavailable. GET и ConfirmPayment сами удержание не запрашивают.

Действующий срок группы — PaymentHeldUntil, если оно есть, иначе ExpiresAt.
По нему проверяются оплата и страховочный GET (+ PaymentExpiryGrace).
Событие и сверка передают удержание по прежнему правилу ревизии.
Публичное groups[].expiresAt отдаёт действующий срок, в том числе в кабинете;
для всей доступной к оплате части покупки витрина берёт минимальный срок её групп.
Отдельное публичное поле не вводится. Срок хранения резерва может отличаться между
группами после удержания: каждый сервер берёт позднее из исходного срока и 5 минут от команды.
Раннее нажатие сохраняет 10-ю минуту; нажатие на последней секунде даёт ещё 5 минут.
Ответ stub-payment 409 ORDER_PAYMENT_EXPIRED переводится в checkout.payment_expired;
сервер отменяет заказ обычным порядком с событием.
