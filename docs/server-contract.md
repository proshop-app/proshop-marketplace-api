# Контракт внутреннего API сервера для маркетплейса (PR-M1)

Источник требований PR-M1 в proshop-server и клиента `infrastructure/platformapi`.
Решение владельца 2026-11-07: вариант В, один платёж за покупку; заказы независимы.
Сейчас деньги не движутся (болванка); боевая оплата — сплит ЮKassa. Фикстуры запросов/ответов —
`internal/infrastructure/platformapi/testdata`, проверки адаптера — httptest.
Пока PR-M1 не установлен, магазины недоступны, участие не включается.
Сервер и marketplace-api выкатываются одновременно. Сервер поддерживает `profile`/`card` в сверке настроек.
Сервер должен отдавать 200 с профилем и готовностью также кандидатам без настроек доставки.

## Общее

| Что | Как |
|---|---|
| Адрес | `PLATFORM_API_URL` + `/api/v1/internal/marketplace/tenants/{tenantId}` + путь |
| Магазин | только tenantId в пути; сегменты экранируются |
| Доступ | `x-internal-token: <SERVICE_TOKEN_MARKETPLACE>`, минимум 32 символа |
| Формат | JSON, `Accept: application/json`, у тела `Content-Type: application/json` |
| Деньги | целые копейки int64 ≥ 0; в событиях — рубли через json.Number и money.ParseRubles |
| Время | RFC 3339 с зоной |
| Успех | 200, включая повтор создания; ответ до 4 МиБ |
| Ожидание | PLATFORM_API_TIMEOUT (5s); витринные чтения PLATFORM_READ_TIMEOUT (300ms); доставка QUOTE_TIMEOUT |
| Повторы | клиент не повторяет сам; сага повторяет создание с прежними ключом и телом |

Неизвестные поля игнорируются. Отсутствующие обязательные поля и нарушение
ограничений — `platform.invalid_response`; обязательные настройки участия —
`platform.invalid_settings`. `null` в настройках доставки означает «не настроено»,
а не ошибку ответа. Не-null невалидная доставка — `platform.invalid_settings`
с журналом и метрикой. Неполная карточка исключает кандидата из очереди, но сама не меняет видимость.
Видимость: `Visible = Enabled && tenant active && DeliveryValid`.
Ошибка сервера: `{"ok":false,"message":"…","status":409,"code":"…","items":null,"data":null}`.

| HTTP/code | Смысл и действие маркетплейса |
|---|---|
| 403 MARKETPLACE_DISABLED | магазин не участвует; `platform.marketplace_disabled`, внеочередная сверка настроек |
| 409 MARKETPLACE_PROMO_CODE_INVALID | заказ не создан; data.promoCode содержит код и причину отказа |
| 409 PRICE_CHANGED | заказ не создан, резерв и платёж не созданы; items — актуальные цены всех изменённых позиций |
| 409 DISPATCH_ORIGIN_CHANGED | заказ не создан; есть подходящий склад, требуется новый расчёт и согласие; data.dispatchReviewRevision связывает расчёт с сохранённым отказом |
| 409 OUT_OF_STOCK | окончательный отказ без заказа; группа rejected, товары возвращаются в корзину |
| 409 DELIVERY_UNAVAILABLE | окончательный отказ без заказа; группа delivery_unavailable, причина reason, новый ПВЗ и новое оформление |
| 409 DELIVERY_CHANGED | плата доставки отличается от текущего расчёта; заказ не создан, группа delivery_unavailable, новое оформление |
| 409 IDEMPOTENCY_CONFLICT | тот же ключ с иным телом; окончательный отказ без orderId; группа возвращается в корзину и исключается из платежа |
| 409 ORDER_CHECKOUT_CANCELLED | ключ создания навсегда закрыт командой отмены; окончательный отказ без повторов создания |
| 409 ORDER_NOT_CANCELLABLE | отмена отклонена: orderId и текущий status сохраняются для операторской сверки |
| 503 MARKETPLACE_TEMPORARY_FAILURE | временный сбой; безопасный повтор команды с паузой |
| 404 ORDER_NOT_FOUND | заказ не найден в этом магазине; повторить сверку, локально не отменять |
| прочие коды/таймаут | seller_unreachable, остальные группы продолжают; создание ограничено сроком 15 секунд, неизвестный код журналируется с tenantId |

`403 MARKETPLACE_DISABLED` ставит outbox `participant.settings.sync` с дедупом.
Сверка обновляет настройки и готовность; временная недоступность сохраняет последний снимок.
403 при сверке и невалидные настройки обнуляют доставку и тем скрывают магазин.
Карточка и скрытия оператора при этом не меняются; стадия участия сохраняется.

## 1. Публичная цена и наличие позиций

`POST /api/v1/internal/marketplace/tenants/{tenantId}/items/check`

Запрос: `{items:[{productId,quantity}], promoCode?}`.
`promoCode` передаётся только непустым. Покупатель не участвует в расчёте цены
и проверке промокода; поле `buyerId` в запросе отсутствует.
Покупатель площадки и клиент магазина — разные учётные записи.

Ответ: `{items:[{productId,available,availableQuantity,price,discounts:[{promotionId,amount}]}], promoCode}`.
`promoCode` — `{code,valid,discount,message}` либо `null`; правила отказов описаны в R5 ниже.
Старый сервер (`origin/master`, `marketplace.service.ts`, `check`) уже принимает этот запрос
и возвращает эти поля, а также `promotions`. Адаптер площадки игнорирует дополнительные
поля ответа без строгого разбора, поэтому новая площадка совместима со старым сервером.
Удаление серверного `/pricing/contexts` выкатывается не раньше новой площадки.
Деньги — целые копейки. `available` означает, что товар продаётся;
`availableQuantity` — свободный остаток ≥ 0. Клиент проверяет полноту и уникальность строк.
Недоступная позиция, нехватка остатка, изменение цены и скидок проверяются корзиной и оформлением.

Публичная цена канала `marketplace`: тип из настроек канала → базовый тип.
Отсутствующая цена переходит к следующему типу; ноль является ценой.
Группы покупателей площадки не участвуют. Настройки типов цен каналов `storefront`
и `marketplace`, персональные цены клиентов магазина и shopper-context витрины не меняются.

Проекция `catalog.product.projected` / `catalog.product.projected.bulk` v1 сохраняет формат
`priceProfiles` с `key`, `price`, `promoPrice`, `effectivePrice` в рублях.
Для площадки сервер публикует только `marketplace:default`; площадка читает только этот ключ,
переводит суммы через `json.Number` / `money.ParseRubles` и хранит `Price`, `BasePrice` в копейках.
Отсутствие публичной цены скрывает предложение, нулевая цена допустима.
Складские ценовые сигналы не меняют цену канала. Служебный контракт поиска — версия 9:
документ содержит `price`, `basePrice`; запрос не содержит ценовых контекстов.
Старый индекс требует пересборки. Гость и вошедший покупатель видят одинаковую цену.

## 2. Стоимость доставки

`POST /delivery/quote`

```json
{"carrier":"cdek","pickupPointCode":"P1","city":"Город","items":[{"productId":"p1","quantity":2}]}
```

Перевозчик — код справочника маркетплейса; ПВЗ — его код у перевозчика.
Ответ при доступности:

```json
{"available":true,"cost":30000,"minDays":2,"maxDays":4,"expiresAt":"2026-10-24T10:30:00Z"}
```

При отсутствии доставки: `{"available":false,"reason":"no_rate"}`.
`cost` — реальная цена перевозки этой группы по договору продавца,
без промо витрины. `0 ≤ minDays ≤ maxDays`; expiresAt необязателен,
маркетплейс ограничивает срок QUOTE_TTL; истёкший ответ не принимается.

Решение владельца 17.11.2026: покупатель площадки всегда получает доставку до ПВЗ
бесплатно. `deliveryPrice`, публичный `buyerCost` и `DeliveryTotal` равны 0.
Настройки `freeDeliveryFrom`, `subsidy` и прежний минимальный процент удалены. Реальный `cost`
считается по договору каждого продавца и сохраняется в `order.delivery.tariffCost`
(рубли серверного заказа); он не входит в amount, оплату или возврат покупателю.
Срок берётся из числового диапазона перевозчика без добавок. Нет срока — `no_rate`,
а не диапазон 0–0. Исторические уже созданные заказы не пересчитываются.

| reason | Кто | Значение |
|---|---|---|
| carrier_not_connected | сервер | нет перевозчика |
| pickup_point_unavailable | сервер/маркетплейс | продавец не везёт в этот ПВЗ/регион/этим способом |
| no_rate | сервер | тариф не рассчитан |
| seller_unreachable | маркетплейс | нет ответа или он не по контракту |

Словарь закрыт. available=false запрещает подтверждение с этим ПВЗ:
покупатель меняет ПВЗ либо убирает группу и оформляет новую покупку.

### Пересчёт после смены склада

Парный код `409 DISPATCH_ORIGIN_CHANGED` сохраняется в попытке с
`data: {dispatchReviewRevision: <положительное целое>}`. Это запрет создания до
пересчёта, а не окончательный отказ по остатку. Повторы с тем же телом получают этот же
отказ; другое тело по тому же ключу — `IDEMPOTENCY_CONFLICT`.

Только новый расчёт этой группы дополняет POST `/delivery/quote` полем:

```json
{"dispatchReview":{"externalCheckoutId":"checkout1:t1","groupId":"t1","revision":3}}
```

Остальные поля запроса расчёта прежние. После успешного расчёта сервер атомарно снимает
лишь отказ с совпадающими ключом и поколением; `available:false`, обычный расчёт без
контекста и поздний расчёт прошлого поколения его не снимают. Отменённый ключ или
созданный заказ не изменяются. Площадка до расчёта фиксирует draft, новую причину и
запрет фонового создания, затем показывает срок и требует нового подтверждения.
Тело POST `/orders`, его отпечаток и ключ группы не меняются; после подтверждения
повтор создаёт один заказ. Склад выбирается по правилу: ближайший с полным заказом;
если полного нет — ближайший с довозом с остальных активных складов. `OUT_OF_STOCK`
допустим только при суммарной нехватке свободного остатка. Часть заказа на каждом из
двух складов — тот же пересчёт и новое согласие, а не отказ по наличию.

При создании заказа внутренние `DELIVERY_ORIGIN_CHANGED` (снимок после маршрутизации) и
`INVENTORY_DISPATCH_PLAN_STALE` (резерв после расчёта тарифа) переводятся одним путём
в сохранённый `DISPATCH_ORIGIN_CHANGED`. Покупка не получает внутренний код или 503
вместо требования пересчёта. Только технический сбой проверки складов остаётся 503.

### Пункты выдачи магазина

`GET /api/v1/internal/marketplace/tenants/{tenantId}/delivery/pickup-points?carrier=cdek&city=Москва`

Как у соседней `POST …/delivery/quote`: заголовок `x-internal-token`, tenant из пути, ответ — «сырой» JSON
без обёртки `{ok, data}`, всегда 200 при корректном запросе:

```json
{ "available": true, "items": [ {
    "carrier": "cdek", "code": "MSK123", "name": "СДЭК", "address": "Профсоюзная ул., 58",
    "city": "Москва", "regionCode": "RU-MOW", "location": { "lat": 55.676, "lon": 37.554 },
    "schedule": "Ежедневно 09:00–21:00"
} ] }
```
```json
{ "available": false, "reason": "carrier_not_connected" }
```

- `carrier` — код службы маркетплейса (тот же, что в `delivery/quote`), `city` — название города, 1–120 символов.
- `code` — тот же идентификатор пункта, который магазин принимает в `pickupPointCode` ручки `delivery/quote`.
- `regionCode` — ISO 3166-2, тем же сопоставлением, что в расчёте. Пункты без региона исключаются.
  Справочник общий для `(carrier, city)`, без фильтра регионов магазина. Разрешения проверяются при quote.
- `reason`: `carrier_not_connected` — служба не подключена у магазина или не разрешена в настройках маркетплейса.
  Включая магазин без настроек доставки: это HTTP 200, не временный отказ и не сбой размыкателя.
  Площадка ставит внеочередную сверку настроек с дедупом; следующий источник выбирается заново
  после завершения предыдущего обращения, чтобы не использовать устаревшую пачку участников.
- `schedule` — строка, может быть пустой. Обрезания справочника нет.
- Первый запрос без курсора, затем `cursor=<nextCursor>`: фиксированные страницы
  по 512 точек, ответ дополняется `{total,nextCursor}`. Курсор содержит смещение и SHA256
  снимка. Иная версия — 409 `MARKETPLACE_PICKUP_CATALOG_CHANGED`, неверный курсор — 400.
- Транспортный предел 4 МиБ применяется к странице; площадка собирает все страницы в
  общий часовой справочник `(carrier, city)`, ключ v3. В памяти один индекс на запись:
  сетка 0,02° с упорядоченными столбцами/строками и региональными счётчиками;
  граничные ячейки содержат простые списки позиций точек.
- Карта читает аутентифицированный GET
  `/api/v1/checkout/{checkoutId}/delivery/pickup-points?carrier&city&tenantId&bbox`.
  `bbox=юг,запад,север,восток`; только разрешённые регионы выбранной группы.
  Без tenantId используется объединение разрешений групп покупки.
  Ответ `{items,total,refineArea,bounds,offset,limit}`: внутри bbox до 500 точек,
  total точный, refineArea означает «увеличьте карту»; bounds — охват разрешённых регионов.
  Предел 500 ограничивает размер JSON и работу WebGL на мобильном клиенте.
  Без bbox остаются страницы списка: offset>=0, limit=100, максимум 200; отдельные
  списки позиций по регионам дают O(R + limit) без обхода города.
- Холодный справочник: ceil(P/512) HTTP площадка→сервер и одна загрузка перевозчика.
  Тёплый viewport не вызывает сервер/перевозчика: бинарный поиск ячеек, длины списков
  целых ячеек, проверка координат граничных и отбор до 500 результатов. Стоимость
  O(log C + затронутые ячейки × R + точки граничных ячеек + 500); в предельном
  случае плотного города в одной ячейке проверяются все его точки.
  Источники — только магазины покупки; участники и реестр читаются двумя пакетами.
- Одновременные промахи склеиваются внутри процесса площадки. Сервер получает общий
  `SingleFlightCache` через DI: один промис на ключ внутри процесса, Redis-аренда
  между процессами, паузы 50→100→200→400→800 мс в пределах HTTP-бюджета.
  Сбои Redis журналируются один раз на вид; доступность сохраняется без межпроцессного склеивания.
  Локальный бюджет сериализованных справочников — 64 МиБ: один больший справочник
  сохраняется целиком, вытесняя остальные. Это бюджет кэша, а не предел ответа/города.

## 3. Настройки участия магазина

`GET /settings/marketplace`, сверка на старте и раз в SETTINGS_SYNC_INTERVAL.

```json
{
  "delivery": {"regions": ["RU-MOW"], "carriers": ["cdek", "yandex"]}
}
```

| Поле | Обязательное правило |
|---|---|
| delivery | null — не настроено; иначе объект с непустыми regions и carriers |
| delivery.regions | непустой список существующих кодов ISO 3166-2 RU, например `RU-MOW` |
| delivery.carriers | непустой список перевозчиков из закрытого перечня `cdek`, `yandex` |

Снимок настроек участия пересекает разрешённые службы с включёнными в CredentialsVault.
Если подключённых служб ПВЗ нет, `delivery=null`; фоновая сверка не делает такую группу доступной.
Выбор интеграций читается через кэш с версией: на тёплой сверке одно GET версии Redis,
без дополнительного чтения Mongo или вызова перевозчика. Изменение выбора увеличивает версию.

Географические регионы не привязаны к перевозчику. Магазин возвращает ISO-коды
в настройках и списке ПВЗ; пункты без региона или вне его настроек не возвращаются.
Маркетплейс проверяет выбранный код по списку `(carrier, city)` и сохраняет
город, адрес и регион из ответа магазина. Покупатель не подставляет произвольный регион.
Миграция старых зон и работа оператора описаны в [operator-gateway.md](operator-gateway.md).
Вне списка регионов или способов предложение доступно для просмотра,
но недоступно к доставке. Окончательная проверка — quote магазина. В HTTP каталога это поле
`deliveryAvailable` при паре query `deliveryCarrier` и `deliveryRegion`;
покрытие доступно в `seller.delivery`. Порог бесплатной доставки из каталога удалён.
Справочник ПВЗ отдаёт `regionCode`. При смене схемы индекс каталога
перестраивается автоматически новым поколением.

Настройки `subsidy`, `freeDeliveryFrom`, минимальный процент и публичная ручка
`GET /api/v1/delivery/settings` удалены. Бесплатность задаёт площадка.
Сервер принимает только нулевую deliveryPrice, старые поля настроек не возвращаются.
Несовместимое обновление выполняется за одну остановку оформления (README площадки);
переходные даты, заголовки версии и закрытые снимки прежней цены отсутствуют.

Согласия магазина нет: верхнеуровневое `enabled` не читается и не требуется.
Отсутствие обязательных настроек запрещает оформление через
магазин, сохраняя стадию участия. Видимость: `Visible = Enabled && tenant active && DeliveryValid`.
Каждый активный магазин автоматически становится кандидатом
с доверием `probation`; на старте и перед каждой сверкой выполняется догон реестра.

Сервер читает `GET /api/v1/internal/tenants/{tenantId}/participation` на маркетплейсе
с `Authorization: Bearer <SERVER_API_TOKEN>`. Ответ: `stage`, `awaitingReview`,
`deliveryValid`, `lastDecision: {reason, note, at, operator}` или `null`.
Не настроенный SERVER_API_TOKEN — 404; отсутствующий или неверный Bearer — 401,
как и у машинного API продвижения.
`POST /api/v1/internal/tenants/{tenantId}/participation/submit` без тела переводит
только `returned` в `candidate`, устанавливает `awaitingReview=true`, сохраняет
последнее решение; из остальных стадий — 409 `conflict`. Кнопку показывает сервер
магазина; согласие на участие не запрашивается.

## 4. Заказ и оплата

### Согласование перед созданием

До перехода confirmed → creating_orders маркетплейс повторяет quote выбранного ПВЗ
каждой группы параллельно через класс `checkout` предохранителя. Отдельного HTTP за
настройками нет: актуальные подключения и разрешения проверяет сервер в quote и
в транзакции создания. В публичном снимке один `delivery` у покупки; у группы
остаются `carriers`, `regions` и собственный расчёт срока. Корневой `carriers` —
весь перечень служб площадки в порядке общего справочника API. Для участия
магазину обязательны все службы; `carriers` внутреннего ответа настроек —
производный факт готовности интеграций, а не редактируемое поле магазина.
POST `/api/v1/checkout/{id}/delivery/quotes` принимает только
`carrier/pickupPointCode/city`; tenantId/tenantIds отвергаются. Выбранный пункт
проверяется один раз (резерв на покупателя), затем расчёты всех магазинов идут
параллельно через существующий класс оформления. Локальный отказ
`region_not_allowed` означает, что регион пункта вне области конкретного магазина.
Карта покупки не принимает tenantId, показывает объединение разрешённых регионов
магазинов для выбранной службы; при выборе каждый магазин проверяется отдельно.

Группа без службы ПВЗ получает `carrier_not_connected` и не создаёт заказа. Отказ
расчёта одной группы не блокирует доступные: покупатель подтверждает частичное
оформление, товары отказавшей группы возвращаются в корзину штатным механизмом.
Нет ни одной доступной группы — оформление не начинается. Изменение только расхода
продавца не меняет сумму покупателя и не требует повторного подтверждения цены.

Запись новых расчётов и переход в creating_orders — один CAS по прежним
статусу и версии. Два конкурентных запуска не могут зафиксировать разные
снимки. После этого тело каждой команды неизменно, включая deliveryPrice,
контакт и ПВЗ: при возобновлении новые настройки в него не попадают.
`buyerId` не входит в тело команды магазину и ключ её идемпотентности.
Перед каждым внешним вызовом группа захватывается CAS с арендой 1 минута;
повтор по истечении аренды использует прежние ключ и тело.

### Команда магазину

`POST /orders` — только доверенный канал из общего раздела.

```json
{
  "externalCheckoutId": "00000000-0000-4000-8000-000000000001:t1",
  "groupId": "t1",
  "paymentDueAt": "2026-10-24T11:00:00Z",
  "items": [{"productId":"p1","quantity":2,"price":199000}],
  "carrier": "cdek",
  "pickupPointCode": "P1",
  "contact": {"phone":"79251234567","name":"Покупатель"},
  "deliveryPrice": 0
}
```

Поля запроса: externalCheckoutId, groupId, paymentDueAt, items, carrier, pickupPointCode, contact, deliveryPrice;
опциональное — promoCode (строка). Каждый элемент items содержит productId, quantity,
price и опциональный массив discounts с promotionId и amount; адаптер всегда передаёт discounts,
в том числе пустой массив. contact содержит только phone и name.

Идентичность заказа: `(tenantId, externalCheckoutId, groupId)`.
Маркетплейс сохраняет externalCheckoutId=`<checkoutId>:<tenantId>`, groupId=tenantId.
Сервер атомарно обеспечивает уникальность, включая конкурентные запросы:
повтор возвращает **тот же** заказ и окно оплаты, даже если заказ
оплачен, отменён или истёк. Проверка ключа идёт **раньше** повторной
проверки цены/остатка; новый резерв и платёж при повторе не создаются.
Исключение — ключ, закрытый cancel-by-checkout: любой поздний POST /orders
получает ORDER_CHECKOUT_CANCELLED вместо прежнего заказа.
Иное тело по существующему ключу — IDEMPOTENCY_CONFLICT (paymentDueAt в сравнении не участвует). Срок хранения
ключа — весь срок хранения заказа, не TTL окна оплаты.
Окончательные отказы PRICE_CHANGED, DELIVERY_UNAVAILABLE, DELIVERY_CHANGED
и OUT_OF_STOCK также фиксируются по ключу атомарно:
повтор возвращает тот же отказ, даже если цена или условия доставки снова поменялись.
Это исключает гонку двух попыток, когда одна уже вернула группу в корзину,
а другая создала заказ. Новое согласие с ценой — новый checkout и новый ключ.
Временная недоступность не фиксируется как окончательный результат.

quantity — положительное целое; price — неизменная цена маркетплейса
при оформлении. Сервер сравнивает с текущей ценой по §1. Расхождение:

```json
{"ok":false,"message":"Цены изменились","status":409,"code":"PRICE_CHANGED","items":[{"productId":"p1","price":209000}],"data":null}
```

Заказ/резерв/платёж при таком отказе не создаются. Маркетплейс сохраняет
актуальные цены рядом со снимком и возвращает группу в корзину для нового
подтверждения; исходный снимок и цены уже созданных групп не меняются.
Нельзя автоматически списывать новую сумму или создавать изменённый заказ
с прежним ключом. Остальные магазины продолжают независимо.

contact — гостевой покупатель магазина: телефон и имя; общий пользовательский аккаунт
платформы не создаётся. `deliveryPrice` для площадки строго 0. Сервер перед созданием
повторно рассчитывает доступность и реальный тариф по ПВЗ. Недоступность — 409
DELIVERY_UNAVAILABLE; ненулевой `deliveryPrice` — 409 DELIVERY_CHANGED. Заказ, резерв
и платёж при отказе не создаются. `delivery.cost=0`, `delivery.tariffCost` — фактический
расход продавца в рублях. ПВЗ, отправитель, перевозчик и тариф сохраняются в штатном
документе доставки; изменение расхода не добавляет его к оплате или возврату.
После первого успешного результата или окончательного отказа повтор
возвращает этот результат **до** новой проверки тарифа. Total обязан совпасть с
`sum(quantity × price − sum(discounts.amount)) + deliveryPrice`. У заказа source=marketplace.
`paymentDueAt` обязателен, RFC 3339. Площадка сохраняет один срок всем группам покупки:
момент записи намерения + 10 минут (константа домена PaymentWindow), включая повторы создания.
Для нового заказа сервер проверяет `now < paymentDueAt ≤ now + 10 минут + 1 минута`;
иначе 400 `MARKETPLACE_PAYMENT_DUE_INVALID`. Минута — допуск расхождения часов.
Идемпотентный повтор возвращает сохранённый заказ и прежний срок, новое значение не проверяет.
`expiresAt` ответа — сохранённый paymentDueAt; иной срок нового заказа — нарушение договора.
Прямые заказы магазина также имеют срок 10 минут, константу платформы без настройки магазина.
Единая болванка подтверждает заказ через stub-payment.

Ответ (200):

```json
{"orderId":"o1","expiresAt":"2026-10-24T11:00:00Z","total":413000}
```

Поле paymentUrl удалено из ответа; expiresAt — RFC 3339.
После потери ответа повтор вправе вернуть уже истёкший expiresAt: это
по-прежнему тот же заказ, маркетплейс сразу сверяет его состояние.
Перенаправления внутреннего API на другой origin запрещены клиентом.

`GET /orders/{orderId}` — тот же доверенный канал, заказ только этого магазина.

```json
{"orderId":"o1","number":"22112026-0003","steps":[{"status":"paid","at":"2026-11-22T08:39:00.000Z"},{"status":"shipped","at":"2026-11-24T05:15:00.000Z"}],"status":"shipped","revision":7,"tracking":{"carrier":"carrier","number":"TRACK1","url":"https://example.test/TRACK1"}}
```

| status | Значение | Шаги магазина |
|---|---|---|
| awaiting_payment | ждёт оплаты | ожидает оплаты |
| paid | оплачен, магазин его собирает | новый, просмотрен, подтверждён, в работе |
| assembled | собран, ждёт передачи перевозчику | готов, доставка оформлена |
| shipped | у перевозчика; tracking — отслеживание, track маркетплейс не читает | передан в доставку, в пути |
| awaiting_pickup | ждёт покупателя в пункте выдачи | доставлен |
| delivered | получен | выполнен |
| returned | возврат магазину; деньги возвращает магазин | возвращён, отмена оплаченного |
| cancelled | неоплаченный отменён, reason — обязательная непустая строка причины магазина | отмена неоплаченного |

Служебные шаги магазина до сборки покупателю неразличимы и статус не меняют.
`revision` — номер перехода статуса заказа у магазина: растёт с каждой сменой статуса, в ответе
создания отсутствует. Площадка не применяет состояние с номером меньше сохранённого.

`number` — номер заказа магазина для покупателя (или null). `steps` — путь заказа до текущего статуса:
служебные шаги схлопнуты, `at` — первый приход в видимый статус по часам магазина, не больше восьми
шагов. Время шага площадка не выдумывает: состояние без `steps` прежнюю ленту не стирает.
Те же поля — в событии статуса и в пакетной сверке.

Магазин сам отменяет неоплаченный заказ и снимает резерв после своего окна.
Маркетплейс запрещает оплату при now ≥ действующего срока, но не выводит отмену из
часов: источником истины остаётся состояние магазина из события или ответа GET.
Неоплаченный заказ не опрашивается до действующего срока + 2 минуты (PaymentExpiryGrace домена площадки).
Если события нет, выполняется одна страховочная проверка GET. При awaiting_payment или отказе
следуют повторы. Успешный awaiting_payment обнуляет PollFailures; задержка равна времени после
действующего срока + PaymentExpiryGrace, ограниченному снизу 30 секундами и сверху 30 минутами (OrderSlowPoll).
Отказы увеличивают PollFailures: задержки 30, 60, 120, 240 секунд, после пятого отказа — 30 минут.
Неизвестный исход оплаты проверяется через 30 секунд после ClaimPayment (PaymentOutcomeDelay),
чтобы запрос оплаты успел завершиться; FinishPayment снимает проверку или переносит её на срок с запасом.
Оплаченный или терминальный итог снимает запланированную проверку. Отказ отмены исполняемого заказа сверяется по прежнему правилу.
Допустимы пропуски промежуточных статусов; регресс из paid в awaiting_payment запрещён. Назад заказ идёт
только из assembled в paid: до передачи перевозчику магазин вправе вернуть его на сборку.
Отмена оплаченного заказа отражается магазином как returned с
`reason: "cancelled_before_shipment"`: товар не уезжал, покупателю показывается отмена с возвратом денег.

### Действия покупателя

`POST /orders/{orderId}/cancel` `{}` — отмена оплаченного заказа покупателем до передачи перевозчику.
Ответ — состояние заказа (`returned`, `reason: "cancelled_before_shipment"`), повтор — тот же ответ.
Иначе `409 ORDER_NOT_CANCELLABLE`. Деньги возвращает магазин.

`POST /orders/{orderId}/return-request` `{"reason":"not_fit|defective|not_as_described|changed_mind"}` —
одна заявка на полученный заказ; повтор открытой — тот же ответ, иначе `409 ORDER_RETURN_UNAVAILABLE`.
Состояние, событие и сверка несут `returnRequest`:

```json
{"status":"rejected","reason":"defective","requestedAt":"2026-11-28T07:14:00.000Z","resolvedAt":"2026-11-29T09:00:00.000Z","comment":"Следов брака нет"}
```

Заявка статус не меняет, но увеличивает `revision` (заявка и отказ — по единице). Согласие магазина —
статус `returned`; отказ всегда с объяснением. Обе команды площадка не ставит в очередь: они
идемпотентны, потерянный ответ догоняет событие или повтор покупателя. Команды и чтение состояния
заказа работают и у магазина, снявшего настройки маркетплейса: его проданные заказы остаются.
Покупателю отдаются только два отказа договора, прочий ответ сервера — `checkout.order_action_unavailable`;
не больше 10 команд покупателя в минуту.

### Событие статуса заказа

Изменения неоплаченного и оплаченного заказа площадка узнаёт событием магазина. Сервер кладёт запись
в outbox заказа тем же обновлением, что и смену статуса, публикует сразу и переиздаёт свипером.

| Что | Значение |
|---|---|
| топик | `orders.order.marketplace-status-changed`, топиком владеет сервер |
| ключ | `["tenantId","orderId"]`; заголовок `x-tenant`, если есть, обязан совпасть |
| когда | заказ площадки сменил статус из таблицы выше или получил накладную (статус прежний, появилось отслеживание); прочие служебные шаги событий не дают |
| тело | состояние заказа на момент публикации, не разница с прежним |

```json
{"version":1,"tenantId":"t1","externalCheckoutId":"<checkoutId>:t1","orderId":"o1","number":"22112026-0003",
 "steps":[{"status":"paid","at":"2026-11-22T08:39:00.000Z"},{"status":"awaiting_pickup","at":"2026-11-25T11:05:00.000Z"}],
 "status":"awaiting_pickup","revision":9,
 "tracking":{"carrier":"carrier","number":"TRACK1","url":"https://example.test/TRACK1"}}
```

`reason` присутствует у `cancelled` и у `returned` после отмены оплаченного заказа. Покупку площадка
находит по `externalCheckoutId` (первичный ключ), заказ сверяет с `orderId` группы. Событие заказа,
которого у группы нет, пропускается с записью в журнал; событие против порядка исполнения,
неизвестная версия, статус вне словаря или чужой магазин в ключе — в отравленные.
Повтор доставки отсекает `processed_events`, опоздавшее состояние — `revision`.
Статус, который площадка поставила сама без номера перехода (оплата, отказ отмены), более раннее
событие не откатывает и в отравленные не отправляет. Событие `cancelled` меняет только группу,
ждущую оплату: отмену по команде площадки ведёт её сценарий. Отслеживание гарантировано с `shipped`.
Читает топик отдельная группа `<KAFKA_GROUP_ID>-orders`: волна проекций каталога статусы не задерживает.

### Сверка статусов пачкой

`POST /orders/statuses` — страховка событий: раз в сутки площадка сверяет исполняемые заказы
(`paid`, `assembled`, `shipped`, `awaiting_pickup`), пока с последней смены статуса не прошло 60 дней
(константа `ReconcileInFlightFor`). Полученный заказ не сверяется (решение владельца 2026-11-22):
возврат оформляется явным действием и приходит событием магазина.
Заказ, застрявший дольше, из сверки выходит: набор растёт с числом живых заказов, а не с возрастом площадки.

```json
{"orderIds":["o1","o2","o3"]}
```

```json
{"items":[{"orderId":"o1","number":"22112026-0003","steps":[{"status":"assembled","at":"2026-11-22T08:40:00.000Z"}],"status":"assembled","revision":4},{"orderId":"o2","status":"returned","revision":11}]}
```

В запросе от 1 до 200 идентификаторов заказов одного магазина; сервер отвечает одним чтением базы,
без треков. Заказа, которого магазин не знает, в ответе нет. Запросы одного магазина идут по очереди,
после первого отказа магазин в этом проходе пропускается. Расхождение площадка применяет прямо из
ответа; `GET /orders/{orderId}` нужен только новому статусу с отслеживанием или причиной
(`shipped`, `awaiting_pickup`, `returned`). Исходы считаются (`matched`, `mismatched`, `missing`,
`unresolved` — расхождение не применилось, например площадка считает заказ оплаченным, а магазин —
отменённым; это сигнал оператору): `marketplace_order_reconcile_orders_total{outcome}` и
`marketplace_checkout_events_total{event="order_status_mismatch"}`. Ненулевой рост означает
пропущенные события. Недоступный магазин — `marketplace_order_reconcile_failures_total{tenant}`,
остальные магазины сверяются без него.

### Локальные статусы, возврат в корзину и повторы

DELIVERY_UNAVAILABLE и DELIVERY_CHANGED при создании — локальный статус
группы `delivery_unavailable`, исходный код сохраняется в lastErrorCode,
причина сервера — в reason (при её отсутствии — код). Это окончательный
отказ: автоматического повтора нет, товары возвращаются в корзину,
покупателю предлагается другой ПВЗ и новая покупка. Этот статус не входит
в словарь GET магазина, поскольку заказа у него не было.

При переполнении корзины возвращается помещающееся количество. В группе
сохраняются `returnFailed=true`, `returnReason` и `returnRemaining`
(offerId/quantity). Повтор через минуту возвращает только остаток;
пока он не помещается, опрос и оплата других магазинов продолжаются.
Успешный полный возврат сбрасывает returnFailed; количества не теряются.

Создание выполняет только outbox по HTTP. Намерение, списание корзины и задачи групп
фиксируются одной транзакцией. Повтор запроса покупателя не создаёт задач.
При неизвестном коде отказа адаптер пишет журнал с tenantId, кодом и HTTP-статусом;
группа seller_unreachable. Код с неожиданным HTTP-статусом считается неизвестным протоколу,
даже если его имя знакомо. Повтор outbox безопасен по ExternalCheckoutID.
Окончательные отказы не превращаются во временную недоступность.
Срок 15 секунд отсчитывается от записи намерения.
После него временный сбой возвращает покупку в draft с прежним составом и суммой;
товары не возвращаются, созданные заказы сохраняются, автоматическое создание приостанавливается
до повторного confirm/orders. Окончательный отказ требует нового подтверждения оставшегося состава.
Поздний ответ сохраняет orderId для сверки, но не открывает оплату этой группы.
Окончательные отказы сохраняют причину и возвращают товары сразу.

Периодический опрос неоплаченного заказа убран. GET страхует потерянное событие после
действующего срока + 2 минуты и неизвестный исход оплаты; правило задержки описано выше.
Сетевой сбой, неизвестный статус и недопустимый переход увеличивают pollFailures.
После пяти последовательных отказов интервал — 30 минут, группа получает seller_unreachable.
Последний подтверждённый статус сохраняется отдельно для запрета регрессов.
Любой успешный ответ восстанавливает статус и обнуляет счётчик отказов. Для awaiting_payment
задержка растёт по времени просрочки независимо от счётчика; оплаченный или терминальный итог снимает проверку.
Отказ отмены abandoned-группы проверяется сразу, затем раз в 10 минут при исполняемом статусе.
Для awaiting_payment отказ отмены контрактом не предусмотрен: магазин отменяет неоплаченный заказ.
При ошибках — 30, 60, 120, 240, 480 секунд,
далее по 480 секунд (счётчик ограничен пятью); delivered, returned или cancelled завершают сверку.
CAS-захват опроса ставит NextPollAt **до** внешнего вызова: параллельные
задачи сверки не обходят срок, включая сбои и перезапуски.
GET покупки читает только локальный снимок, без HTTP магазина.

## Решения по вопросам к серверу

Решение владельца **2026-11-07**, заменяет прежний план недели 3:

1. Вариант В: единый платёж за покупку. Сейчас болванка без движения денег;
   боевой вариант — сплит ЮKassa после согласования. Статусы и возвраты — по группам.
2. Уточнение 17.11.2026: доставка в цене продавца, покупателю всегда 0; весь тариф
   перевозчика — расход продавца. Платформа не субсидирует доставку.
3. Обязательны подключённые перевозчики и регионы доставки.
   Отдельная группа и брошенная корзина не меняют условия других групп.
4. PRICE_CHANGED — явный отказ без заказа; идемпотентность переживает
   потерю ответа и перезапуск. Оплаченные группы не ждут остальных.
5. Возврат с кассы — экран «Проверяем оплату», query-параметры не являются
   подтверждением. Пересмотрено владельцем 2026-11-22: статусы приходят событиями; неоплаченный
   заказ проверяется после срока с запасом, неизвестная оплата — через 30 секунд после отправки. Исполняемые заказы
   страхует суточная сверка пачкой; отказ отмены сохраняет прежнюю проверку (разделы выше).
6. Словарь причин quote и MARKETPLACE_DISABLED сохранены. PR-M1 — после PR-08d.

## Карточка маркетплейса

Обе темы проекции товара используют один формат версии 1, ключ `["tenantId","productId"]`
и одинаковые заголовки. `catalog.product.projected` несёт точечные снимки,
`catalog.product.projected.bulk` — массовые снимки и восстановление. В операции `upsert` сервер передаёт
отдельный блок `product.marketplace`. Категории и атрибуты магазина остаются
для его витрины; для площадки используются только её коды и значения.
Схема строгая, без ИИ, с точным совпадением значений словаря.

```json
{
  "version": 1,
  "tenantId": "t1",
  "productId": "p1",
  "revision": 12,
  "operation": "upsert",
  "product": {
    "id": "p1",
    "name": "Товар",
    "image": "products/p1/main.jpg",
    "assets": ["products/p1/main.jpg", "products/p1/detail.jpg"],
    "price": 199.99,
    "priceProfiles": [{"key":"marketplace:default","price":249.99,"promoPrice":null,"effectivePrice":249.99}],
    "availableQuantity": 3,
    "marketplace": {
      "categoryId": "c1",
      "attributes": {
        "a1": "v1",
        "a2": 12.5,
        "a3": false
      },
      "published": true
    }
  }
}
```

Галерея снимка v1 — `product.assets`: ключи бакета без хоста и `/images/`,
сегменты не кодированы (кодирует витрина), порядок магазина; `image` обычно равен
первому элементу. При разборе остаются строки после `TrimSpace`, без пустых,
`data:`, `blob:`, управляющих символов Unicode (Cc, `unicode.IsControl`), повторов
и значений длиннее 512 байт; максимум 20.
Недопустимые и нестроковые элементы пропускаются, сообщение принимается.
Отсутствие поля и null означают пустую галерею; если после очистки она пуста, используется допустимый `image`.

`c1`, `a1`–`a3`, `v1` в примере — условные идентификаторы из загруженной
оператором схемы. Ключ Kafka по-прежнему `["t1","p1"]`; время публикации —
в метаданных события. Цены остаются рублями в событии и разбираются через
`money.ParseRubles`; числовые атрибуты не являются денежными суммами.

Форма блока:

| Поле | Смысл |
|---|---|
| `categoryId` | id одного узла дерева категорий площадки |
| `attributes` | объект код → скалярное JSON-значение; enum/string — строка, number — число, boolean — true/false |
| `published` | явное желание магазина публиковать товар; отсутствие равно false |

Нет преобразования строк в числа/boolean, синонимов, массивов, объектов,
`null` или наследования схем родителей. Обязательные поля определяются
схемой выбранного узла. Отсутствующий блок или `published=false` скрывает
предложение. Удаление товара по-прежнему передаётся без `product`.

Сервер магазина получает согласованный набор таксономии через:

- `GET /api/v1/taxonomy/version` — `{version}`, 0 до первой поставки.
- `GET /api/v1/taxonomy/categories` — `{version, categories}`: дерево с
  `id`, `name`, `title?`, `slug`. Лист содержит `schema`, ветка содержит
  `children` и `priorityFilters?`. Каждый приоритет содержит `code` и boolean `primary`.
  Порядок списка значим. Отсутствие списка означает пустой набор характеристик.
  Полных определений атрибутов в дереве нет. `name` — короткое имя, `title` — самостоятельное
  полное имя (без него используется `name`). `slug` — уникальный сохранённый
  адрес до 128 символов, `^[a-z0-9]+(-[a-z0-9]+)*$`; витрина строит
  `/category/<slug>`, поиск фильтруется по `id`.
- `GET /api/v1/taxonomy/attributes` — `{version, attributes}`: глобальные
  определения `code`, `name`, `type`, `unit?`, `dictionary?`, `facet`,
  `values?`, `valuesMeta?`, `searchTermsByValue?`. Здесь `facet: true` означает,
  что код фильтруем хотя бы в одном листе площадки. В поставке 17, закреплённой
  на `ca15867`, таких кодов 809. Enum ссылается на закрытый словарь с
  каноническими confirmed-значениями, сохранёнными в `values` при публикации версии.
  String может ссылаться на открытый словарь, но остаётся свободной строкой.
  `searchTermsByValue` — словарь каноническое значение enum или строка true/false
  → до восьми поисковых выражений по 128 символов Unicode. Пустые списки допустимы.
  Выражения содержат только одиночные обычные пробелы, без пробелов по краям,
  управляющих символов и дублей без учёта регистра и ё/е.
- `GET /api/v1/taxonomy/schemas` — `{version, schemas}`, словарь ключ →
  `{attributes: [коды], optional?: [коды], filters: [{code, primary}]}`.
  Порядок `attributes` значим. Обязательны поля вне `optional`.
  В `filters` сначала идут основные характеристики с `primary: true`,
  затем дополнительные с `primary: false`. Пустая панель листа даёт `[]`.
- `GET /api/v1/taxonomy/categories/{id}/schema` — узел с `filters` и собранными
  `attributes` в порядке схемы. У каждого атрибута `required = !optional`,
  `facet` показывает наличие кода в `filters` именно этой схемы.
  У ветки ответ содержит `priorityFilters?`, `attributes: []` и `filters: []`.

Например, у `electronics.smartphones` начало `filters` содержит
`{"code":"storage_capacity","primary":true}`, а блок дополнительных
начинается с `{"code":"esim_support","primary":false}`. У ветки `electronics`
все `priorityFilters` основные. Коды идут в порядке
`@price`, `brand`, `@inStock`, `@seller`, `@category`.
Явная раскладка ветки включает общие для всех её листьев характеристики и
может содержать встроенные коды. Для ветки без раскладки используются общие
характеристики в порядке кодов, первые шесть основные. Исходные
`facetOverrides?` и `facetLayout?` в ответах схем и `facetLayout?` в дереве
служат для редактирования. Сервер магазина использует вычисленные `filters` или
`priorityFilters` выбранной категории.

`proshop-search` фиксирует `attributes[].facet = true` при сборке поколения
индекса площадки. `facetValues.<code>` разрешён для каждого такого кода,
`facetNumbers.<code>` — для числовых. Служебные ключи и подсказки учитываются
по своему контракту. Площадка передаёт за один поисковый запрос упорядоченные
`facetFields: [{code, name, type, unit}]` выбранной панели, до 32 характеристик.
Встроенные коды передаются селектором `facets` как `price`, `inStock`, `tenant`,
`category`. Селектор клиента может сузить панель.

Клиенты витрины читают уже упорядоченные `facets` из
`GET /api/v1/catalog/offers`. Каждый элемент имеет обязательное boolean
`primary`. Характеристики имеют код `attr.<code>`. Дополнительные фильтры
идут под «Показать ещё». Клиент может получить панель без пустых агрегаций
характеристик. Порядок и группа остальных сохраняются. В листе до шести основных
характеристик плюс до четырёх встроенных фильтров по контексту.

Сервер сохраняет `searchTermsByValue` в согласованном снимке таксономии. При
построении поисковой проекции магазина выражения берутся только из доверенной
схемы выбранной категории и фактического корректного enum/boolean. Производное
`searchTerms: string[]` передаётся отдельно у каждого атрибута проекции; входные
выражения карточки не являются источником. Исходный блок `marketplace.attributes`
по-прежнему содержит только скаляры. Backend площадки вычисляет выражения
независимо по своей таксономии при проверке публикации.

Все ответы чтения имеют `ETag: "taxonomy-<version>"`, `X-Taxonomy-Version`,
`Cache-Control: public, max-age=0, must-revalidate`; совпадающий
`If-None-Match` даёт 304, поддерживаются слабые ETag, списки и *.
Версия одна на весь набор. Сервер проверяет её и скачивает части при изменении.
Если версии ответов частей различаются из-за публикации между запросами,
нужно повторить обновление; смешивать части разных версий нельзя.
Переход сервера магазина на этот контракт — отдельная задача.

Оператор: GET `/api/v1/operator/taxonomy` возвращает весь набор в JSON,
включая `facetKeys` и `rootFilters` (панель выдачи без категории).
GET `/api/v1/operator/taxonomy/{part}` — YAML parts categories, attributes, schemas.
PUT той же части принимает один YAML до 2 МиБ с обязательным
`If-Match: "taxonomy-<version>"`, публикует версию +1 и перепроверяет карточки.
Несовпадение версии — 409; неверный/отсутствующий заголовок или YAML — 400.
Скачанный YAML можно загрузить без преобразования. Его `facet` задаёт исходное
правило характеристики. Источники панели задаются через `facetOverrides`
и `facetLayout`. Вычисленные списки, `values` и `required` в YAML запрещены. Старый PUT целого набора удалён.
Доступ оператора остаётся прежним. Изменения словаря влияют только на
следующую публикацию, автоматической перепубликации нет.

Маркетплейс повторно проверяет карточку при приёме. Ошибка карточки не
теряет снимок товара и не паркует корректный конверт события: inbox,
проекция и outbox сохраняются одной транзакцией. В проекции остаются
исходный блок, версия проверки, канонические атрибуты и причины отказа.
Ошибочная карточка не имеет индексируемых атрибутов и не видна ни в выдаче,
ни по прямой ссылке. Некорректный JSON или сломанный конверт события
по-прежнему паркуются по общим правилам Kafka.

| Ключ причины | Значение |
|---|---|
| `taxonomy.card_missing` | блок отсутствует |
| `taxonomy.category_unknown` | неизвестная категория, в том числе до первой загрузки схем |
| `taxonomy.attribute_unknown` | код отсутствует в схеме выбранной категории |
| `taxonomy.type` | неверный тип, null, пустая строка или непредставимое в double число |
| `taxonomy.required` | пропущено обязательное поле |
| `taxonomy.enum_value` | значение не входит в словарь |
| `taxonomy.unpublished` | магазин снял публикацию |

Причины и проверенные атрибуты доступны оператору через
`GET /api/v1/operator/catalog/offers/{offerId}/publication` под
`OPERATOR_TOKEN`. Смена версии таксономии перепроверяет все сохранённые
проекции, включая магазины без участия; индекс догоняет через outbox.
Повтор старого события не отменяет перепроверку новой схемой. Исправленный
блок магазин отправляет новой ревизией проекции. Причины в админку магазина
доставляет событие `marketplace.offer.status` (раздел «Статус предложения и
участника»); операторский токен магазинам не передаётся.

## Статус предложения и участника

Согласовано владельцем 2026-11-05 (`proshop-server/docs/marketplace-mvp.md`
§6d), реализация — этап M3. Маркетплейс сообщает магазину, виден ли товар на
площадке и почему, двумя событиями Kafka. Топики заводит сервер установки;
событие ставится в outbox той же транзакцией, что и изменение. Сервер читает
статусы для админки запросом к площадке, не храня их копию.

`GET /api/v1/internal/tenants/{tenantId}/status?ids=a,b` принимает
`Authorization: Bearer <SERVER_API_TOKEN>`, как продвижение и участие.
Без настройки токена — 404, неверный или отсутствующий токен — 401.
`ids` необязателен: без него читается только участник (`items: []`);
с ним читаются только товары (`participant: null`), от 1 до 200
непустых id через запятую, с удалением пробелов и дублей, неверная пачка — 400.
Ответ `{items: OfferEvent[], participant: ParticipantEvent|null}` использует
поля событий ниже и ту же функцию расчёта. Неизвестные и удалённые товары
пропускаются; отсутствующий участник — null. Решения товаров читаются одной
пачкой, причины отклонений — одной пачкой дел, без запроса на каждый товар.
`at` — время формирования снимка.
Запрос читает существующие таблицы PostgreSQL, не сохраняет состояние и
не публикует события. Сервер магазина удаляет служебные `schemaVersion` и
`tenantId` и сохраняет прежний HTTP-договор `/marketplace/status/*`.
Одиночное чтение идёт этим же запросом с одним id. Недоступность площадки —
503 `MARKETPLACE_STATUS_UNAVAILABLE`, без кэша и запасного значения.
Публикация событий ниже сохраняется.

| Событие | Топик без префикса | Ключ | Когда |
|---|---|---|---|
| статус предложения | `marketplace.offer.status` (`KAFKA_TOPIC_OFFER_STATUS`) | `["tenantId","productId"]`, заголовок `x-tenant` | изменились `visible`, `status`, причины или решение оператора |
| статус участника | `marketplace.participant.status` (`KAFKA_TOPIC_PARTICIPANT_STATUS`) | `tenantId` | включение, выключение, смена уровня доверия, в том числе автоматическая |

Время — RFC 3339 с зоной. Ключ сохраняет порядок событий одного товара и
одного участника.

### `marketplace.offer.status`

```json
{
  "schemaVersion": 1,
  "tenantId": "t1",
  "productId": "p1",
  "revision": 7,
  "visible": false,
  "status": "hidden",
  "reasons": [
    {"source": "moderation", "key": "moderation.stop_phrase", "message": "Стоп-фраза «фраза» найдена в описании"},
    {"source": "taxonomy", "key": "taxonomy.required", "message": "Нет обязательного атрибута «a1»"}
  ],
  "decision": {
    "action": "reject",
    "reason": {"code": "wrong_category", "message": "Неверная категория"},
    "note": "Уберите из описания фразу «фраза» и заполните атрибут «a1».",
    "at": "2026-11-05T12:40:00+03:00"
  },
  "at": "2026-11-05T12:40:01+03:00"
}
```

| Поле | Смысл |
|---|---|
| `revision` | ревизия проекции товара, к которой относится статус |
| `visible` | итог карточки, публикации и вердикта модерации; выключенный участник скрывает все предложения, об этом сообщает `marketplace.participant.status` |
| `status` | `published` — виден; `pending` — скрыт до решения оператора; `hidden` — скрыт, причины в `reasons` |
| `reasons` | причины скрытия или ожидания, у `published` — пустой массив; `source`: `taxonomy` — карточка не прошла схему (ключи — раздел «Карточка маркетплейса»), `moderation` — вердикт модерации |
| `decision` | решение оператора, которым установлен текущий статус; `null`, если статус поставили правила |
| `decision.action` | `allow` или `reject` |
| `decision.reason` | причина из словаря оператора `{code, message}` или `null`; код стабилен, текст — на момент решения |
| `decision.note` | заметка оператора, 1–2000 символов; её видит магазин |

При техническом переносе допуска на идентичный новый снимок внешняя `revision`
содержит актуальную ревизию проекции, а `decision.at` сохраняет исходное время
решения оператора. Перенос не создаёт нового человеческого решения; его условия
описаны в `moderation.md`, раздел «Повторная доставка проверенного содержимого».

| Ключ модерации | Значение и статус |
|---|---|
| `moderation.category_forbidden` | категория площадки запрещена политикой узла; `hidden`, в очередь не идёт |
| `moderation.category_manual` | категория требует ручной проверки; `pending` |
| `moderation.stop_phrase` | в названии или описании найдена стоп-фраза, она в `message`; `pending` |
| `moderation.image_missing` | у карточки нет изображения; `hidden`, новая ревизия с картинкой проходит сама |
| `moderation.probation` | участник на испытании; `pending` |
| `moderation.manual_review` | оператор открыл дело вручную, «На ручной проверке»; `pending` |
| `moderation.rejected_revision` | предыдущая ревизия отклонена оператором, новая ждёт человека; `pending` |
| `moderation.rejected_by_operator` | отказ оператора, в `message` — причина из словаря или заметка; `hidden` |
| `moderation.not_evaluated` | вердикта ещё нет, до первой оценки; `hidden` |

Отказ оператора даёт `hidden` с причинами дела и `decision.action: "reject"`;
он прилипает к предложению, и следующая ревизия снова приходит со статусом
`pending`. Одобрение действует на ревизию и не снимает причины таксономии:
пока магазин их не исправит, статус остаётся `hidden`.

### `marketplace.participant.status`

```json
{
  "schemaVersion": 1,
  "tenantId": "t2",
  "stage": "connected",
  "enabled": true,
  "trust": "probation",
  "reason": {"code": "wrong_category", "message": "Неверная категория"},
  "note": "Повторные ошибки в категориях, возвращаем на ручную проверку",
  "by": "operator",
  "at": "2026-10-30T09:30:00+03:00"
}
```

| Поле | Смысл |
|---|---|
| `stage` | `candidate`, `connected`, `returned`, `disconnected` |
| `enabled` | производное: true только для `connected` |
| `trust` | `probation` — каждое предложение ждёт одобрения оператора; `trusted` — проходит по правилам; покупатель уровень не видит |
| `reason` | причина из того же словаря оператора `{code, message}` или `null` |
| `note` | заметка оператора; при `by: "system"` — служебный текст с числом одобренных |
| `by` | `operator` — решение оператора; `system` — автоматическое повышение после `MODERATION_PROBATION_OFFERS` одобренных |

Возврат оператором отправляет `stage=returned`, `enabled=false`, причину, заметку
и `by=operator`. Отключение подключённого — `disconnected`.

Ручное понижение до `probation` обнуляет счётчик одобренных, автоматическое
повышение снова наступает после `MODERATION_PROBATION_OFFERS` одобрений.

## Реестр справочных сущностей

Владелец реестра и его пополнения — proshop-marketplace. proshop-server
и proshop-search потребляют снимки площадки, а не ведут собственный реестр.
Discovery: `GET /api/v1/internal/reference`; снимок:
`GET /api/v1/internal/reference/{code}/snapshot?since=`; запись:
`GET /api/v1/internal/reference/{code}/entries/{id}` (200/404).
Все три маршрута принимают `Authorization: Bearer <REFERENCE_READ_TOKEN>`.
Поля и семантика дельт описаны в [reference.md](reference.md).

### Имя кандидата из реестра магазинов

События `platform.tenant.created`, `platform.tenant.updated`,
`platform.tenant.suspended`, `platform.tenant.resumed`, `platform.tenant.deleted`
содержат `tenantId`, `slug`, `status`, `plan`, `hosts`, `at`; поле `name` сервер
не отправляет (формирование — `modules/platform/helpers/events.ts`,
`tenantEventMessageOf`). Поэтому имя автоматически созданного кандидата — slug.
Если в расширенном снимке поступит `name`, площадка использует его только при
допустимом имени; пустое или недопустимое имя заменяется slug без отказа события.

## Карточка магазина (06.11.2026)

Сверка `GET /api/v1/internal/marketplace/tenants/{tenantId}/settings/marketplace`
дополнительно требует `profile` и `card`, сохраняет типизированный `returns: {days: int, shipping: string, how: string} | null`:

```json
{
  "profile": {
    "name": "Магазин",
    "logo": null
  },
  "card": {"ready": false, "missing": ["requisites", "contacts", "terms"]},
  "returns": {"days": 14, "shipping": "Условия возврата", "how": "Инструкция"}
}
```

Кандидат без настроек маркетплейса получает 200 с `profile` и `card`;
`delivery`, `returns` равны null. Это «не настроено»,
а не невалидный ответ; `DeliveryValid=false`. Чеклист и его порядок считает только сервер.
Четыре пункта: `identity`, `requisites`, `contacts`, `terms`.
Допустимое `profile.name`
становится именем участника; недопустимое сохраняет прежнее имя, остальные поля применяются.
Оператор имя участника не меняет: его задаёт магазин в настройках.
При ошибке сверки или 403 последний профиль, возврат и скрытия сохраняются. Любое изменение карточки увеличивает версию участника;
из изменений карточки только имя требует `catalog.tenant.sync`.

Сервер вызывает `POST /api/v1/internal/tenants/{tenantId}/settings/sync` без тела,
с `Authorization: Bearer <SERVER_API_TOKEN>` маркетплейса (на сервере значение
`MARKETPLACE_SERVER_TOKEN`). Ответ 202 означает постановку `participant.settings.sync`
в транзакционный outbox. Повторы склеиваются по магазину. Неизвестный участник — 404.

`GET /api/v1/internal/tenants/{tenantId}/store-card` с тем же токеном возвращает
`offers`, `fromPrice` в копейках (null при отсутствии предложений), `categories`
(`id`, `name`, `count`), `uncategorized`, `hidden` (`key`, `reason`, `at`), `rating`, `badge`, `rank`.
Последние три поля всегда null. Ручка доступна только при `page_public=true`,
иначе возвращает 404 (в том числе до первого пересчёта). Категории группируются по корневому узлу текущей
таксономии; порядок — число убыв., имя, id. Цена — минимальная действующая цена
публичного профиля `marketplace:default`. Если видимых предложений нет, статистика
использует отмеченные к публикации предложения, прошедшие структурную проверку.
`uncategorized` считает отмеченные товары без известной категории, независимо от допуска.
`StoreSummary.products` и публичный `ShopCard.products` содержат до трёх автоматически
выбранных публичных товаров. Каждый элемент: `productId`, `offerId`, `name`, `image`
(строка либо `null`), без цены. `ShopHeader` не содержит списка товаров.
Выбор выполняется только среди `ComposeOffer.Visible`: скрытые, удалённые,
отклонённые и товары другого магазина не попадают в карточку.
Порядок: `salesCount` по убыванию, наличие изображения, время снимка, ревизия,
затем стабильный `productId`. Ручных закреплений и выключателя подбора нет.
Служебная статистика хранит копейки, публичный `fromPrice` — рубли.

Страница `GET /api/v1/shops/{slug}` требует видимости магазина
(`Enabled && tenant active && DeliveryValid`) и хотя бы одного видимого предложения:
это флаг `page_public`, независимый от готовности карточки.
«Топ магазинов» `GET /api/v1/shops` дополнительно требует готовую карточку (`public`). Список имеет оболочку
`{items,total,limit,offset}` (как соседние списки); limit по умолчанию 20, максимум 100.
`category` принимает любой узел таксономии, включая его потомков; при отборе `offers`
и порядок относятся к этому узлу. Без отбора выбирается крупнейший корневой узел.
При отсутствии категорий `category=null`, `moreCategories=0`. Условия для пустых
выборок и оболочка списка уточняют неописанные случаи исходного контракта.
Сводка хранится готовой в `store_cards` и `store_card_categories`; задача outbox
склеивается по магазину при индексации предложений, сверке, вердикте и постмодерации.
Таксономия читается один раз на пересчёт. Все три ручки карточки читают эту сводку;
список — один SQL с `ORDER BY offers DESC, name`, `LIMIT/OFFSET` и отбором по категории.
Кэш публичный: `public, max-age=0, must-revalidate`, `ETag` и `If-None-Match`,
как у публичной таксономии каталога.
Скрытый логотип заменяется null. Неготовая карточка исключает магазин
из списка, но `card.ready=false` не закрывает страницу, не отключает участие и товары.

Профиль содержит только `name` и `logo`. Логотип — из опубликованного оформления
Студии (`look.logo.onLight`, иначе `migrateLegacy`). Публикация логотипа запускает
сверку; правка черновика Студии — нет. Цвет и подборка не входят в настройки магазина.
Миграция 00061 удаляет их из снимков и публичных проекций, заменяет подборку
автоматической и ставит сверку/пересчёт. Down восстанавливает пустую JSONB-структуру
без прежних данных. Кэш использует пространство ключей v3.

Публичные списки `ShopCard` (`/shops`, включая подборку топов, и разрешённые карточки подписок)
хранятся в Redis до 20 минут. Обычные показатели продаж, рейтинга и ранги обновляются при следующем
запросе после TTL; фонового cron для кэша нет. Логотип, состав/данные доступных
товаров и публичная видимость меняют транзакционное поколение вместе с записью готовой проекции:
первый GET после её фиксации читает свежие данные, без ожидания TTL.
Поколение проверяется в PostgreSQL, поэтому восстановление Redis после сбоя не возвращает устаревшую видимость.
При отказе Redis используется PostgreSQL; операции кэша ограничены бюджетом 100ms. Ключи включают поколение и аргументы запроса;
одновременные заполнения одного ключа объединяются, поздний запрос не записывает данные в новое поколение.
Кэш содержит внутренние целые копейки; публичные рубли по-прежнему формирует HTTP DTO.
Персональные поля подписки и шапки магазина не кэшируются.

Подключение из любой стадии требует готовую карточку. У подключённого магазина
опустевшие контакты, реквизиты или возврат не выключают участие и товары.
Видимость остаётся `Enabled && tenant active && DeliveryValid`.
Серверные `items/check`, `delivery/quote`, `orders` требуют подключённую доставку,
но не возврат и остальные пункты карточки. Оператор получает исходные
`card: {logo, hidden[]}`; hide/show возвращают обновлённого участника.

Задачи пересчёта из индексатора склеиваются в окне `STORE_CARD_REFRESH_DELAY`
(по умолчанию 30s, положительная длительность, проверяется на старте).
При дедупликации сохраняется самое раннее время задачи, поэтому непрерывный поток не откладывает пересчёт.
Если видимых предложений нет, внутренняя сводка при любой стадии использует отмеченные
к публикации предложения, прошедшие структурную проверку; публичность это не включает.
До первого пересчёта существующий участник получает пустую внутреннюю сводку, публичная шапка — 404.

## Отзывы товара (R4.3)

`GET /api/v1/internal/marketplace/tenants/:id/products/:productId/reviews?limit&offset`
использует тот же служебный токен, что остальные внутренние методы. Только опубликованные отзывы:

```json
{"items":[{"author":"Имя","rating":5,"text":"Текст отзыва","createdAt":"2026-11-06T10:00:00Z"}],"total":1}
```

`author` — имя без фамилии, пустая строка допустима для удалённого или безымянного покупателя; `rating` — целое 1–5; `createdAt` — RFC3339.
`limit` — 1–100 (по умолчанию 20), `offset` ≥ 0, окно ≤ 10000.
Пустой результат — `items: []`, `total: 0`; `items: null` нормализуется в пустой массив.
404 отображается в `not_found`, остальные отказы — в `unavailable` с ключом `platform.reviews_unavailable`.
Маркетплейс проверяет видимость предложения перед проксированием; публичный HTTP-кэш — 30 секунд.
Порт сохраняет указанные коды отказов адаптера, но витринная обёртка возвращает последнюю успешную
страницу либо `{items:[],total:0}` с HTTP 200 при отказе сервера. Локальная проверка скрытого товара
по-прежнему возвращает 404. Бюджеты, кэш, предохранитель и метрики — в
[platform-dependency.md](platform-dependency.md).

Снимок товара дополнительно содержит `averageRating` (0–5, один десятичный знак) и
`ratingsCount` (неотрицательное целое). Они применяются только с новой ревизией снимка;
при отсутствии полей принимаются нули, публичный рейтинг при нулевом числе оценок — null.

### Продавец в корзине, оформлении и заказах покупателя

Каждая `CartLine` и `CheckoutGroup` содержит обязательное nullable-поле
`seller: {slug, name}` — актуальные слаг и имя участника, как в каталоге.
Для удалённого или неизвестного участника возвращается `seller: null`.
Это относится ко всем ответам корзины, создания/чтения/изменения оформления,
создания заказов и списка заказов покупателя, включая снимок при `DELIVERY_CHANGED`.
Продавцы всех строк и групп всего ответа (включая страницу заказов) читаются
одним пакетным запросом; отсутствие участника не ломает ответ.

## R5: промокод группы и отслеживание (R4 сервера)

`POST /api/v1/internal/marketplace/tenants/{tenantId}/items/check` принимает
`{items:[{productId,quantity}], promoCode?}`.
Поле `promoCode` передаётся только для непустого кода; без кода поле отсутствует.
Ответ: `{items, promoCode}`.
Строки `items`: `{productId,available,availableQuantity,price,discounts}`;
`discounts`: `[{promotionId,amount}]`. Деньги — целые копейки.
`promoCode`: `{code,valid,discount,message}` либо `null`; message при успехе — null.
Неверный код — обычный результат `valid:false` с обязательной причиной message;
valid:false с message:null нарушает контракт ответа. Технический сбой — ошибка.
Цена единицы остаётся после ITEM; итог строки — `price * quantity - sum(discounts.amount)`.
GET /api/v1/cart читает сохранённый снимок; явная проверка вызывает Verify параллельно по группам.
Проверка повторяется и при изменении корзины. Каждая группа, включая
группы без кода, получает цены и автоматические скидки из items/check.
Проверенный код с valid:false и причиной в message не переносится в покупку.
После Consume/Return код остаётся непроверенным: valid:false, discount:0, message:null.
Create проверяет такой код у сервера. Скидки входят в снимок покупки.
При возврате группы код, уже установленный в корзине, имеет приоритет над снимком покупки.
При отсутствии кода восстанавливается код покупки; при отказе кода —
valid:false с причиной, в остальных случаях — состояние «не проверен».

В `POST /tenants/{id}/orders` передаётся принятый `promoCode`.
`/delivery/quote` промокода не принимает.
В каждой позиции заказа передаются `discounts` (в том числе пустой массив) для сравнения
сервером внутри транзакции: изменение цены или скидок — `PRICE_CHANGED`.
Недействующий код при создании заказа — окончательный 409 `MARKETPLACE_PROMO_CODE_INVALID`
с телом `{ok,message,status,code,items,data:{promoCode}}`.
Причина для покупателя берётся из data.promoCode.message; без неё — сообщение ErrPromoInvalid.
Маркетплейс сохраняет в группе `checkout.promo_invalid`, возвращает её строки в корзину
и продолжает оформление остальных магазинов. Ответ 200 с `valid:false` не считается
отказом: проверяется сумма созданного заказа. После отказа кода на Create/Confirm корзина
перепроверяется; новая покупка создаётся без отвергнутого кода.

`GET /tenants/{id}/orders/{orderId}` возвращает `tracking:{carrier,number,url}|null`
с nullable `number`: у перевозчика может быть только ссылка.
Перевозчик должен быть непустым, ссылка — допустимой HTTP(S) ссылкой;
некорректное значение превращается в null. Фоновый опрос сохраняет tracking в снимок
группы покупки, отдельно от order_progress. Чтение покупки и списка покупок отдаёт этот
снимок без кэша и запросов сервера. В публичной группе покупки есть только tracking.

## Однократное удержание начатой оплаты

`POST /api/v1/internal/marketplace/tenants/{tenantId}/orders/{orderId}/payment-hold`,
доверенный канал, тело `{}`. Ответ 200 — состояние как GET заказа.

- Заказ ждёт оплаты, удержания нет и `now < paymentDueAt`: одной условной операцией
  сервер сохраняет `paymentHeldUntil = max(now + 5 минут, paymentDueAt)` и возвращает его в состоянии.
- Удержание уже есть: 200 с тем же временем, без продления, даже после его истечения.
- Заказ уже оплачен или исполняется: 200 его состоянием, без удержания.
- Срок прошёл и удержания нет: 409 `ORDER_PAYMENT_EXPIRED`.
- Заказ отменён: 409 `ORDER_NOT_AWAITING_PAYMENT`; заказа нет: 404 `ORDER_NOT_FOUND`.

Действующий срок — `paymentHeldUntil`, если установлено, иначе `paymentDueAt`.
Удержание никогда не сокращает исходный срок: на первой минуте сохраняет десятую,
на последней секунде даёт ещё 5 минут от команды.
До него сервер принимает `stub-payment` и не отменяет заказ; с достижением срока
отменяет обычным порядком с событием. Для прямых заказов правило «платёж в пути
не даёт отменить» сохраняется. Удержание входит в GET, событие и сверку пачкой,
когда установлено, и применяется площадкой по ревизии состояния магазина.

После проверки готовности `Pay` параллельно вызывает удержание готовых групп без
сохранённого удержания. Все успешные ответы сохраняются одной транзакцией покупки,
включая частичный отказ. Любой неподтверждённый ответ закрывает кассу с
`checkout.payment_unavailable`; `ORDER_PAYMENT_EXPIRED` — `checkout.payment_expired`.
Повтор вызывает только группы без сохранённого удержания. Новая операция ограждения
`payment_hold` относится к классу оформления. Страховочный GET — от действующего
срока + PaymentExpiryGrace; неизвестный исход уже отправленной оплаты сохраняет
прежнее отдельное правило PaymentOutcomeDelay.

## Единая оплата — служебная болванка

`POST /api/v1/internal/marketplace/tenants/{tenantId}/orders/{orderId}/stub-payment`
Авторизация: `x-internal-token`. Тело: `{ "amount": 413000 }`, целые копейки,
товары после скидок + доставка заказа. Ответ 200: `{ "status": "paid" }`.

Сервер проводит оплату тем же путём, что подтверждённый платёж: заказ, склад,
события и уведомления. Провайдер/метод `stub`, движения денег нет.
Повтор уже оплаченного этой болванкой заказа возвращает тот же ответ 200.
Несовпадение суммы — 409 `MARKETPLACE_STUB_PAYMENT_AMOUNT`; неподходящий статус —
409 `MARKETPLACE_STUB_PAYMENT_STATE`; заказа нет — 404.
После действующего срока оплаты — 409 `ORDER_PAYMENT_EXPIRED`; сервер отменяет заказ
обычным порядком с событием, площадка возвращает `checkout.payment_expired`.
Без `MARKETPLACE_PAYMENT_STUB=true` ручка отсутствует (404).

Ошибки — обычный конверт сервера `{ok:false,message,status,code,items:null}`.
Технический сбой — 503 `MARKETPLACE_TEMPORARY_FAILURE`; кодов `_FAILED` и `_DISABLED` нет.
Идемпотентность сохраняется для оплаченных болванкой заказов после отгрузки и доставки;
отменённый или возвращённый заказ — 409 STATE. Возврат болванки проводится локально,
без провайдера: резерв и сразу «проведён», без ожидания возврата и блокировки удаления заказа.

Marketplace проверяет сроки всех ожидающих заказов до первого вызова, затем вызывает
ручку вне транзакции по группам до первого отказа. STATE/AMOUNT, ORDER_NOT_FOUND и MARKETPLACE_DISABLED —
`checkout.transition` (409). 404 без кода ORDER_NOT_FOUND означает отсутствие маршрута болванки;
это и технический сбой — `checkout.payment_unavailable` (503).
Успешные вызовы безопасно повторяются. Опрос может показать `partially_paid` после сбоя.
При сохранении проверяется набор оплаченных заказов; уже оплаченная покупка не меняется.
Достаточно CAS: при конфликте версий короткая транзакция повторяется до трёх раз, без сетевых вызовов.
FOR UPDATE не нужен: после исчерпания попыток состояние восстановит опрос.
Недоступный магазин с ожидающим заказом блокирует единый платёж до успешной сверки;
истечение его окна запрещает оплату всей покупки, но само по себе не отменяет заказ.
Отказы пишутся с tenantId и orderId.

Создание заказа не открывает кассу магазина и не возвращает `paymentUrl`.
Флаг сервера управляет только маршрутом stub-payment; без флага заказ создаётся,
но оплатить его нечем. Поэтому API с `PAYMENT_STUB=false` отказывает в CreateOrders
до изменения покупки и корзины. Адрес возврата кассы-болванки использует
`MARKETPLACE_PUBLIC_URL` витрины и путь `/checkout/{id}/return`.
Параметры возврата не подтверждают оплату; неизвестный исход оплаты сверяется через GET заказа.

Сервер и marketplace-api выкатываются одновременно.
Новый marketplace-api не шлёт `returnUrl`, обязательный для старого сервера (400);
новый сервер не отдаёт `paymentUrl`, обязательный для старого marketplace-api.
Флаги стенда: `PAYMENT_STUB=true` у API,
`MARKETPLACE_PAYMENT_STUB=true` у сервера. Публичный контракт кассы — в OpenAPI.

### Накопительные фасеты каталога

Контракт proshop-search 8 использует `tenantIds` и фасеты без собственного фильтра
(категория сохраняет все фильтры). Публичная цена одинакова для всех покупателей;
дополнительного чтения магазинов или назначения профилей нет.
`groupId` требует ровно один tenant; выдача и total учитывают все выбранные фильтры.

## Асинхронное оформление

Публичный сценарий описан в [checkout-async.md](checkout-async.md).
Срок оплаты — 10 минут от намерения, общий для покупки; удержание не сокращает его и применяется по правилу выше.
После своего окна сервер сам отменяет неоплаченный заказ и снимает резерв.
Площадка также может отменить заказ по ключу создания, даже если ответ с orderId потерян.

### Отмена по ключу оформления

`POST /api/v1/internal/marketplace/tenants/{tenantId}/orders/cancel-by-checkout`
использует тот же доверенный канал и авторизацию `x-internal-token`, что создание.

Тело:
```json
{"externalCheckoutId":"<checkoutId>:<tenantId>","groupId":"<tenantId>","reason":"creation_timeout"}
```
Причина: `creation_timeout` или `buyer_cancelled`.
Ключ — магазин + externalCheckoutId + groupId, тот же, что у идемпотентного создания.

Ответ 200:
```json
{"status":"cancelled","orderId":"<id>"}
```
либо:
```json
{"status":"absent","orderId":null}
```

Если по ключу есть неоплаченный заказ, сервер отменяет его и освобождает резерв в одной транзакции.
Если заказа нет, отвечает absent. В обоих случаях сервер атомарно и навсегда запрещает создание
по ключу. Создание и отмена сериализованы: поздний или конкурентный POST /orders после отмены
не создаёт заказа или резерва и получает `409 ORDER_CHECKOUT_CANCELLED`.
Повтор команды возвращает тот же результат; другая причина результата не меняет.

Оплаченный или исполняемый заказ: `409 ORDER_NOT_CANCELLABLE`, тело:
```json
{"orderId":"<id>","status":"<текущий статус>"}
```
Площадка сохраняет причину отказа и оставляет группу на сверке, не объявляя отмену успешной.
Временный сбой: `503 MARKETPLACE_TEMPORARY_FAILURE`; повтор безопасен.

Класс отказа для фонового повтора: сетевой сбой, срок HTTP и HTTP 5xx —
`unavailable`, без предела числа повторов. Известные отказы намерения по договору
(`DELIVERY_UNAVAILABLE`, `DELIVERY_CHANGED`, `OUT_OF_STOCK`, `IDEMPOTENCY_CONFLICT`,
`ORDER_CHECKOUT_CANCELLED`, отказы болванки оплаты) — `invalid`,
`ORDER_NOT_FOUND` — `not_found`, `MARKETPLACE_DISABLED` — `forbidden`.
Неизвестный код вне 5xx — `internal` с отдельным бюджетом неизвестных ошибок. Исходные код и причина сохраняются для диагностики.


Публичная покупка не содержит `quote.cost`/`quote.subsidy`: расход продавца остаётся
во внутреннем расчёте и `delivery.tariffCost` заказа магазина. Тело до записи попытки
проверяет полная zod-схема маршрута с `deliveryPrice: literal(0)`; неверное тело даёт
400 REQUEST_BODY_INVALID и не создаёт попытку. Сохранённый ответ или отказ возвращается
только для совпадающего отпечатка; другое тело — 409 IDEMPOTENCY_CONFLICT.
Отмена ключа всегда запрещает повторное создание.

Обе ручки ПВЗ площадки принимают bbox (юг, запад, север, восток); максимум 500,
при превышении — refineArea и точный total. Без bbox — offset/limit (100 по умолчанию,
максимум 200). Внутренние страницы сервера содержат 512 пунктов, курсор привязан
к упорядоченному набору (перевозчик, код). Изменение расписания не меняет состав;
при изменении состава 409 MARKETPLACE_PICKUP_CATALOG_CHANGED перезапускает чтение
с начала (не больше двух перезапусков в пределах бюджета запроса). Ошибки общего
справочника не открывают размыкатель магазина для расчёта или заказов.


Внутренние запросы передают `x-marketplace-deadline-ms` — абсолютный срок Unix в
миллисекундах. Сервер ограничивает исходящие HTTP-вызовы оставшимся временем:
обычные чтения — не более 250 мс, строгие команды — не более 4 с. Только маршрут
`GET .../delivery/pickup-points` получает именованный класс `pickupCatalog` и срок
из заголовка (без заголовка — существующий строгий резерв 4 с). Страницы одного
справочника делят один срок; при переходе к новой странице он не начинается заново.

Площадка оставляет источнику ПВЗ два бюджета стадии (определение города и список):
при `QUOTE_TIMEOUT=5s` и `PLATFORM_TIMEOUT=5s` — до 10 с. Классы `pickup_catalog`
и `pickup_selection` имеют отдельные пулы `min(4, max(1, MaxConcurrent/4))`, не
занимают резерв магазина и не меняют быстрые чтения 300 мс. Общая фоновая загрузка
остаётся ограничена `3 * QUOTE_TIMEOUT + 5s = 20s`; следующий источник получает
не больше оставшегося общего срока. Успешный пустой список кэшируется на 30 с.
Если успешного списка нет и хотя бы один источник не ответил, это
`503 seller_unreachable`, короткий кэш отказа на 5 с, а не пустая выдача.

### Диагностика регионов ПВЗ (18.11.2026)

Сервер поставляет соответствия СДЭК → ISO вместе с кодом (83 региона, официальный
тестовый справочник); Яндекс определяется по `address.region`, не городскому `geoId`.
Непустой список, целиком отсеянный из-за неизвестного региона, возвращает 503
`MARKETPLACE_PICKUP_REGION_UNMAPPED`. Площадка считает это отказом источника,
переходит к следующему и сохраняет окончательный отказ лишь на 5 с; это не
пустой город на 30 с. Настоящее отсутствие пунктов — 200, `items:[], total:0`.

Общий справочник не ограничен регионами магазина-источника. Фильтр регионов
конкретной группы выполняется индексом площадки без внешних обращений.
Если в городе есть пункты, но нет регионов, разрешённых группе, ручка покупки
возвращает 400 `delivery.region_not_allowed`; пустая область карты внутри разрешённого
города остаётся 200. Web показывает причину и предлагает изменить город.
Новые версии кэша: сервер v4, площадка v5; прежние пустые записи не используются.

### Город сайта (18.11.2026, круг 15)

Публичный `GET /api/v1/city` после гидратации определяет город по доверенному clientIP
локально: DB-IP City Lite → координаты → ближайший город встроенного HFLabs/city.
Ответ `{city,country,label?,region?,regionCode?,fiasId?,kladrId?}` имеет private/no-store.
Найденный город уже канонический: подтверждение не вызывает поиск по имени.
Страна не RU — пустой city и найденный country: web предлагает город получения в России без подтверждения.
Служебный IP, отсутствие записи или город дальше 50 км — пустые city/country.
Файл отсутствует/повреждён при отсутствии прежней рабочей базы — 503 `city.unavailable`.
Нет исходящих запросов, Redis-кэша или лимитера по адресу на этом пути.
`GET /api/v1/region` использует тот же детектор для подсказки по IP, если нет
региона профиля или сохранённого ПВЗ.
Частные адреса стенда подменяются только при явных `MARKETPLACE_ENV=development` и
`MARKETPLACE_CITY_DEV_CLIENT_IP`; production с этой переменной не запускается.
Подробности поставки и приватности — `internal/infrastructure/localgeoip/README.md`.

`GET /api/v1/delivery/cities?value=...` возвращает `{items:[{city,label,region?,fiasId?,kladrId?}]}`.
Существующий Client вызывает с внутренним токеном общий серверный
`GET /api/v1/internal/marketplace/delivery/cities?value=...`, без магазина.
Сервер использует существующий GeoSuggestService (DaData), валидирует value
(2–120 символов) до вызова; класс geoSuggest наследует x-marketplace-deadline-ms,
без заголовка — прежний строгий бюджет 4 секунды. Чтения каталога остаются 250 мс.
Лимит ручных подсказок — 30 обращений в минуту на сеть IP.
Ручной выбор остаётся доступен при отказе определения/подсказок.

Создание заказа возвращает подтверждённые `carrier` и `pickupPointCode` в сохранённом
идемпотентном ответе вместе с `orderId`, `expiresAt`, `total`. Площадка сверяет их с
единым пунктом покупки до допуска к оплате. Несовпадение снимает неоплаченную группу,
ставит cancel-by-checkout и требует нового согласия по остальным группам; новый заказ
под прежним ключом с другим телом автоматически не создаётся.
