# Контракт внутреннего API сервера для маркетплейса (PR-M1)

Источник требований PR-M1 в proshop-server и клиента `infrastructure/platformapi`.
Решение владельца 2026-11-07: вариант В, один платёж за покупку; заказы независимы.
Сейчас деньги не движутся (болванка); боевая оплата — сплит ЮKassa. Фикстуры запросов/ответов —
`internal/infrastructure/platformapi/testdata`, проверки адаптера — httptest.
Пока PR-M1 не установлен, магазины недоступны, участие не включается.
Сервер и marketplace-api выкатываются одновременно.
Сервер поддерживает `profile`/`card` в сверке настроек.
Сервер должен отдавать 200 с профилем и готовностью также кандидатам без настроек доставки.

## Общее

| Что | Как |
|---|---|
| Адрес | `PLATFORM_API_URL` + `/api/v1/internal/marketplace/tenants/{tenantId}` + путь |
| Магазин | только tenantId в пути; сегменты экранируются |
| Доступ | `x-internal-token: <SERVICE_TOKEN_MARKETPLACE>`, минимум 32 символа |
| Формат | JSON, `Accept: application/json`, у тела `Content-Type: application/json` |
| Деньги | целые копейки int64 ≥ 0; в событиях — рубли через json.Number и money.ParseRubles |
| Время | RFC 3339 с зоной |
| Успех | 200, включая повтор создания; ответ до 4 МиБ |
| Ожидание | PLATFORM_API_TIMEOUT (5s); доставка дополнительно QUOTE_TIMEOUT на магазин |
| Повторы | клиент не повторяет сам; сага повторяет создание с прежними ключом и телом |

Неизвестные поля игнорируются. Отсутствующие обязательные поля и нарушение
ограничений — `platform.invalid_response`; обязательные настройки участия —
`platform.invalid_settings`. `null` в настройках доставки и субсидии означает «не настроено»,
а не ошибку ответа. Не-null невалидная доставка или субсидия — `platform.invalid_settings`
с журналом и метрикой. Неполная карточка исключает кандидата из очереди, но сама не меняет видимость.
Видимость: `Visible = Enabled && tenant active && DeliveryValid`.
Ошибка сервера: `{"ok":false,"message":"…","status":409,"code":"…","items":null,"data":null}`.

| HTTP/code | Смысл и действие маркетплейса |
|---|---|
| 403 MARKETPLACE_DISABLED | магазин не участвует; `platform.marketplace_disabled`, внеочередная сверка настроек |
| 409 MARKETPLACE_PROMO_CODE_INVALID | заказ не создан; data.promoCode содержит код и причину отказа |
| 409 PRICE_CHANGED | заказ не создан, резерв и платёж не созданы; items — актуальные цены всех изменённых позиций |
| 409 OUT_OF_STOCK | окончательный отказ без заказа; группа cancelled, товары возвращаются в корзину |
| 409 DELIVERY_UNAVAILABLE | окончательный отказ без заказа; группа delivery_unavailable, причина reason, новый ПВЗ и новое оформление |
| 409 DELIVERY_CHANGED | плата доставки отличается от текущего расчёта; заказ не создан, группа delivery_unavailable, новое оформление |
| 409 IDEMPOTENCY_CONFLICT | тот же ключ с иным телом; окончательный отказ без orderId; группа возвращается в корзину и исключается из платежа |
| 404 ORDER_NOT_FOUND | заказ не найден в этом магазине; повторить сверку, локально не отменять |
| прочие коды/таймаут | seller_unreachable, остальные группы продолжают; создание ограничено пятью неудачами, неизвестный код журналируется с tenantId |

`403 MARKETPLACE_DISABLED` ставит outbox `participant.settings.sync` с дедупом.
Сверка обновляет настройки и готовность; временная недоступность сохраняет последний снимок.
403 при сверке и невалидные настройки обнуляют доставку и тем скрывают магазин.
Карточка и скрытия оператора при этом не меняются; стадия участия сохраняется.

## 1. Цена и наличие позиций

`POST /items/check`

Запрос: `{"buyerId":"00000000-0000-4000-8000-000000000002","items":[{"productId":"p1","quantity":2}]}`.
Ответ: `{"items":[{"productId":"p1","available":true,"price":199000,"availableQuantity":5}]}`.

`productId` — идентификатор из запроса, `available` — товар продаётся,
`availableQuantity` — свободный остаток ≥ 0. Нет строки/available=false —
товар недоступен, остатка мало — not_enough_stock, другая цена — price_changed.
Этот маршрут сервер сохраняет для других клиентов; маркетплейс использует pricing/contexts
для корзины и перед confirmed, чтобы получать также скидки.

`price` — применимая цена канала marketplace после акций. Сервер выбирает
тип из группы проверенного аккаунта → настроек канала → базового типа.
Отсутствующая цена переходит к следующему типу; ноль является ценой.
Единственный источник цен продажи — Pricing; у товара и InventoryItem цены нет.

`buyerId` — UUID проверенного identity-hub аккаунта маркетплейса, который Go
передаёт по доверенному каналу. Телефон/email получателя не определяют группу.
Для гостя поле отсутствует и выбирается публичная цена канала. Этот же buyerId
передаётся в delivery/quote и orders и входит в неизменное тело идемпотентной команды.
Браузер не может задавать чужой buyerId, группу или тип цены в публичном каталоге.

### Выбор цен для поиска

`POST /api/v1/internal/marketplace/pricing/contexts` — общий маршрут без tenantId
в пути, с тем же служебным токеном. Запрос содержит `buyerId` (UUID) и
`tenantIds` (1–100 идентификаторов магазинов). Ответ:

```json
{"items":[{"tenantId":"000000000000000000000001","profileKey":"marketplace:default","revision":7}]}
```

Для группы profileKey равен `marketplace:<priceTypeId>`. Ответ содержит только
выбор профиля, без прайса, контактных данных и себестоимости. Все магазины должны
быть действующими участниками; клиент проверяет полноту ответа и формат ключей.

Каталог получает выбор для проверенного аккаунта до запроса OpenSearch.
Фильтр цены, сортировка, диапазоны и карточки используют один профиль каждого
магазина до пагинации; браузеру отдаётся только выбранная цена. Публичные ответы
с персональными ценами имеют `Cache-Control: private, no-store`.

Проекция `catalog.product.projected` v1 содержит `priceProfiles` с `key`, `price`,
`promoPrice`, `effectivePrice` в рублях. Маркетплейс хранит только marketplace
профили, деньги переводит в копейки через json.Number/money.ParseRubles.
Сигналы складского остатка не меняют цены. Профили — восстанавливаемая проекция,
а не второй источник цен. Отсутствующий выбранный профиль скрывает предложение.
Индекс предложений версии 4 требует перестроения из новых проекций.

## 2. Стоимость доставки

`POST /delivery/quote`

```json
{"buyerId":"00000000-0000-4000-8000-000000000002","carrier":"cdek","pickupPointCode":"P1","city":"Город","items":[{"productId":"p1","quantity":2}]}
```

Перевозчик — код справочника маркетплейса; ПВЗ — его код у перевозчика.
Ответ при доступности:

```json
{"available":true,"cost":30000,"minDays":2,"maxDays":4,"expiresAt":"2026-10-24T10:30:00Z"}
```

При отсутствии доставки: `{"available":false,"reason":"no_rate"}`.
`cost` — реальная цена перевозки этой группы по договору продавца,
без промо витрины. `0 ≤ minDays ≤ maxDays`; expiresAt необязателен,
маркетплейс ограничивает срок QUOTE_TTL; истёкший ответ не принимается.

Каждая группа считается независимо, без распределения между продавцами:

- сумма товаров ≥ freeDeliveryFrom: плата покупателя 0; отдельная строка
  доставки для этой группы не показывается; freeDeliveryFrom=0 — всегда так;
- сумма ниже порога: плата = cost − max(subsidy.Apply(cost), DELIVERY_SUBSIDY_MIN_PERCENT% × cost); это именно субсидия
  продавца из §3, ограниченная cost, без денег платформы;
- остаток передаётся как `deliveryPrice` в заказ этого же магазина (§4),
  плата за доставку входит в единый платёж; покупатель видит
  «доставка магазина X: N ₽» только при ненулевой плате;
- DeliveryTotal — сумма этих плат, Total — товары по ценам площадки плюс DeliveryTotal.

Таким образом, cost применяется как основа платы только ниже порога;
`deliveryPrice` — **остаток после субсидии**, а не сырой cost.
Выше порога расчёт всё равно нужен для проверки доступности перевозки.

| reason | Кто | Значение |
|---|---|---|
| carrier_not_connected | сервер | нет перевозчика |
| pickup_point_unavailable | сервер/маркетплейс | продавец не везёт в этот ПВЗ/регион/этим способом |
| no_rate | сервер | тариф не рассчитан |
| seller_unreachable | маркетплейс | нет ответа или он не по контракту |

Словарь закрыт. available=false запрещает подтверждение с этим ПВЗ:
покупатель меняет ПВЗ либо убирает группу и оформляет новую покупку.

## 3. Настройки участия магазина

`GET /settings/marketplace`, сверка на старте и раз в SETTINGS_SYNC_INTERVAL.

```json
{
  "freeDeliveryFrom": 500000,
  "subsidy": {"enabled": true, "type": "percent", "value": 50, "maxAmount": 30000},
  "delivery": {"regions": ["RU-MOW"], "carriers": ["cdek", "yandex"]}
}
```

| Поле | Обязательное правило |
|---|---|
| freeDeliveryFrom | int64 ≥ 0, копейки; null — не настроено; 0 — доставка всегда включена |
| subsidy | null — не настроено; иначе subsidy.enabled=true, type=fixed/percent; субсидия продавца для группы ниже порога |
| subsidy.value | fixed: копейки ≥ 0; percent: целое 0–100 |
| subsidy.maxAmount | копейки ≥ 0; 0 — без потолка |
| delivery | null — не настроено; иначе объект с непустыми regions и carriers |
| delivery.regions | непустой список существующих кодов ISO 3166-2 RU, например `RU-MOW` |
| delivery.carriers | непустой список перевозчиков из закрытого перечня `cdek`, `yandex` |

Географические регионы не привязаны к перевозчику. Формат `<carrier>:<code>`
заменён ISO 3166-2 RU; числовые `location.region_code` СДЭК и `address.geoId`
Яндекса не являются ISO. Адаптеры справочников переводят их через явные
`CDEK_REGION_CODES` / `YANDEX_REGION_CODES`; неизвестный код оставляет
`regionCode` пустым и запрещает доставку. Магазин возвращает ISO-коды уже в
`GET /settings/marketplace`; невалидная доставка исключает магазин из очереди и скрывает подключённого.
Поля ПВЗ хранятся маркетплейсом; покупатель не подставляет произвольный регион.
Миграция старых зон и работа оператора описаны в [operator-gateway.md](operator-gateway.md).
Вне списка регионов или способов предложение доступно для просмотра,
но недоступно к доставке. Окончательная проверка — quote магазина. В HTTP каталога это поле
`deliveryAvailable` при паре query `deliveryCarrier` и `deliveryRegion`;
покрытие и минимум также доступны в `seller.delivery` и `seller.freeDeliveryFrom`.
Справочник ПВЗ отдаёт `regionCode`. При смене схемы индекс каталога
перестраивается автоматически новым поколением.

**Порог площадки (решение владельца 2026-10-23):** ниже freeDeliveryFrom
действующая субсидия продавца = `max(subsidy.Apply(cost), minPercent × cost / 100)`.
Сначала применяются настройка продавца и её maxAmount, затем нижняя граница.
Настройка ниже порога принимается; maxAmount не может опустить результат
ниже порога. Субсидию полностью оплачивает продавец, денег платформы нет.
`minPercent` — конфиг маркетплейса `DELIVERY_SUBSIDY_MIN_PERCENT`, по умолчанию 30,
целое 0–100; 0 выключает нижнюю границу, 100 означает всю перевозку за счёт продавца.
Процент округляется к нулю до копейки; итоговая субсидия не больше cost.
При сумме товаров не ниже freeDeliveryFrom по-прежнему deliveryPrice=0.

Админка магазина (PR-A1) читает фактический порог без служебного токена:
`GET /api/v1/delivery/settings` на маркетплейсе →
`{"deliverySubsidyMinPercent":30}`. Это публичное правило площадки, а не
новое поле ответа `GET /settings/marketplace` магазина. PR-A1 показывает
его продавцу и предупреждает, что более низкая настройка будет повышена до порога.
Схема ответа и диапазон закреплены в `api/openapi.yaml`.

Субсидия по настройке ограничена cost и ненулевым maxAmount; процент округляется к нулю.
Без обязательных настроек оформление недоступно. Для видимости нужны
Enabled, active в реестре и DeliveryValid. Привязка кассы платформе не нужна.

Согласия магазина нет: верхнеуровневое `enabled` не читается и не требуется.
Отсутствие обязательных настроек запрещает оформление через
магазин, сохраняя стадию участия. Видимость: `Visible = Enabled && tenant active && DeliveryValid`.
Каждый активный магазин автоматически становится кандидатом
с доверием `probation`; на старте и перед каждой сверкой выполняется догон реестра.

Сервер читает `GET /api/v1/internal/tenants/{tenantId}/participation` на маркетплейсе
с `Authorization: Bearer <SERVER_API_TOKEN>`. Ответ: `stage`, `awaitingReview`,
`deliveryValid`, `lastDecision: {reason, note, at, operator}` или `null`.
Не настроенный SERVER_API_TOKEN — 404; отсутствующий или неверный Bearer — 401,
как и у машинного API продвижения.
`POST /api/v1/internal/tenants/{tenantId}/participation/submit` без тела переводит
только `returned` в `candidate`, устанавливает `awaitingReview=true`, сохраняет
последнее решение; из остальных стадий — 409 `conflict`. Кнопку показывает сервер
магазина; согласие на участие не запрашивается.

## 4. Заказ и оплата

### Согласование перед созданием

До перехода confirmed → creating_orders маркетплейс заново читает §3 и
получает §2 по **всем** группам, даже если старый quote ещё не истёк.
Плату считает по текущим freeDeliveryFrom, subsidy и порогу площадки.
Если хотя бы одна плата изменилась или доступность не подтверждена,
ни одного POST /orders нет: покупка и новые расчёты сохраняются в draft,
покупателю — HTTP 409 `DELIVERY_CHANGED`, новое подтверждение обязательно.
Ответ `POST /api/v1/checkout/{id}/orders` содержит
`{"error":{"code":"DELIVERY_CHANGED","message":"…"},"checkout":{…}}`,
где checkout — новый снимок с итогами. Корзина ещё не изъята.

Запись новых расчётов и переход в creating_orders — один CAS по прежним
статусу и версии. Два конкурентных запуска не могут зафиксировать разные
снимки. После этого тело каждой команды неизменно, включая deliveryPrice,
контакт и ПВЗ: при возобновлении новые настройки в него не попадают.
Перед каждым внешним вызовом группа захватывается CAS с арендой 1 минута;
повтор по истечении аренды использует прежние ключ и тело.

### Команда магазину

`POST /orders` — только доверенный канал из общего раздела.

```json
{
  "buyerId": "00000000-0000-4000-8000-000000000002",
  "externalCheckoutId": "00000000-0000-4000-8000-000000000001:t1",
  "groupId": "t1",
  "items": [{"productId":"p1","quantity":2,"price":199000,"discounts":[]}],
  "carrier": "cdek",
  "pickupPointCode": "P1",
  "contact": {"phone":"79251234567","name":"Покупатель"},
  "deliveryPrice": 15000
}
```

Поля запроса: externalCheckoutId, groupId, items, carrier, pickupPointCode, contact, deliveryPrice;
опциональные — buyerId (UUID) и promoCode (строка). Каждый элемент items содержит productId, quantity,
price и опциональный массив discounts с promotionId и amount; адаптер всегда передаёт discounts,
в том числе пустой массив. contact содержит только phone и name.

Идентичность заказа: `(tenantId, externalCheckoutId, groupId)`.
Маркетплейс сохраняет externalCheckoutId=`<checkoutId>:<tenantId>`, groupId=tenantId.
Сервер атомарно обеспечивает уникальность, включая конкурентные запросы:
повтор возвращает **тот же** заказ и окно оплаты, даже если заказ
оплачен, отменён или истёк. Проверка ключа идёт **раньше** повторной
проверки цены/остатка; новый резерв и платёж при повторе не создаются.
Иное тело по существующему ключу — IDEMPOTENCY_CONFLICT. Срок хранения
ключа — весь срок хранения заказа, не TTL окна оплаты.
Окончательные отказы PRICE_CHANGED, DELIVERY_UNAVAILABLE, DELIVERY_CHANGED
и OUT_OF_STOCK также фиксируются по ключу атомарно:
повтор возвращает тот же отказ, даже если цена или условия доставки снова поменялись.
Это исключает гонку двух попыток, когда одна уже вернула группу в корзину,
а другая создала заказ. Новое согласие с ценой — новый checkout и новый ключ.
Временная недоступность не фиксируется как окончательный результат.

quantity — положительное целое; price — неизменная цена маркетплейса
при оформлении. Сервер сравнивает с текущей ценой по §1. Расхождение:

```json
{"ok":false,"message":"Цены изменились","status":409,"code":"PRICE_CHANGED","items":[{"productId":"p1","price":209000}],"data":null}
```

Заказ/резерв/платёж при таком отказе не создаются. Маркетплейс сохраняет
актуальные цены рядом со снимком и возвращает группу в корзину для нового
подтверждения; исходный снимок и цены уже созданных групп не меняются.
Нельзя автоматически списывать новую сумму или создавать изменённый заказ
с прежним ключом. Остальные магазины продолжают независимо.

contact — гостевой покупатель магазина: телефон и имя; не создавать
общий пользовательский аккаунт платформы. deliveryPrice — 0 или остаток
по §2, принимается в штатный заказ **как доставка**.
Сервер атомарно с созданием проверяет актуальную доступность и плату:
повторно рассчитывает cost по ПВЗ, читает действующие настройки и применяет
порог из публичных правил площадки. Недоступность — 409 DELIVERY_UNAVAILABLE
с reason (например, pickup_point_unavailable); отличие deliveryPrice от
актуальной платы — 409 DELIVERY_CHANGED. Ни заказ, ни резерв, ни платёж
при этих отказах не создаются. Так закрывается смена условий между
проверкой маркетплейса и POST без изменения уже сохранённого тела.
После первого успешного результата или окончательного отказа повтор
возвращает этот результат **до** новой проверки тарифа. Total обязан совпасть с
`sum(quantity × price − sum(discounts.amount)) + deliveryPrice`. У заказа source=marketplace.
Заказ сохраняет штатное окно оплаты; единая болванка подтверждает его через stub-payment.

Ответ (200):

```json
{"orderId":"o1","expiresAt":"2026-10-24T11:00:00Z","total":413000}
```

expiresAt — RFC 3339.
После потери ответа повтор вправе вернуть уже истёкший expiresAt: это
по-прежнему тот же заказ, маркетплейс сразу сверяет его состояние.
Перенаправления внутреннего API на другой origin запрещены клиентом.

`GET /orders/{orderId}` — тот же доверенный канал, заказ только этого магазина.

```json
{"orderId":"o1","status":"shipped","tracking":{"carrier":"carrier","number":"TRACK1","url":"https://example.test/TRACK1"}}
```

| status | Значение |
|---|---|
| awaiting_payment | ждёт оплаты |
| paid | оплачен; исполняется как обычный заказ магазина |
| cancelled | отменён, reason — обязательная непустая строка причины магазина |
| shipped | передан в доставку; tracking — отслеживание, track маркетплейс не читает |
| delivered | получен |
| returned | возврат магазину; деньги возвращает магазин |

Магазин сам отменяет неоплаченный заказ и снимает резерв после своего окна.
Маркетплейс запрещает оплату при now≥expiresAt, но не выводит отмену из
часов: GET остаётся источником истины и после истечения. Допустимы пропуски
промежуточных статусов при опросе; регресс из paid в awaiting_payment запрещён.
Отмена оплаченного заказа отражается магазином как returned.

### Локальные статусы, возврат в корзину и повторы

DELIVERY_UNAVAILABLE и DELIVERY_CHANGED при создании — локальный статус
группы `delivery_unavailable`, исходный код сохраняется в lastErrorCode,
причина сервера — в reason (при её отсутствии — код). Это окончательный
отказ: автоматического повтора нет, товары возвращаются в корзину,
покупателю предлагается другой ПВЗ и новая покупка. Этот статус не входит
в словарь GET магазина, поскольку заказа у него не было.

При переполнении корзины возвращается помещающееся количество. В группе
сохраняются `returnFailed=true`, `returnReason` и `returnRemaining`
(offerId/quantity). Повтор через минуту возвращает только остаток;
пока он не помещается, опрос и единый платёж остальных групп продолжаются.
Успешный полный возврат сбрасывает returnFailed; количества не теряются.

При неизвестном коде отказа серверного API адаптер пишет журнал с tenantId,
кодом и HTTP-статусом; группа seller_unreachable. Повтор создания после
неудач — 30s, 1m, 2m, 4m (верхний предел обычной задержки 10m).
После пяти неудач `createExhausted=true`, автоматического создания больше нет:
без orderId группа считается cancelled, возвращается в корзину и исключается из единого платежа.
IDEMPOTENCY_CONFLICT останавливает создание сразу с тем же результатом.
Возможный потерянный заказ на сервере истечёт неоплаченным. Окончательные отказы
не превращаются в временную недоступность. Код с неожиданным HTTP-статусом
считается неизвестным протоколу, даже если его имя знакомо.

Ошибки GET /orders, неизвестный статус и недопустимый регресс увеличивают
pollFailures и сдвигают NextPollAt с той же экспоненциальной задержкой.
После пяти подряд — seller_unreachable и сверка раз в 30m. Последний
подтверждённый статус сохраняется отдельно для запрета регрессов;
успешный ответ восстанавливает статус и сбрасывает счётчик.
CAS-захват опроса ставит NextPollAt **до** внешнего вызова: параллельные
GET покупки не обходят срок, включая сбои и перезапуски.

## Карточка маркетплейса

В `catalog.product.projected` версии 1, операция `upsert`, сервер передаёт
отдельный блок `product.marketplace`. Категории и атрибуты магазина остаются
для его витрины; для площадки используются только её коды и значения.
Схема строгая, без ИИ, с точным совпадением значений словаря.

```json
{
  "version": 1,
  "tenantId": "t1",
  "productId": "p1",
  "revision": 12,
  "operation": "upsert",
  "product": {
    "id": "p1",
    "name": "Товар",
    "image": "products/p1/main.jpg",
    "assets": ["products/p1/main.jpg", "products/p1/detail.jpg"],
    "price": 199.99,
    "priceProfiles": [{"key":"marketplace:default","price":249.99,"promoPrice":null,"effectivePrice":249.99}],
    "availableQuantity": 3,
    "marketplace": {
      "categoryId": "c1",
      "attributes": {
        "a1": "v1",
        "a2": 12.5,
        "a3": false
      },
      "published": true
    }
  }
}
```

Галерея снимка v1 — `product.assets`: ключи бакета без хоста и `/images/`,
сегменты не кодированы (кодирует витрина), порядок магазина; `image` обычно равен
первому элементу. При разборе остаются строки после `TrimSpace`, без пустых,
`data:`, `blob:`, управляющих символов Unicode (Cc, `unicode.IsControl`), повторов
и значений длиннее 512 байт; максимум 20.
Недопустимые и нестроковые элементы пропускаются, сообщение принимается.
Отсутствие поля и null означают пустую галерею; если после очистки она пуста, используется допустимый `image`.

`c1`, `a1`–`a3`, `v1` в примере — условные идентификаторы из загруженной
оператором схемы. Ключ Kafka по-прежнему `["t1","p1"]`; время публикации —
в метаданных события. Цены остаются рублями в событии и разбираются через
`money.ParseRubles`; числовые атрибуты не являются денежными суммами.

Форма блока:

| Поле | Смысл |
|---|---|
| `categoryId` | id одного узла дерева категорий площадки |
| `attributes` | объект код → скалярное JSON-значение; enum/string — строка, number — число, boolean — true/false |
| `published` | явное желание магазина публиковать товар; отсутствие равно false |

Нет преобразования строк в числа/boolean, синонимов, массивов, объектов,
`null` или наследования схем родителей. Обязательные поля определяются
схемой выбранного узла. Отсутствующий блок или `published=false` скрывает
предложение. Удаление товара по-прежнему передаётся без `product`.

Сервер магазина получает согласованный набор таксономии через:

- `GET /api/v1/taxonomy/version` — `{version}`, 0 до первой поставки.
- `GET /api/v1/taxonomy/categories` — `{version, categories}`: дерево с
  `id`, `name`, `title?`, `slug`; у листа `schema`, у раздела `children`.
  Атрибутов в дереве нет. `name` — короткое имя, `title` — самостоятельное
  полное имя (без него используется `name`). `slug` — уникальный сохранённый
  адрес до 128 символов, `^[a-z0-9]+(-[a-z0-9]+)*$`; витрина строит
  `/category/<slug>`, поиск фильтруется по `id`.
- `GET /api/v1/taxonomy/attributes` — `{version, attributes}`: глобальные
  определения `code`, `name`, `type`, `unit?`, `dictionary?`, `facet`,
  `values?`, `valuesMeta?`. Enum ссылается на закрытый словарь; values —
  канонические confirmed-значения, сохранённые при публикации версии.
  String может ссылаться на открытый словарь, но остаётся свободной строкой.
- `GET /api/v1/taxonomy/schemas` — `{version, schemas}`, словарь ключ →
  `{attributes: [коды], optional: [коды]}`. Порядок attributes значим;
  обязательны все поля, кроме перечисленных в optional.
- `GET /api/v1/taxonomy/categories/{id}/schema` — узел с собранными
  `attributes` в порядке схемы, с `required = !optional` и значениями снимка.

Все ответы чтения имеют `ETag: "taxonomy-<version>"`, `X-Taxonomy-Version`,
`Cache-Control: public, max-age=0, must-revalidate`; совпадающий
`If-None-Match` даёт 304, поддерживаются слабые ETag, списки и *.
Версия одна на весь набор. Сервер проверяет её и скачивает части при изменении.
Если версии ответов частей различаются из-за публикации между запросами,
нужно повторить обновление; смешивать части разных версий нельзя.
Переход сервера магазина на этот контракт — отдельная задача.

Оператор: GET `/api/v1/operator/taxonomy` возвращает весь набор в JSON;
GET `/api/v1/operator/taxonomy/{part}` — YAML parts categories, attributes, schemas.
PUT той же части принимает один YAML до 2 МиБ с обязательным
`If-Match: "taxonomy-<version>"`, публикует версию +1 и перепроверяет карточки.
Несовпадение версии — 409; неверный/отсутствующий заголовок или YAML — 400.
Скачанный YAML можно загрузить без преобразования; values и required в
глобальных определениях YAML запрещены. Старый PUT целого набора удалён.
Доступ оператора остаётся прежним. Изменения словаря влияют только на
следующую публикацию, автоматической перепубликации нет.

Маркетплейс повторно проверяет карточку при приёме. Ошибка карточки не
теряет снимок товара и не паркует корректный конверт события: inbox,
проекция и outbox сохраняются одной транзакцией. В проекции остаются
исходный блок, версия проверки, канонические атрибуты и причины отказа.
Ошибочная карточка не имеет индексируемых атрибутов и не видна ни в выдаче,
ни по прямой ссылке. Некорректный JSON или сломанный конверт события
по-прежнему паркуются по общим правилам Kafka.

| Ключ причины | Значение |
|---|---|
| `taxonomy.card_missing` | блок отсутствует |
| `taxonomy.category_unknown` | неизвестная категория, в том числе до первой загрузки схем |
| `taxonomy.attribute_unknown` | код отсутствует в схеме выбранной категории |
| `taxonomy.type` | неверный тип, null, пустая строка или непредставимое в double число |
| `taxonomy.required` | пропущено обязательное поле |
| `taxonomy.enum_value` | значение не входит в словарь |
| `taxonomy.unpublished` | магазин снял публикацию |

Причины и проверенные атрибуты доступны оператору через
`GET /api/v1/operator/catalog/offers/{offerId}/publication` под
`OPERATOR_TOKEN`. Смена версии таксономии перепроверяет все сохранённые
проекции, включая магазины без участия; индекс догоняет через outbox.
Повтор старого события не отменяет перепроверку новой схемой. Исправленный
блок магазин отправляет новой ревизией проекции. Причины в админку магазина
доставляет событие `marketplace.offer.status` (раздел «Статус предложения и
участника»); операторский токен магазинам не передаётся.

## Статус предложения и участника

Согласовано владельцем 2026-11-05 (`proshop-server/docs/marketplace-mvp.md`
§6d), реализация — этап M3. Маркетплейс сообщает магазину, виден ли товар на
площадке и почему, двумя событиями Kafka. Топики заводит сервер установки;
событие ставится в outbox той же транзакцией, что и изменение. Сервер читает
их так же, как `catalog.reference.changed`, хранит последний статус товара и
участника и показывает его в админке магазина: раздел «Маркетплейс» и
«скрыто на маркетплейсе: причина» в карточке товара.

| Событие | Топик без префикса | Ключ | Когда |
|---|---|---|---|
| статус предложения | `marketplace.offer.status` (`KAFKA_TOPIC_OFFER_STATUS`) | `["tenantId","productId"]`, заголовок `x-tenant` | изменились `visible`, `status`, причины или решение оператора |
| статус участника | `marketplace.participant.status` (`KAFKA_TOPIC_PARTICIPANT_STATUS`) | `tenantId` | включение, выключение, смена уровня доверия, в том числе автоматическая |

Время — RFC 3339 с зоной. Ключ сохраняет порядок событий одного товара и
одного участника.

### `marketplace.offer.status`

```json
{
  "schemaVersion": 1,
  "tenantId": "t1",
  "productId": "p1",
  "revision": 7,
  "visible": false,
  "status": "hidden",
  "reasons": [
    {"source": "moderation", "key": "moderation.stop_phrase", "message": "Стоп-фраза «фраза» найдена в описании"},
    {"source": "taxonomy", "key": "taxonomy.required", "message": "Нет обязательного атрибута «a1»"}
  ],
  "decision": {
    "action": "reject",
    "reason": {"code": "wrong_category", "message": "Неверная категория"},
    "note": "Уберите из описания фразу «фраза» и заполните атрибут «a1».",
    "at": "2026-11-05T12:40:00+03:00"
  },
  "at": "2026-11-05T12:40:01+03:00"
}
```

| Поле | Смысл |
|---|---|
| `revision` | ревизия проекции товара, к которой относится статус |
| `visible` | итог карточки, публикации и вердикта модерации; выключенный участник скрывает все предложения, об этом сообщает `marketplace.participant.status` |
| `status` | `published` — виден; `pending` — скрыт до решения оператора; `hidden` — скрыт, причины в `reasons` |
| `reasons` | причины скрытия или ожидания, у `published` — пустой массив; `source`: `taxonomy` — карточка не прошла схему (ключи — раздел «Карточка маркетплейса»), `moderation` — вердикт модерации |
| `decision` | решение оператора, которым установлен текущий статус; `null`, если статус поставили правила |
| `decision.action` | `allow` или `reject` |
| `decision.reason` | причина из словаря оператора `{code, message}` или `null`; код стабилен, текст — на момент решения |
| `decision.note` | заметка оператора, 1–2000 символов; её видит магазин |

| Ключ модерации | Значение и статус |
|---|---|
| `moderation.category_forbidden` | категория площадки запрещена политикой узла; `hidden`, в очередь не идёт |
| `moderation.category_manual` | категория требует ручной проверки; `pending` |
| `moderation.stop_phrase` | в названии или описании найдена стоп-фраза, она в `message`; `pending` |
| `moderation.image_missing` | у карточки нет изображения; `hidden`, новая ревизия с картинкой проходит сама |
| `moderation.probation` | участник на испытании; `pending` |
| `moderation.manual_review` | оператор открыл дело вручную, «На ручной проверке»; `pending` |
| `moderation.rejected_revision` | предыдущая ревизия отклонена оператором, новая ждёт человека; `pending` |
| `moderation.rejected_by_operator` | отказ оператора, в `message` — причина из словаря или заметка; `hidden` |
| `moderation.not_evaluated` | вердикта ещё нет, до первой оценки; `hidden` |

Отказ оператора даёт `hidden` с причинами дела и `decision.action: "reject"`;
он прилипает к предложению, и следующая ревизия снова приходит со статусом
`pending`. Одобрение действует на ревизию и не снимает причины таксономии:
пока магазин их не исправит, статус остаётся `hidden`.

### `marketplace.participant.status`

```json
{
  "schemaVersion": 1,
  "tenantId": "t2",
  "stage": "connected",
  "enabled": true,
  "trust": "probation",
  "reason": {"code": "wrong_category", "message": "Неверная категория"},
  "note": "Повторные ошибки в категориях, возвращаем на ручную проверку",
  "by": "operator",
  "at": "2026-10-30T09:30:00+03:00"
}
```

| Поле | Смысл |
|---|---|
| `stage` | `candidate`, `connected`, `returned`, `disconnected` |
| `enabled` | производное: true только для `connected` |
| `trust` | `probation` — каждое предложение ждёт одобрения оператора; `trusted` — проходит по правилам; покупатель уровень не видит |
| `reason` | причина из того же словаря оператора `{code, message}` или `null` |
| `note` | заметка оператора; при `by: "system"` — служебный текст с числом одобренных |
| `by` | `operator` — решение оператора; `system` — автоматическое повышение после `MODERATION_PROBATION_OFFERS` одобренных |

Возврат оператором отправляет `stage=returned`, `enabled=false`, причину, заметку
и `by=operator`. Отключение подключённого — `disconnected`.

Ручное понижение до `probation` обнуляет счётчик одобренных, автоматическое
повышение снова наступает после `MODERATION_PROBATION_OFFERS` одобрений.

## Реестр справочных сущностей

Владелец реестра и его пополнения — proshop-marketplace. proshop-server
и proshop-search потребляют снимки площадки, а не ведут собственный реестр.
Discovery: `GET /api/v1/internal/reference`; снимок:
`GET /api/v1/internal/reference/{code}/snapshot?since=`; запись:
`GET /api/v1/internal/reference/{code}/entries/{id}` (200/404).
Все три маршрута принимают `Authorization: Bearer <REFERENCE_READ_TOKEN>`.
Поля и семантика дельт описаны в [reference.md](reference.md).

### Имя кандидата из реестра магазинов

События `platform.tenant.created`, `platform.tenant.updated`,
`platform.tenant.suspended`, `platform.tenant.resumed`, `platform.tenant.deleted`
содержат `tenantId`, `slug`, `status`, `plan`, `hosts`, `at`; поле `name` сервер
не отправляет (формирование — `modules/platform/helpers/events.ts`,
`tenantEventMessageOf`). Поэтому имя автоматически созданного кандидата — slug.
Если в расширенном снимке поступит `name`, площадка использует его только при
допустимом имени; пустое или недопустимое имя заменяется slug без отказа события.

## Карточка магазина (06.11.2026)

Сверка `GET /api/v1/internal/marketplace/tenants/{tenantId}/settings/marketplace`
дополнительно требует `profile` и `card`, сохраняет типизированный `returns: {days: int, shipping: string, how: string} | null`:

```json
{
  "profile": {
    "name": "Магазин",
    "logo": null,
    "color": {"value": "#2F5D8A", "card": "#2F5D8A", "contrast": 6.8},
    "showcase": {"mode": "auto", "productIds": []}
  },
  "card": {"ready": false, "missing": ["requisites", "contacts", "terms"]},
  "returns": {"days": 14, "shipping": "Условия возврата", "how": "Инструкция"}
}
```

Кандидат без настроек маркетплейса получает 200 с `profile` и `card`;
`freeDeliveryFrom`, `subsidy`, `delivery`, `returns` равны null. Это «не настроено»,
а не невалидный ответ; `DeliveryValid=false`. Чеклист, его порядок и контраст цвета считает
только сервер; маркетплейс использует готовый `color.card`. Допустимое `profile.name`
становится именем участника; недопустимое сохраняет прежнее имя, остальные поля применяются.
Оператор имя участника не меняет: его задаёт магазин в настройках.
При ошибке сверки или 403 последний профиль, возврат и скрытия сохраняются. Любое изменение карточки увеличивает версию участника;
из изменений карточки только имя требует `catalog.tenant.sync`.

Сервер вызывает `POST /api/v1/internal/tenants/{tenantId}/settings/sync` без тела,
с `Authorization: Bearer <SERVER_API_TOKEN>` маркетплейса (на сервере значение
`MARKETPLACE_SERVER_TOKEN`). Ответ 202 означает постановку `participant.settings.sync`
в транзакционный outbox. Повторы склеиваются по магазину. Неизвестный участник — 404.

`GET /api/v1/internal/tenants/{tenantId}/store-card` с тем же токеном возвращает
`offers`, `fromPrice` в копейках (null при отсутствии предложений), `categories`
(`id`, `name`, `count`), `uncategorized`, `showcase` (`offerId`, `productId`, `name`,
`price`, `image`), `hidden` (`key`, `reason`, `at`), `rating`, `badge`, `rank`.
Последние три поля всегда null. Ручка доступна только при `page_public=true`,
иначе возвращает 404 (в том числе до первого пересчёта). Категории группируются по корневому узлу текущей
таксономии; порядок — число убыв., имя, id. Цена — минимальная действующая цена
публичного профиля `marketplace:default`. Если видимых предложений нет, статистика
использует отмеченные к публикации предложения, прошедшие структурную проверку.
`uncategorized` считает отмеченные товары без известной категории, независимо от допуска.
Витрина использует тот же набор, что статистика: видимые предложения, а у кандидата
без видимых — запасной набор. Сначала доступные закрепления в заданном порядке,
затем авто до трёх, без дублей. Товар без цены `marketplace:default` пропускается.

Временное правило авто до появления Q: `salesCount` убыв., наличие картинки,
ревизия убыв., productId для разрешения равенства. `salesCount` — целое int64 из
`product.salesCount` снимка `catalog.product.projected`, актуальный итог продаж магазина.
Сервер гарантирует актуальность; маркетплейс применяет значение по ревизии снимка.
Заказы площадки (`checkout_groups`) для витрины не считаются.

Шапка `ShopHeader` содержит `showcase: [{offerId, image}]`: до трёх тех же предложений
в том же порядке, что у `ShopCard` в списке магазинов. `image` может быть `null`,
пустая витрина — `[]`. Читается готовая карточка `store_cards`; скрытые предложения
исключаются при пересчёте общей публичной витрины.

Страница `GET /api/v1/shops/{slug}` требует видимости магазина
(`Enabled && tenant active && DeliveryValid`) и хотя бы одного видимого предложения:
это флаг `page_public`, независимый от готовности карточки.
«Топ магазинов» `GET /api/v1/shops` дополнительно требует готовую карточку (`public`). Список имеет оболочку
`{items,total,limit,offset}` (как соседние списки); limit по умолчанию 20, максимум 100.
`category` принимает любой узел таксономии, включая его потомков; при отборе `offers`
и порядок относятся к этому узлу. Без отбора выбирается крупнейший корневой узел.
При отсутствии категорий `category=null`, `moreCategories=0`. Условия для пустых
выборок и оболочка списка уточняют неописанные случаи исходного контракта.
Сводка хранится готовой в `store_cards` и `store_card_categories`; задача outbox
склеивается по магазину при индексации предложений, сверке, вердикте и постмодерации.
Таксономия читается один раз на пересчёт. Все три ручки карточки читают эту сводку;
список — один SQL с `ORDER BY offers DESC, name`, `LIMIT/OFFSET` и отбором по категории.
Кэш публичный: `public, max-age=0, must-revalidate`, `ETag` и `If-None-Match`,
как у публичной таксономии каталога.
Скрытый логотип заменяется null. Неготовая карточка исключает магазин
из списка, но `card.ready=false` не закрывает страницу, не отключает участие и товары.

Цвет и логотип — из опубликованного оформления Студии (`look.colors.brand`,
`look.logo.onLight`, иначе `migrateLegacy`) через external-api владельца оформления.
Публикация оформления запускает сверку; правка черновика — нет.
`color` равен null без валидного `#RRGGBB`; `contrast` округлён до 0,1.
Публичная карточка при null берёт нейтральный тёмный цвет.
`initial` — первая буква или цифра имени, знаки пропускаются; иначе пустая строка.
`showcase` изменяется только отдельной ручкой: auto хранит пустые productIds,
pinned — 1–3 уникальных id в нижнем регистре. Merchant PATCH это поле не принимает.

Подключение из любой стадии требует готовую карточку. У подключённого магазина
опустевшие контакты, реквизиты или возврат не выключают участие и товары.
Видимость остаётся `Enabled && tenant active && DeliveryValid`.
Серверные `items/check`, `delivery/quote`, `orders` требуют доставку и субсидию,
но не возврат и остальные пункты карточки. Оператор получает исходные
`card: {logo, hidden[]}`; hide/show возвращают обновлённого участника.

Задачи пересчёта из индексатора склеиваются в окне `STORE_CARD_REFRESH_DELAY`
(по умолчанию 30s, положительная длительность, проверяется на старте).
При дедупликации сохраняется самое раннее время задачи, поэтому непрерывный поток не откладывает пересчёт.
Если видимых предложений нет, внутренняя сводка при любой стадии использует отмеченные
к публикации предложения, прошедшие структурную проверку; публичность это не включает.
До первого пересчёта существующий участник получает пустую внутреннюю сводку, публичная шапка — 404.

## Отзывы товара (R4.3)

`GET /api/v1/internal/marketplace/tenants/:id/products/:productId/reviews?limit&offset`
использует тот же служебный токен, что остальные внутренние методы. Только опубликованные отзывы:

```json
{"items":[{"author":"Имя","rating":5,"text":"Текст отзыва","createdAt":"2026-11-06T10:00:00Z"}],"total":1}
```

`author` — имя без фамилии, пустая строка допустима для удалённого или безымянного покупателя; `rating` — целое 1–5; `createdAt` — RFC3339.
`limit` — 1–100 (по умолчанию 20), `offset` ≥ 0, окно ≤ 10000.
Пустой результат — `items: []`, `total: 0`; `items: null` нормализуется в пустой массив.
404 отображается в `not_found`, остальные отказы — в `unavailable` с ключом `platform.reviews_unavailable`.
Маркетплейс проверяет видимость предложения перед проксированием; публичный HTTP-кэш — 30 секунд.

Снимок товара дополнительно содержит `averageRating` (0–5, один десятичный знак) и
`ratingsCount` (неотрицательное целое). Они применяются только с новой ревизией снимка;
при отсутствии полей принимаются нули, публичный рейтинг при нулевом числе оценок — null.

### Продавец в корзине, оформлении и заказах покупателя

Каждая `CartLine` и `CheckoutGroup` содержит обязательное nullable-поле
`seller: {slug, name}` — актуальные слаг и имя участника, как в каталоге.
Для удалённого или неизвестного участника возвращается `seller: null`.
Это относится ко всем ответам корзины, создания/чтения/изменения оформления,
создания заказов и списка заказов покупателя, включая снимок при `DELIVERY_CHANGED`.
Продавцы всех строк и групп всего ответа (включая страницу заказов) читаются
одним пакетным запросом; отсутствие участника не ломает ответ.

## R5: промокод группы и отслеживание (R4 сервера)

`POST /api/v1/internal/marketplace/pricing/contexts` для группы принимает
`{buyerId, tenantIds:[tenantId], items:[{productId,quantity}], promoCode}`.
Поле `promoCode` передаётся только для непустого кода; без кода поле отсутствует.
Ответ: `{items:[{tenantId,profileKey,revision,items,promoCode}]}`.
Строки `items`: `{productId,available,availableQuantity,price,discounts}`;
`discounts`: `[{promotionId,amount}]`. Деньги — целые копейки.
`promoCode`: `{code,valid,discount,message}` либо `null`; message при успехе — null.
Неверный код — обычный результат `valid:false` с обязательной причиной message;
valid:false с message:null нарушает контракт ответа. Технический сбой — ошибка.
Цена единицы остаётся после ITEM; итог строки — `price * quantity - sum(discounts.amount)`.
GET /api/v1/cart вызывает Verify: все группы проверяются параллельно.
Проверка повторяется и при изменении корзины. Каждая группа, включая
группы без кода, получает цены и автоматические скидки из pricing/contexts.
Проверенный код с valid:false и причиной в message не переносится в покупку.
После Consume/Return код остаётся непроверенным: valid:false, discount:0, message:null.
Create проверяет такой код у сервера. Скидки входят в снимок покупки.
При возврате группы код, уже установленный в корзине, имеет приоритет над снимком покупки.
При отсутствии кода восстанавливается код покупки; при отказе кода —
valid:false с причиной, в остальных случаях — состояние «не проверен».

В `POST /tenants/{id}/orders` передаётся принятый `promoCode`.
`/delivery/quote` промокода не принимает.
В каждой позиции заказа передаются `discounts` (в том числе пустой массив) для сравнения
сервером внутри транзакции: изменение цены или скидок — `PRICE_CHANGED`.
Недействующий код при создании заказа — окончательный 409 `MARKETPLACE_PROMO_CODE_INVALID`
с телом `{ok,message,status,code,items,data:{promoCode}}`.
Причина для покупателя берётся из data.promoCode.message; без неё — сообщение ErrPromoInvalid.
Маркетплейс сохраняет в группе `checkout.promo_invalid`, возвращает её строки в корзину
и продолжает оформление остальных магазинов. Ответ 200 с `valid:false` не считается
отказом: проверяется сумма созданного заказа. После отказа кода на Create/Confirm корзина
перепроверяется; новая покупка создаётся без отвергнутого кода.

`GET /tenants/{id}/orders/{orderId}` возвращает `tracking:{carrier,number,url}|null`
с nullable `number`: у перевозчика может быть только ссылка.
Перевозчик должен быть непустым, ссылка — допустимой HTTP(S) ссылкой;
некорректное значение превращается в null. Фоновый опрос сохраняет tracking в снимок
группы покупки, отдельно от order_progress. Чтение покупки и списка покупок отдаёт этот
снимок без кэша и запросов сервера. В публичной группе покупки есть только tracking.

## Единая оплата — служебная болванка

`POST /api/v1/internal/marketplace/tenants/{tenantId}/orders/{orderId}/stub-payment`
Авторизация: `x-internal-token`. Тело: `{ "amount": 413000 }`, целые копейки,
товары после скидок + доставка заказа. Ответ 200: `{ "status": "paid" }`.

Сервер проводит оплату тем же путём, что подтверждённый платёж: заказ, склад,
события и уведомления. Провайдер/метод `stub`, движения денег нет.
Повтор уже оплаченного этой болванкой заказа возвращает тот же ответ 200.
Несовпадение суммы — 409 `MARKETPLACE_STUB_PAYMENT_AMOUNT`; неподходящий статус —
409 `MARKETPLACE_STUB_PAYMENT_STATE`; заказа нет — 404.
Без `MARKETPLACE_PAYMENT_STUB=true` ручка отсутствует (404).

Ошибки — обычный конверт сервера `{ok:false,message,status,code,items:null}`.
Технический сбой — 503 `MARKETPLACE_TEMPORARY_FAILURE`.
Кодов `MARKETPLACE_STUB_PAYMENT_FAILED` и `MARKETPLACE_STUB_PAYMENT_DISABLED` нет;
общий 403 `MARKETPLACE_DISABLED` возможен.
Идемпотентность сохраняется для оплаченных болванкой заказов после отгрузки и доставки;
отменённый или возвращённый заказ — 409 STATE. Возврат болванки проводится локально,
без провайдера: резерв и сразу «проведён», без ожидания возврата и блокировки удаления заказа.

Marketplace проверяет сроки всех ожидающих заказов до первого вызова, затем вызывает
ручку вне транзакции по группам до первого отказа. STATE/AMOUNT, ORDER_NOT_FOUND и MARKETPLACE_DISABLED —
`checkout.transition` (409). 404 без кода ORDER_NOT_FOUND означает отсутствие маршрута болванки;
это и технический сбой — `checkout.payment_unavailable` (503).
Успешные вызовы безопасно повторяются. Опрос может показать `partially_paid` после сбоя.
При сохранении проверяется набор оплаченных заказов; уже оплаченная покупка не меняется.
Достаточно CAS: при конфликте версий короткая транзакция повторяется до трёх раз, без сетевых вызовов.
FOR UPDATE не нужен: после исчерпания попыток состояние восстановит опрос.
Недоступный магазин с ожидающим заказом блокирует единый платёж, пока магазин не ответит на подтверждение;
истечение его окна запрещает оплату всей покупки, но само по себе не отменяет заказ.
Отказы пишутся с tenantId и orderId.

Создание заказа не открывает кассу магазина и не возвращает `paymentUrl`.
Флаг сервера управляет только маршрутом stub-payment; без флага заказ создаётся,
но оплатить его нечем. Поэтому API с `PAYMENT_STUB=false` отказывает в CreateOrders
до изменения покупки и корзины. Адрес возврата кассы-болванки использует
`MARKETPLACE_PUBLIC_URL` витрины и путь `/checkout/{id}/return`.
`MARKETPLACE_PUBLIC_URL` — тот же HTTPS-origin, с которого отдаётся `/api/v1`:
касса и витрина находятся за одним прокси.
Параметры возврата не подтверждают оплату; статусы сверяются через GET заказа.

Сервер и marketplace-api выкатываются одновременно.
Перед выкатом на kind нужно убедиться, что нет покупок в `creating_orders`: удаление `returnUrl`
меняет отпечаток идемпотентности тела запроса, поэтому повтор старой попытки получит `IDEMPOTENCY_CONFLICT`.
Новый marketplace-api не шлёт `returnUrl`, обязательный для старого сервера (400);
новый сервер не отдаёт `paymentUrl`, обязательный для старого marketplace-api.
Флаги стенда: `PAYMENT_STUB=true` у API,
`MARKETPLACE_PAYMENT_STUB=true` у сервера. Публичный контракт кассы — в OpenAPI.
