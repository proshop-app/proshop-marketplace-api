# Каталог после поставки 10: ограничения поиска

Проверено 14.11.2026 на встроенных YAML поставки 10,
SHA-256 `e0b0788645c21e0b101f3164ae9e4e74d2fe0a12c5b3e43de7fbd9d7bd29b70f`.
432 атрибута, 404 с `facet: true`; в снимке 9 — 219 атрибутов, 218 фасетных.
3974 узла, 3555 листьев, 29 направлений, глубина 5.

## Причины и воспроизведение

- Старый `PrepareQuery` без категории отправляет 404 фасета. Тест на настоящей
  поставке до исправления падает: `filters=0 facets=404 exceeds search v5`.
  `sc-search/marketplace.ValidateQuery` отвергает более 256 фильтров или фасетов.
- HTTP читает `category`, но игнорировал `categoryId`. На HTTP-стенде корень
  и `?categoryId=accessories` дают 503 `search.unavailable`, а
  `?category=accessories` — 200. В этой области 46 фасетов, переполнения нет.
  `?categoryId=accessories&attributeFacets=false` также даёт 200.
- Операторский загрузчик таксономии поиска ограничивал весь справочник
  256 атрибутами: снимок с 432 не мог обновиться. Теперь глобальный предел
  512 согласован с площадкой, отдельная схема по-прежнему ограничена 256.

## Правило

Фасеты характеристик — пересечение полей **всех листьев** выбранной области,
включая корень без категории. На листе это его схема; одинаковые схемы
поддерева сохраняют все свои фасетные поля. `facet=false` и deprecated исключены.
Бюджет — 32 поля: сначала выбранные фильтры из пересечения, затем остальные
по коду. После отсечения ответ сортируется по коду. Базовые category/tenant/
price/inStock и селектор фасетов сохраняют свои правила.

Объединение схем остаётся областью допустимых фильтров, поэтому сужение набора
фасетов не меняет фильтрацию, total, цены или предложения. Более 256 фильтров
площадка отклоняет как 400 до вызова поиска. У схем установлен предел 256,
чтобы новый операторский импорт не породил непринимаемые поиском документы.
Лимит поискового запроса и документа не повышается. Потомки при сборке полей
обходятся напрямую без повторного поиска каждого листа от корня.

## Соседние ограничения

| Место | Проверка / решение |
|---|---|
| Фильтры | Был предел глобального справочника 512, теперь контрактные 256; до 100 значений/поле и 1024 символов/значение уже согласованы |
| Подсказки значений | Оператор: до 32 constraints, до 50 результатов; исправлен глобальный снимок 256 → 512, схема ≤256 |
| Служебные attribute-values | include/exclude до 32 категорий; площадка уже делит include на пачки, избыточные exclude не объединяет небезопасно, фиксирует пропуски |
| Фоновые покупательские фразы | Имена категорий ограничены 5000 (3974 укладываются); значения — до 20 ключей × 200 значений, а не все 432 атрибута |
| Конфигурация facets=auto | MaxCategories=1000, MaxKeys=50 и 4 MiB относятся к локальным категориям магазина, не к канонической таксономии; SearchOffers этим снимком не пользуется, изменения не нужны |
| Публичные части для web / admin | HTTP-стенд, версия 36: дерево 1534650 B, схемы 128008 B, атрибуты 162727 B, dictionary-sources 765128 B; все 200. Snapshot поставки 1821304 B, загрузчик поиска допускает 32 MiB на часть |
| Операторский YAML-импорт | Предел 2 MiB/часть; дерево 1668506 B, схемы 105317 B, атрибуты 168765 B; реальные файлы проходят существующий HTTP-тест поставки |
| Дерево | Оба сервиса допускают 4096 узлов и глубину 16; осталось 122 узла. Лимит не повышен: следующая поставка должна пройти check; граница 4096/4097 проверена тестом поиска |
| Документы / индекс | Максимум 27 полей в схеме, 26 фасетов; потолок документа 256. Flat-объекты создают dynamic keyword для каждого кода и float для числовых; даже верхняя оценка 2×512 плюс статические поля ниже лимита 2000 (живой mapping не прочитан) |
| HTTP поиска | 4 MiB/запрос, текущие запросы имеют до 26 определений фасетов; размер дерева в запрос не включается |

## Повторная проверка

`go test ./internal/infrastructure/searchapi -run TestReleaseSearchLimits -v`
проверяет корень и каждый узел реальной поставки. Переменная
`TAXONOMY_CONTRACT_DIR` сохраняет CSV, snapshot и wire-запросы.

`bash scripts/check-search-taxonomy.sh /путь/к/proshop-search` готовит
закреплённый артефакт Uno и строит этот корпус
и проверяет все 3975 запросов настоящим `marketplace.ValidateQuery` поиска,
а snapshot — загрузчиком операторских подсказок. Без этой команды внешние
корпусные тесты поиска пропускаются; его граничные тесты автономны.
CSV получен из того же корпуса, старые числа восстановлены объединением схем.

В обоих клонах прошли `go build ./...`, `go vet ./...`, `go test ./...`;
на площадке также `go vet -tags integration ./...`, `make lint` (0 issues),
`go run ./cmd/taxonomy check`. Корпусный скрипт прошёл для обоих сервисов.
В поиске также прошёл `go test -race ./...`, на площадке — `make test` (все пакеты с race).

Живые интеграции с PostgreSQL/OpenSearch/Kafka, нагрузка, frontend в браузере
и выкладка исправлений не проверены: доступен только прежний HTTP-стенд,
Docker/kubectl недоступны. Состояние его mapping не читалось.
Исходные `.git` смонтированы read-only: коммиты подготовлены в отдельных
временных локальных клонах и доступны как Git bundles, исходные рабочие
деревья содержат исправления. Никакого пуша.
