# IDH-05: JWT покупателей и операторов через identity-hub

Проверку звонка покупателя и пароля оператора выполняет marketplace-api.
Токены выпускает identity-hub: отдельный backend-клиент покупателей в realm
`marketplace`, другой клиент операторов в realm `platform`. Профили, заказы
и роль оператора остаются локальными. Контакты не объединяют аккаунты.

## Контракт

- Покупатель: access JWT в `__Host-mp_access`, случайный ключ продления в
  `__Host-mp_key`. Оператор: `__Host-kvazar_operator` и
  `__Host-kvazar_operator_key`. Все cookie HttpOnly/Secure/SameSite=Strict,
  Path=/, без Domain. Имя cookie не является дополнительной защитой.
- Прежний `__Host-mp_session` только удаляется. Старые opaque access-токены
  не принимаются; переключение требует повторного входа.
- Обычная авторизация проверяет ES256/JWKS, iss/aud/client_id/realm,
  отсутствие чужого tid, sub/jti/iat/nbf/exp. ID token вместо access не принимается.
  Redis и hub userinfo не участвуют в обычной проверке access.
- `identity_bindings` хранит неизменяемое соответствие issuer/client/sub/local_id.
  Телефон и email не используются для поиска идентичности hub. Покупатель
  перечитывается из PostgreSQL. Оператор сверяется с текущей конфигурацией и ролью;
  смена пароля/локального ID немедленно отклоняет прежний subject даже до exp JWT.
- Redis хранит только AES-256-GCM refresh и метаданные. AAD привязан к
  issuer/client и SHA-256 браузерного ключа. Access JWT не сохраняется в Redis.
  Отдельные namespaces клиентов; окно refresh абсолютно и не продлевается ротацией.

## Загрузка, обновление и выход

GET `/api/v1/me` и GET `/api/v1/operator/session` могут молча обновить
отсутствующий или криптографически проверенный истёкший access. Поддельный JWT
не исправляется; истёкший JWT другого аккаунта не допускает использования его ключа.

При работе интерфейса interceptor использует exp профиля только из памяти:
POST refresh → GET профиль → исходная операция. После 401 бизнес-операции
не повторяются. 401 завершает текущий вход; 503 сохраняет профиль, но не
отправляет операцию без обновления. Cookie-запросы сериализуются, в поддерживаемых
браузерах — также Web Locks между вкладками. Поздний ответ прежнего входа
отклоняется до записи в состояние другого покупателя.

Операторский refresh: POST `/api/v1/operator/session/refresh`; покупательский:
POST `/api/v1/auth/refresh`. Ключ продления не заменяет access для бизнес-ручек.
SSR пересылает JWT как Bearer, ключ — только на me/refresh/logout; возвращает
только разрешённые cookie своему браузеру. Origin проверяется до пересылки
cookie-операций и на backend. Operator mutation требует свой Origin и
`X-Requested-With: KvazarOperator`; загрузка профиля допускает отсутствие Origin
у same-origin GET, сохраняя проверку custom header и Sec-Fetch-Site.

Single-flight в процессе возвращает общий результат только из памяти.
Между процессами — Redis Claim/Finish CAS: последующий экземпляр обменивает
уже новый refresh. Ошибка до отправки в hub освобождает Claim; неизвестный
результат сетевого обмена блокирует повтор прежнего секрета и требует нового
входа. Отмена/потеря процесса не разрешает повторить потенциально использованный refresh.
Logout удаляет refresh до сетевого revoke; Finish не воскрешает запись.
Даже при ошибке revoke браузерные cookie очищаются, ошибка не скрывается.
Скопированный JWT после выхода остаётся действительным до exp — stateless-доступ.

## Настройка и выкат

Обязательны `IDENTITY_HUB_URL`, `IDENTITY_CLIENT_ID`, `IDENTITY_BACKEND_SECRET`,
`IDENTITY_REFRESH_KEY` (отдельные 32 случайных байта в base64).
При включённом операторском входе также обязательны
`IDENTITY_OPERATOR_CLIENT_ID`, `IDENTITY_OPERATOR_SECRET`: разные client_id и
credentials. Общие `IDENTITY_TIMEOUT` (по умолчанию 5s), `IDENTITY_CA_FILE`
(добавляет CA, проверка TLS остаётся включённой).
URL — HTTPS origin без пути; HTTP разрешён только на loopback для локальных тестов.
`SESSION_TTL` ограничивает refresh покупателя, `OPERATOR_SESSION_TTL` — оператора.

В hub заранее зарегистрировать оба backend-клиента с разными `backend_secret_env`,
PKCE S256 и фиксированным redirect `https://backend.identity.invalid/<client_id>`.
Рабочий clients.yaml и существующая авторизация этим заданием не меняются.

Миграция 00024 создаёт только identity_bindings; на рабочих БД не запускалась.
Down отказывается удалять непустые соответствия. При откате приложения нельзя
считать прежние opaque-токены действительными: нужен новый вход.
Не включать новый API без настройки двух clients, секретов, ключа и миграции.

Приёмка включает реальные локальные hub/PostgreSQL/Redis, короткий TTL JWT,
границы двух realms и клиентов, конкуренцию, logout, ошибку preflight,
неизвестный результат обмена, SSR cookie и формы двух интерфейсов.
Результаты и ограничения полной web-проверки — в общем handoff сервера.
