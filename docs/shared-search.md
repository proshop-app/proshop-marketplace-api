# Общий поиск маркетплейса

Backend маркетплейса сохраняет проекции в PostgreSQL, повторно проверяет
публикацию по текущей таксономии и через outbox передаёт предложения в
`proshop-search`. Текстовый поиск, ранжирование, фильтры, фасеты и физические
поколения индекса принадлежат общему поиску. Собственный OpenSearch-клиент
маркетплейса используется только для геоиндекса пунктов выдачи.

## Контракт и сохранённое поведение

Служебные маршруты `/api/v1/internal/marketplace/*` защищены отдельным
`SEARCH_MARKETPLACE_TOKEN`. Маркетплейсу нужны `SEARCH_URL`, этот токен,
`SEARCH_TIMEOUT` (35 секунд) и `SEARCH_MAINTENANCE_INTERVAL` (минута).
`GET /status` возвращает `contractVersion: 5` и `ready`. Старый контракт
не принимается. Совместимость схемы активного поколения проверяется отдельно:
старая схема означает необходимость перестроения из PostgreSQL.

Документы сохраняют все ценовые профили в целых копейках, условия и порог
доставки, канонический путь категории и только проверенные атрибуты. Типы
числа и boolean передаются явно: строка `"001"` остаётся строкой, `false`
остаётся boolean. Товарные категории магазина не подменяют категорию площадки.
Цены и характеристики не проходят через промежуточное представление денег
в `float64`.

Backend определяет ценовой профиль покупателя отдельно для каждого продавца.
Поиск применяет его до отбора по цене, сортировки, пагинации и агрегаций.
`priceContexts: null` означает публичные профили; пустой объект означает
отсутствие разрешённых профилей. Нулевая цена допустима. Диапазон цен фасета
читается через `top_hits`, чтобы не потерять целые копейки выше 2^53.

Фасеты и фильтры атрибутов сохраняют контракт публичного API. OR действует
внутри значений одного атрибута, AND — между кодами. Числовые диапазоны
включают границы, `inStock=false` отличается от отсутствующего фильтра.
Фасеты считаются без собственного фильтра до пагинации (category — со всеми); порог покрытия
редких атрибутов по-прежнему применяет приложение маркетплейса.

Общий поиск ограничивает каждый запрос каталогом площадки и опубликованными
видимыми предложениями. Идентичность включает tenant и product; версии
защищают от поздних снимков, снятие публикации оставляет tombstone.

## Пересборка

На первом запуске или при старой схеме backend создаёт новое поколение,
заполняет его из согласованной PostgreSQL-проекции, выполняет догоняющий
проход и переключает рабочее поколение. Общий поиск сохраняет строящееся
поколение до сканирования и направляет текущие записи в обе цели. Прерванная
сборка старой схемы заменяется новой без активации устаревшего поколения.

CLI и фоновые процессы используют одну advisory lock в PostgreSQL с отдельным
соединением. Потеря соединения отменяет работу; два процесса не завершают
сборку независимо. Фоновая проверка размера и незавершённого переноса
использует прежние бюджеты общего поиска: не более трёх поколений, лимиты
частей, шардов и свободного диска.

## Теги и миграции

Маркетплейс больше не подписывается на `catalog.tag.projected`, не хранит
проекцию тегов, не принимает фильтр `tag` и не возвращает `tags` в карточке.
Миграция `00028_retire_search_tags.sql` удаляет `catalog_tags` и поле `tags`
только из проекции `catalog_products`. Ручной справочник магазина и его
привязки в server/admin не затрагиваются.

Миграция реестра справочных сущностей `00027_reference_registry.sql` входит
в тот же комплект и выполняется перед `00028`. Старые миграции таксономии
не меняются, вторая схема хранения не добавляется.

## Порядок обновления и откат

1. Выпустить общий поиск с целевой версией контракта первым. Проверить отдельный каталог площадки,
   служебный токен и бюджеты пересборки. При несовместимой схеме до пересборки площадкой ожидается
   окно HTTP 503: старое поколение несовместимо с новой схемой.
2. Сохранить резервную копию PostgreSQL и применить миграции, необходимые
   для выбранного релиза. Дождаться миграций до запуска нового backend.
3. Запустить backend с согласованной версией контракта, `SEARCH_URL` и `SEARCH_MARKETPLACE_TOKEN` одной
   репликой или со стратегией Recreate, исключив запись старых подов во время
   пересборки. Если поды сменяются постепенно, после ухода всех старых подов
   обязательно повторить пересборку. До готовности backend восстанавливает каталог
   площадки; затем проверить цены гостя и покупателя,
   фильтры, фасеты, доставку, снятие публикации и отставание outbox.
4. Следить за ошибками HTTP к поиску, `marketplace_outbox_*`, возрастом задач,
   отставанием Kafka, ошибками фоновой пересборки и readiness `search`/`opensearch-pickups`.

Рабочая установка и production этой задачей не обновляются.

Для отката поиска закрыть трафик, вернуть прежний backend вместе с движком
предыдущего контракта (v3) и выполнить `reindex` из актуальной PostgreSQL-проекции
до открытия чтения старого индекса. Старая копия без догоняющих удалений
не является безопасным откатом. Данные магазинов при этом не объединяются
с каталогом площадки.

## Проверки

Обычные проверки: `go build ./...`, оба `go vet`, `make lint`, `make test` и
`make test-integration`. Пакет `searchapi` дополнительно проверяет настоящий
путь PostgreSQL → outbox → HTTP → общий поиск → OpenSearch, если запущен
изолированный контур из `proshop-search/tools/marketplace-fixture`:

```bash
# В proshop-search; HTTP слушает только 127.0.0.1:19207.
TEST_OPENSEARCH_URL=http://127.0.0.1:19206 go run ./tools/marketplace-fixture

# В proshop-marketplace; остальные TEST_* задают изолированную инфраструктуру.
TEST_SEARCH_API_URL=http://127.0.0.1:19207 make test-integration
```

Без `TEST_SEARCH_API_URL` сквозная HTTP-проверка явно пропускается. Контур
создаёт собственный случайный набор индексов и удаляет его при штатной остановке.
В общем поиске `SEARCH_GOLDEN=1 go test -race ./internal/modules/search
./internal/infrastructure/db -run TestGoldenMarketplace` проверяет точные
цены и фасеты, изоляцию продавцов, перестановку событий, смену схемы и
прерванную пересборку на настоящем OpenSearch.

### Поля каталога R2 — контракт версии 3

Документ предложения передаёт `rating: {value, count} | null`;
`sort=rating` сортирует по убыванию среднего балла, затем числа оценок; без оценок — последними.
Баллы приходят из ревизионного снимка товара (`averageRating`, `ratingsCount`).
Фасет `price` может дополнительно содержать `buckets: [{from, to, count}]`: границы
в целых копейках, до 20 корзин по круглой шкале движка. Адаптер передаёт корзины
без пересчёта; старый ответ без `buckets` остаётся допустимым.
Рекомендации читают локальную проекцию пачкой кандидатов (при пустом personal — повтор для popular), поэтому
не требуют расширения поискового протокола для категорий интересов и исключений.

Требование R2: поле `rating`, сортировка `rating` и гистограмма относятся
к контракту поиска **версии 3**. Сначала выкатить движок с поддержкой версии 3 (R3),
затем marketplace-api. `Offer.rating` берётся из ответа движка.
Для baseline рейтингов переиздать снимки товаров на сервере с новой ревизией,
дождаться обработки событий и обновления индекса и сводок магазинов.

В документе v3 нет `salesCount`: продажи хранятся только в PostgreSQL для рекомендаций,
поиск не применяет скрытый буст продаж.

Рекомендации читаются двумя запросами: категории через `category_id = ANY(...)`
и популярное без условия категорий. Оба требуют `on_sale AND default_price IS NOT NULL`
для частичных индексов. Перед DISTINCT ON группы вариантов берётся верх по sales_count:
не более `limit * recommendationCandidateMultiplier` (множитель 10) кандидатов.
После свёртки применяется окончательный LIMIT. Поэтому блок может быть короче лимита,
если среди верхних кандидатов больше 10 вариантов на группу.
Распаковка price_profiles нужна только вошедшему с фильтром цены; иначе используется default_price.
Приоритет «другие магазины первыми» применяется после внутреннего отсечения кандидатов.
Если магазин-источник занимает весь верх, «похожие» покажут его, даже если за пределами
внутреннего LIMIT есть другие магазины.
Регион доставки ограничивает все виды рекомендаций.

### Галерея — контракт версии 4

Контракт 4 = контракт 3 + `offer.assets: string[]`: максимум 20 уникальных
ключей, каждый непустой после `TrimSpace`, без управляющих символов Unicode
(Cc, `unicode.IsControl`), до 512 байт; порядок магазина. В ответах поиска всегда массив,
включая пустой. Скрытый документ не содержит галерею карточки.
При разборе снимка недопустимые ключи отбрасываются без отравления сообщения;
повторы удаляются. Подстановка `image` проходит ту же проверку.
Публичный API возвращает `assets` только в карточке товара, не в списках.
Галерея — поле только для чтения: движок хранит её в `_source` внутри `offer` и не индексирует, поиск,
фильтры и сортировка по ней не работают и не планируются.

Сначала выкатить движок с контрактом 4, затем marketplace-api с контрактом 4
и дождаться пересборки несовместимого поколения. Миграция jsonb не нужна.
После выката переиздать снимки сервером в proshop-server:
`scripts/seed-search-projection.ts --all --apply`, затем дождаться Kafka и outbox.
Иначе у уже принятых товаров галерея пустая до следующей ревизии;
одна пересборка индекса отсутствующие в PostgreSQL ключи не восстановит.

### Накопительные фасеты — контракт версии 5

`/search` принимает `tenantIds: string[]` вместо `tenantId`; публичный API —
`?tenant=A&tenant=B` (до 100 значений, повторы удаляются).
`groupId` требует ровно один магазин. Значения одного фасета объединяются через ИЛИ,
разные фасеты — через И. Выдача и total учитывают все фильтры.
Каждый фасет (tenant, inStock, price, attr.<code>) исключает только собственный
фильтр, включая обе границы диапазона. category остаётся навигацией и учитывает
все фильтры. Текст, категория, группа и ценовой профиль всегда ограничивают выборку.
Счётчики и min/max рассчитываются до пагинации; при total=0 могут остаться варианты.
Ценовые контексты покупателя запрашиваются для всех публичных магазинов, даже при
выбранном tenant; сужение допускается только для groupId. Гость использует default.

Выкатывать совместно с proshop-search контракта 5: проверить `/status`, несколько
магазинов и перекрёстные фасеты для гостя и персонального профиля. Перестроение
нужно при `ready=false`/смене схемы по процедуре выше, а не из-за tenantIds само по себе.
