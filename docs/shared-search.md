# Общий поиск маркетплейса

Backend маркетплейса сохраняет проекции в PostgreSQL, повторно проверяет
публикацию по текущей таксономии и через outbox передаёт предложения в
`proshop-search`. Текстовый поиск, ранжирование, фильтры, фасеты и физические
поколения индекса принадлежат общему поиску. Собственный OpenSearch-клиент
маркетплейса используется только для геоиндекса пунктов выдачи.

## Контракт и сохранённое поведение

Служебные маршруты `/api/v1/internal/marketplace/*` защищены отдельным
`SEARCH_MARKETPLACE_TOKEN`. Маркетплейсу нужны `SEARCH_URL`, этот токен,
`SEARCH_TIMEOUT` (35 секунд) и `SEARCH_MAINTENANCE_INTERVAL` (минута).
`GET /status` возвращает `contractVersion: 2` и `ready`. Старый контракт
не принимается. Совместимость схемы активного поколения проверяется отдельно:
старая схема означает необходимость перестроения из PostgreSQL.

Документы сохраняют все ценовые профили в целых копейках, условия и порог
доставки, канонический путь категории и только проверенные атрибуты. Типы
числа и boolean передаются явно: строка `"001"` остаётся строкой, `false`
остаётся boolean. Товарные категории магазина не подменяют категорию площадки.
Цены и характеристики не проходят через промежуточное представление денег
в `float64`.

Backend определяет ценовой профиль покупателя отдельно для каждого продавца.
Поиск применяет его до отбора по цене, сортировки, пагинации и агрегаций.
`priceContexts: null` означает публичные профили; пустой объект означает
отсутствие разрешённых профилей. Нулевая цена допустима. Диапазон цен фасета
читается через `top_hits`, чтобы не потерять целые копейки выше 2^53.

Фасеты и фильтры атрибутов сохраняют контракт публичного API. OR действует
внутри значений одного атрибута, AND — между кодами. Числовые диапазоны
включают границы, `inStock=false` отличается от отсутствующего фильтра.
Фасеты считаются по всей отфильтрованной выдаче до пагинации; порог покрытия
редких атрибутов по-прежнему применяет приложение маркетплейса.

Общий поиск ограничивает каждый запрос каталогом площадки и опубликованными
видимыми предложениями. Идентичность включает tenant и product; версии
защищают от поздних снимков, снятие публикации оставляет tombstone.

## Пересборка

На первом запуске или при старой схеме backend создаёт новое поколение,
заполняет его из согласованной PostgreSQL-проекции, выполняет догоняющий
проход и переключает рабочее поколение. Общий поиск сохраняет строящееся
поколение до сканирования и направляет текущие записи в обе цели. Прерванная
сборка старой схемы заменяется новой без активации устаревшего поколения.

CLI и фоновые процессы используют одну advisory lock в PostgreSQL с отдельным
соединением. Потеря соединения отменяет работу; два процесса не завершают
сборку независимо. Фоновая проверка размера и незавершённого переноса
использует прежние бюджеты общего поиска: не более трёх поколений, лимиты
частей, шардов и свободного диска.

## Теги и миграции

Маркетплейс больше не подписывается на `catalog.tag.projected`, не хранит
проекцию тегов, не принимает фильтр `tag` и не возвращает `tags` в карточке.
Миграция `00028_retire_search_tags.sql` удаляет `catalog_tags` и поле `tags`
только из проекции `catalog_products`. Ручной справочник магазина и его
привязки в server/admin не затрагиваются.

Миграция реестра справочных сущностей `00027_reference_registry.sql` входит
в тот же комплект и выполняется перед `00028`. Старые миграции таксономии
не меняются, вторая схема хранения не добавляется.

## Порядок обновления и откат

1. Выпустить общий поиск с контрактом 2. Проверить отдельный каталог площадки,
   служебный токен и бюджеты пересборки.
2. Включить миграции `00027` и `00028` в согласованном порядке, сохранить резервную
   копию PostgreSQL. Дождаться миграций до запуска нового backend.
3. Запустить backend с `SEARCH_URL` и `SEARCH_MARKETPLACE_TOKEN`. До готовности
   он восстанавливает каталог площадки; затем проверить цены гостя и покупателя,
   фильтры, фасеты, доставку, снятие публикации и отставание outbox.
4. Следить за ошибками HTTP к поиску, `marketplace_outbox_*`, возрастом задач,
   отставанием Kafka, ошибками фоновой пересборки и readiness `search`/`opensearch-pickups`.

Рабочая установка и production этой задачей не обновляются.

Для отката поиска закрыть трафик, вернуть прежний backend, восстановить схему
`00028 Down` и обязательно выполнить `reindex` из актуальной PostgreSQL-проекции
до открытия чтения старого индекса. Старая копия без догоняющих удалений
не является безопасным откатом. `Down` восстанавливает таблицу тегов, но
не удалённые значения; для полного восстановления нужна резервная копия.
Данные магазинов при этом не объединяются с каталогом площадки.

## Проверки

Обычные проверки: `go build ./...`, оба `go vet`, `make lint`, `make test` и
`make test-integration`. Пакет `searchapi` дополнительно проверяет настоящий
путь PostgreSQL → outbox → HTTP → общий поиск → OpenSearch, если запущен
изолированный контур из `proshop-search/tools/marketplace-fixture`:

```bash
# В proshop-search; HTTP слушает только 127.0.0.1:19207.
TEST_OPENSEARCH_URL=http://127.0.0.1:19206 go run ./tools/marketplace-fixture

# В proshop-marketplace; остальные TEST_* задают изолированную инфраструктуру.
TEST_SEARCH_API_URL=http://127.0.0.1:19207 make test-integration
```

Без `TEST_SEARCH_API_URL` сквозная HTTP-проверка явно пропускается. Контур
создаёт собственный случайный набор индексов и удаляет его при штатной остановке.
В общем поиске `SEARCH_GOLDEN=1 go test -race ./internal/modules/search
./internal/infrastructure/db -run TestGoldenMarketplace` проверяет точные
цены и фасеты, изоляцию продавцов, перестановку событий, смену схемы и
прерванную пересборку на настоящем OpenSearch.
