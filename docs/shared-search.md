# Общий поиск маркетплейса

Backend маркетплейса сохраняет проекции в PostgreSQL, повторно проверяет
публикацию по текущей таксономии и через outbox передаёт предложения в
`proshop-search`. Текстовый поиск, ранжирование, фильтры, фасеты и физические
поколения индекса принадлежат общему поиску. Собственный OpenSearch-клиент
маркетплейса используется только для геоиндекса пунктов выдачи.

## Контракт и сохранённое поведение

Служебные маршруты каталога и обратной связи `/api/v1/internal/marketplace/*`
принимают `SEARCH_MARKETPLACE_TOKEN` в `X-Admin-Id`. Маркетплейсу нужны `SEARCH_URL`, этот токен
и `SEARCH_MAINTENANCE_INTERVAL` (минута). Сроки вызовов — константы адаптера
`internal/infrastructure/searchapi/client.go`: выдача, карточка и группа для покупателя — 3 секунды
(движок сам режет запрос в индекс на 1,5 с), служебные вызовы (пачки, поколения, пересборка) —
35 секунд. Транспорт держит до 64 соединений к поиску и переиспользует их между всплесками.
`GET /status` возвращает `contractVersion` и `ready`; ожидаемую версию задаёт
константа в `internal/infrastructure/searchapi/client.go`. Старый контракт
не принимается. Совместимость схемы активного поколения проверяется отдельно:
старая схема означает необходимость перестроения из PostgreSQL.

Служебный контракт — 13, схема поколения — 12, раскладка OpenSearch — 6.
Видимый вариант требует `price`;
неизвестные поля запроса, включая удалённый `priceContexts`, отклоняются движком.


Документы сохраняют публичные `price` и `basePrice` в целых копейках, условия и порог
доставки, канонический путь категории и только проверенные атрибуты. Типы
числа и boolean передаются явно: строка `"001"` остаётся строкой, `false`
остаётся boolean. Товарные категории магазина не подменяют категорию площадки.
Цены и характеристики не проходят через промежуточное представление денег
в `float64`.

Поисковые выражения значений передаются отдельным необязательным `searchTerms`
у каждого фактического атрибута служебного документа. Их источник —
`Publication.attributeSearchTerms`, вычисленный по `searchTermsByValue`
таксономии, фактическому скаляру и схеме категории. Непроверенные поля магазина,
скрытые и снятые с публикации предложения не несут этих выражений.
Общий движок индексирует их в отдельном `searchableAttributeTerms.ru` и сопоставляет
в обычном поиске всех слов вместе с названием и фактическими значениями. Raw-значения,
keyword-ранжирование, фасеты и
фильтры сохраняют исходные типы и значения; выражение не создаёт фильтр.
Поисковые выражения не меняют значения фасетов. Текущую версию служебного
контракта задаёт `contractVersion` в `internal/infrastructure/searchapi/client.go`.

После публикации метаданных backend перепроверяет сохранённые карточки и
отправляет обновлённые документы через outbox. Перестроение поколения берёт
новую проекцию из PostgreSQL. Для витрин сервер магазина должен загрузить
новую версию таксономии и переиздать полные проекции с новыми ревизиями через
`scripts/seed-search-projection.ts --all --apply`; повтор старых сообщений
не добавляет новые производные поля. Сначала разворачивается общий поиск,
принимающий `searchTerms` и подготовивший новое поле индекса, затем producers.

Поиск применяет публичную цену до отбора, сортировки, пагинации и агрегаций.
Цена одна для всех покупателей; запросы не содержат выбора профиля.

Фасеты и фильтры атрибутов сохраняют контракт публичного API. OR действует
внутри значений одного атрибута, AND — между кодами. Числовые диапазоны
включают границы, `inStock=false` отличается от отсутствующего фильтра.
Фасеты считаются без собственного фильтра до пагинации (category — со всеми); порог покрытия
редких атрибутов по-прежнему применяет приложение маркетплейса.

## Плитки и перестроение

Единица листинга, total и фасетов — плитка с ключом `tileKey ?? productId`.
Плитка получает `DocumentID(tenantId, key)`. Маршрут `/offer` находит плитку по
индексированному идентификатору участника. Маршрут `/group` читает плитки по
`groupKey` и восстанавливает порядок предложений по позициям. Каждый маршрут
выполняет один запрос OpenSearch.

Служебный batch `/offers` передаёт `tile: {key, base, members}`.
Полную карточку передаёт `base`, изменения каждого SKU — `members`.
Поиск индексирует текст, сигналы ранжирования, атрибуты для построения панели,
минимальную цену и сводное наличие на уровне плитки. Вложенные варианты хранят
идентификаторы, различающиеся значения, цену, наличие, позицию и изменения
карточки относительно представителя. Отбор по цене, наличию и размерам
сохраняет совпадение внутри одного предложения. При сортировке по цене
используется минимальная цена среди подходящих вариантов.

Одна SQL-выборка присоединяет все SKU затронутых ключей по `catalog_tile_key`.
Изменение SKU, его сигналов или вердикта поднимает версию участника плитки.
Версия плитки — сумма этих версий, накопленного вклада ушедших участников и
версий продавца и реестра. Перенос ставит задачу старого ключа в транзакции
приёма снимка. Пустая плитка получает tombstone. `external_gte` защищает
плитку от запоздалых записей. Основной и догоняющий проходы идут
по `(tenantId, tileKey)`.

Для стенда применить миграции площадки, затем обновить все реплики поиска и
воркеры площадки в одном окне. Запустить на площадке `make reindex` с её
штатными `DATABASE_URL` и `SEARCH_URL`. Команда наполняет новое поколение из
PostgreSQL, догоняет изменения и активирует его. Проверить `GET /status`
с контрактом 13, схемой 12 и `ready: true`, затем выдачу, фасеты, карточку и группу.
Прежнее поколение читается старой версией приложения до обновления поиска.
Пока новое поколение не активировано, выдача новой версии недоступна.

## Обратная связь V1

Обязательный порядок одного окна выката — **все реплики поиска → сервер
магазина → все реплики и воркеры API площадки → витрина площадки**.
Старый поиск отклоняет `observe` с HTTP 400. API повторяет такую выдачу один
раз без полей наблюдения и пишет предупреждение. Покупатель получает выдачу
без квитанции. Старый сервер магазина может пропустить сигнал покупки или
неверно связать его при смене аккаунта. Старые воркеры API могут отправить
`search.purchase` в карантин. Старая версия API не собирает наблюдения,
поэтому ранний выкат витрины оставляет действия без сигнала спроса.

Обратная связь включена всегда и отдельных переменных не требует. Ключ псевдонимов
выводится из обязательного `IDENTITY_REFRESH_KEY` (HMAC с меткой назначения
`proshop-marketplace/search-buyer-keys/v1`), покупки уходят по `SEARCH_MARKETPLACE_TOKEN`.

`GET /api/v1/catalog/offers?q=товар&observe=1` включает наблюдение порции.
API передаёт `observe: true` в существующем `POST /api/v1/internal/marketplace/search`.
При проверенном access там же передаётся `buyerKey`. API переносит опциональный
`receipt` из выдачи поиска. Ответ с `observe=1` имеет `Cache-Control: private, no-store`.

`POST /api/v1/search/feedback` передаёт `kind`, `receipt` и `offerIds` для показов
либо `offerId` для клика во внутренний `POST /api/v1/internal/marketplace/feedback`.
Лимит составляет 120 POST в минуту на IPv4-адрес или IPv6-сеть /64 и 16 КиБ на
тело. Реплики API используют общий лимитер с ключом HMAC от сети. Для клика с проверенным access API добавляет `buyerKey`.
При сбое лимитера или поиска API возвращает `200 {"data":false}`.

Для V1 `buyerKey` — 64 строчных hex-символа HMAC-SHA256 от `marketplace`, нулевого
байта и локального `buyerId` на ключе, выведенном из `IDENTITY_REFRESH_KEY`; он общий у всех реплик.
Смена `IDENTITY_REFRESH_KEY` меняет псевдонимы: окно спроса (7 дней) начинается заново.
После фиксации оплаты отдельная транзакция ставит `search.purchase` в PostgreSQL
outbox. Сбой записи оставляет оплату зафиксированной и даёт предупреждение.
Её выполняет независимая полоса вызовов поиска общего outbox (вместе с индексацией; опроса
очереди нет) и посылает в `POST /api/v1/internal/marketplace/search-purchases`
с `SEARCH_MARKETPLACE_TOKEN` в `X-Admin-Id`; попытка ограничена одной секундой. При `503` и потере
ответа полоса отправляет то же событие с тем же `eventId`, максимум до двух часов от
`paidObservedAt`. `200 {"data":{"attributed":0}}` завершает доставку.
Доставленное событие удаляется из outbox при завершении; помещённое в карантин очищается по
`RETENTION_SEARCH_PURCHASE_QUARANTINE` (72 часа по умолчанию с карантина).

## Пакетная доставка из outbox

Цепочка изменения: событие магазина → `Projector.ApplyProduct` (либо сигналы
цены/остатка) → проекция и допуск по таксономии/модерации → `catalog.offer.sync`
в той же транзакции → `Dispatcher` → `Indexer.HandleOfferBatch` →
`OfferIndex.Put` → `infrastructure/searchapi` → служебный `Put([]Offer)` поиска.
Решения модерации также ставят синхронизацию в транзакции изменения вердикта.

Раньше диспетчер уже забирал несколько задач, но вызывал `SyncOffer` последовательно.
Для каждой задачи открывалась транзакция, читался отдельный согласованный снимок,
ставился пересчёт сводки магазина, отправлялся один документ и отдельно сохранялся
результат задачи. Поиск ожидал `refresh=wait_for` рабочего поколения на каждом таком
HTTP-запросе. При 57 задачах/мин это около 0,95 документа/с; 10 000 документов
требуют около трёх часов только на эту стадию, даже без ошибок и повторов.

Задачи `catalog.offer.sync` одной выборки обрабатываются вместе. Один
`OfferStates.Tiles` находит ключи затронутых плиток и читает весь их состав
вместе с сигналами, участниками, реестром и вердиктами. Два задания одного
товара дают одну запись SKU, несколько изменений одной плитки дают один
снимок плитки на пачку.
Пересчёт сводки ставится один раз на магазин в той же транзакции (отдельный INSERT
на магазин). Опциональный расчёт modelKey сохраняет прежние условные записи и
может дополнительно обращаться к справочнику и сохранять изменившиеся товары.
Внешний вызов поиска выполняется после закрытия транзакции чтения.

Все документы, включая скрытие и удаление через tombstone, передаются одним
вызовом порта индекса. Адаптер сохраняет лимиты поиска: 200 документов и 4 МиБ
JSON с экранированием и конвертом. Обычная пачка даёт один HTTP-запрос и ожидание
refresh на пачку в каждой затронутой физической части рабочего поколения.
При превышении бюджета байтов адаптер делает несколько запросов; каждый имеет
свой барьер видимости. Строящееся поколение записывается без ожидания refresh.

Результаты группы сохраняются одним условным UPDATE в транзакции. Проверяются
все пары `(id, attempts)`: смена владельца любой задачи откатывает отметки всей
группы. Падение процесса оставляет задачи до истечения аренды. Повтор после
частичной записи в поиск безопасен: `external_gte` и сумма версий товара,
сигналов, участника, реестра и вердикта защищают от старого состояния.

Сетевой сбой, 429 или 5xx откладывает все задачи неуспешной пачки на повтор
с прежним backoff 1, 2, 4… секунды, максимум 10 минут. Поиск может успеть записать
часть документов до сбоя — повторяется вся неуспешная группа. При локальном
отказе документа либо HTTP 400/413 индексатор делит группу пополам до изоляции
одного документа. Успешные части завершаются; отравленная задача остаётся
на повторе с `last_error`, как раньше. Исправление предложения будет прочитано
при следующей попытке. Нельзя считать 400/413 общим временным сбоем.

В общем диспетчере до восьми обработчиков работают одновременно. Пакет
`catalog.offer.sync` занимает один слот, сохраняя одну отправку до 200 документов в пределах 4 МиБ.
Остальные слоты получают сначала по одной задаче каждого готового магазина,
затем следующие задачи тех же магазинов до заполнения свободных слотов. После прохода курсор tenant продолжает круг: постоянно
пополняемая старая очередь не вытесняет новый магазин, даже если магазинов больше
слотов. Отдельный курсор есть для пакетной выборки. Курсоры локальны воркеру;
аренда и attempts по-прежнему защищают работу нескольких процессов.
Результаты ограниченного прохода фиксируются общей пачкой с проверкой attempts;
блокировка задач делает отдельный поиск по PK только для выбранных ID.

Выборка чередует магазины: сначала первая готовая задача каждого tenant,
затем вторая и так далее, с квотой на tenant. Чередование происходит **до** общего
LIMIT: старый импорт одного магазина не вытесняет позднюю правку другого.
Внутри tenant сохраняется порядок `next_at, id`; версии защищают и от пересечения
аренд. После пробуждения по сигналу цикл даёт короткое окно на наполнение
пачки. При наличии готовых задач разбор продолжается по ближайшим срокам.

Настройки проверяются при запуске:

| Переменная | По умолчанию | Ограничение и назначение |
|---|---|---|
| `OUTBOX_BATCH` | `200` | 1–200 задач в пакетной порции; точечные задачи занимают отдельные свободные слоты |
| `OUTBOX_PER_TENANT` | `200` | 1–OUTBOX_BATCH, верхняя квота магазина в пакетной порции; у точечных задач квота ограничена числом слотов |
| `OUTBOX_LEASE` | `90s` | ≥ 2 × 40 с срока обработчика (35 с служебного вызова поиска и запас); аренда задач, включая повторы после падения |

Аренда должна покрывать всю выборку, включая задачи других видов и дробление;
срок обработчика ограничен меньшим из 30 секунд и половины аренды.
Обработчики и адаптеры обязаны учитывать context; завершение по сроку откладывает
задачу на повтор. Фоновые `catalog.tenant.sync` и `moderation.tenant.reevaluate`
обрабатывают одну страницу и сохраняют продолжение, поэтому большой магазин
не начинает весь обход заново после срока. При штатной регистрации двух
пакетных видов (индекс и статус предложения) в проходе до 200 пакетных задач
и оставшиеся свободные слоты для точечных;
одновременно выполняются не более 8 вызовов обработчиков. Даже истёкшая аренда не позволяет
устаревшему обработчику подтвердить задачу нового владельца.

Метрики:

- `marketplace_offer_index_batch_size{result}` — число документов в вызове порта;
- `marketplace_offer_index_send_seconds{result}` — время отправки, включая refresh
  и возможное транспортное дробление по байтам; result = done/retry/invalid;
- `marketplace_outbox_task_lag_seconds{kind}` — возраст задачи до успешного завершения,
  с корзинами до шести часов;
- `marketplace_outbox_ready_tenants{kind}` и `marketplace_outbox_ready_age_seconds{kind}` —
  магазины с созревшей задачей и возраст старейшей из них, раз в 15 с, без действующих
  аренд и отложенных повторов ([outbox](outbox.md#метрики));
- прежние `marketplace_outbox_tasks_total{kind,tenant,result}` и ошибки цикла сохраняются.

Готовая работа снимается прыжками по полосам «вид × магазин», а не подсчётом задач:
стоимость не растёт с длиной очереди. Размер/время отправки
включают неуспешные попытки и дочерние отправки при изоляции. Их сумма не равна
числу уникально проиндексированных документов.

Оценка без нагрузочного замера: при прежнем барьере около 1,05 с и пачке из
200 документов чистая синхронизация может дать до ~190 документов/с за вычетом
SQL, сериализации, частей индекса и сети. Для смешанной очереди из 100 sync и
100 `moderation.offer.status` на выборку, при ~50 мс ожидания Kafka на статус,
расчётный темп около 100 / (1,05 + 5) = 16 документов/с до прочих расходов.
Это оценка, а не обещанная производительность; подтверждение — на стенде по
метрикам размера, длительности, lag и глубины, отдельно для чистой и смешанной очередей.

Статусы модерации обрабатываются по одному. Каждый строится с историей решений и отклонений в
транзакции и публикуется синхронным `Publisher.Publish` с ключом предложения.
Общий порт пока не выражает результаты нескольких Kafka-сообщений; безопасное
ускорение потребует отдельного пакетного чтения истории и публикации с сохранением
порядка по ключу и обработкой частичного подтверждения брокером. `moderation.reevaluate`,
replay и пересчёт сводки меняют данные и не заменяются пакетной записью индекса.

На стороне поиска изменения не нужны: действующий контракт уже принимает срез,
ограничен 200 документами и 4 МиБ. Reverse proxy должен пропускать такие тела и
ожидание refresh; при меньшем лимите 413 вызовет дополнительные дробления.

## Пересборка

Сборку ведёт фоновая проверка `SEARCH_MAINTENANCE_INTERVAL` (первая — сразу
после старта), а не путь старта процесса. Если рабочего поколения нет (первый
запуск, потеря кластера), схема старая или поиск просит перенос, проверка под
advisory lock создаёт новое поколение, заполняет его из согласованной
PostgreSQL-проекции, выполняет догоняющий проход и переключает рабочее
поколение. Сборку ведёт одна реплика, остальные получают «занято» и работают
дальше. Процесс стартует и проходит готовность без поиска: готовность требует
только PostgreSQL, поиск — необязательная проверка, видимая в `/health`.
Покупатель, корзина (кроме добавления предложения, оно читает карточку из
поиска), оформление, заказы и приём событий работают; выдача и карточки
отвечают `503 search.unavailable`, задачи outbox для поиска ждут повтора. Общий поиск сохраняет строящееся
поколение до сканирования и направляет текущие записи в обе цели. Прерванная
сборка старой схемы заменяется новой без активации устаревшего поколения.

Основной обход сохраняет подтверждённую позицию поколения в PostgreSQL и
возобновляется с неё. Переиндексация магазина заканчивает обход текущей
целевой версии и объединяет поступившие обновления в следующую цель.
Постоянный отказ карточки изолируется дроблением пачки. Пропуски записываются
в журнал с `tenantId` и `productId` и учитываются в
`marketplace_offer_index_skipped_total` по этапам. Временный сбой оставляет
страницу для повтора.

CLI и фоновые процессы используют одну advisory lock в PostgreSQL с отдельным
соединением. Потеря соединения отменяет работу; два процесса не завершают
сборку независимо. Фоновая проверка размера и незавершённого переноса
использует прежние бюджеты общего поиска: не более трёх поколений, лимиты
частей, шардов и свободного диска.

## Теги и миграции

Маркетплейс больше не подписывается на `catalog.tag.projected`, не хранит
проекцию тегов, не принимает фильтр `tag` и не возвращает `tags` в карточке.
Миграция `00028_retire_search_tags.sql` удаляет `catalog_tags` и поле `tags`
только из проекции `catalog_products`. Ручной справочник магазина и его
привязки в server/admin не затрагиваются.

Миграция реестра справочных сущностей `00027_reference_registry.sql` входит
в тот же комплект и выполняется перед `00028`. Старые миграции таксономии
не меняются, вторая схема хранения не добавляется.

## Порядок обновления и откат

Для релиза с миграцией `00080` остановить реплики площадки, выкатить новую версию без запуска, мигрировать PostgreSQL и запустить реплики.

1. Выпустить общий поиск с целевой версией контракта первым. Проверить отдельный каталог площадки,
   служебный токен и бюджеты пересборки. При несовместимой схеме до пересборки площадкой ожидается
   окно HTTP 503: старое поколение несовместимо с новой схемой.
2. Сохранить резервную копию PostgreSQL и применить миграции, необходимые
   для выбранного релиза. Дождаться миграций до запуска нового backend.
3. Запустить backend с согласованной версией контракта, `SEARCH_URL` и `SEARCH_MARKETPLACE_TOKEN` одной
   репликой или со стратегией Recreate, исключив запись старых подов во время
   пересборки. Если поды сменяются постепенно, после ухода всех старых подов
   обязательно повторить пересборку. Фоновая проверка сразу после старта
   восстанавливает каталог площадки, до активации поколения выдача отвечает 503;
   затем проверить цены гостя и покупателя,
   фильтры, фасеты, доставку, снятие публикации и отставание outbox.
4. Следить за ошибками HTTP к поиску, `marketplace_outbox_*`, возрастом задач,
   отставанием Kafka, ошибками фоновой пересборки и проверкой `search` в `/health`.

Рабочая установка и production этой задачей не обновляются.

Для отката поиска закрыть трафик, вернуть прежний backend вместе с движком
предыдущего контракта (v3) и выполнить `reindex` из актуальной PostgreSQL-проекции
до открытия чтения старого индекса. Старая копия без догоняющих удалений
не является безопасным откатом. Данные магазинов при этом не объединяются
с каталогом площадки.

### Поля каталога R2 — контракт версии 3

Документ предложения передаёт `rating: {value, count} | null`;
`sort=rating` сортирует по убыванию среднего балла, затем числа оценок; без оценок — последними.
Баллы приходят из ревизионного снимка товара (`averageRating`, `ratingsCount`).
Фасет `price` может дополнительно содержать `buckets: [{from, to, count}]`: границы
в целых копейках, до 20 корзин по круглой шкале движка. Адаптер передаёт корзины
без пересчёта; старый ответ без `buckets` остаётся допустимым.
Рекомендации читают локальную проекцию пачкой кандидатов (при пустом personal — повтор для popular), поэтому
не требуют расширения поискового протокола для категорий интересов и исключений.

Требование R2: поле `rating`, сортировка `rating` и гистограмма относятся
к контракту поиска **версии 3**. Сначала выкатить движок с поддержкой версии 3 (R3),
затем marketplace-api. `Offer.rating` берётся из ответа движка.
Для baseline рейтингов переиздать снимки товаров на сервере с новой ревизией,
дождаться обработки событий и обновления индекса и сводок магазинов.

В контракте 10 API передаёт `salesTier` (0–3) из уже прочитанного
`catalog_products.sales_count`. Релевантность добавляет 0,08 за каждую
пройденную границу 1/10/100 и 0,04 × `rating.value` при `rating.count > 0`.
В покупательских ответах нет ступени и количества продаж. Полный счётчик
в PostgreSQL продолжает определять рекомендации. Входной снимок товара
по-прежнему может обновить индекс внутри той же ступени, поскольку его
`projected_at` участвует в сравнении со складским сигналом.

Рекомендации читаются двумя запросами: категории через `category_id = ANY(...)`
и популярное без условия категорий. Оба требуют `on_sale AND price IS NOT NULL`
для частичных индексов. Перед DISTINCT ON группы вариантов берётся верх по sales_count:
не более `limit * recommendationCandidateMultiplier` (множитель 10) кандидатов.
После свёртки применяется окончательный LIMIT. Поэтому блок может быть короче лимита,
если среди верхних кандидатов больше 10 вариантов на группу.
Все покупатели используют публичную колонку price, без распаковки профилей.
Приоритет «другие магазины первыми» применяется после внутреннего отсечения кандидатов.
Если магазин-источник занимает весь верх, «похожие» покажут его, даже если за пределами
внутреннего LIMIT есть другие магазины.
Регион доставки ограничивает все виды рекомендаций.

### Галерея — контракт версии 9

Контракт 4 = контракт 3 + `offer.assets: string[]`: максимум 20 уникальных
ключей, каждый непустой после `TrimSpace`, без управляющих символов Unicode
(Cc, `unicode.IsControl`), до 512 байт; порядок магазина. В ответах поиска всегда массив,
включая пустой. Скрытый документ не содержит галерею карточки.
При разборе снимка недопустимые ключи отбрасываются без отравления сообщения;
повторы удаляются. Подстановка `image` проходит ту же проверку.
Публичный API возвращает `assets` только в карточке товара, не в списках.
Галерея — поле только для чтения: движок хранит её в `_source` внутри `offer` и не индексирует, поиск,
фильтры и сортировка по ней не работают и не планируются.

Сначала выкатить движок с контрактом 4, затем marketplace-api с контрактом 4
и дождаться пересборки несовместимого поколения. Миграция jsonb не нужна.
После выката переиздать снимки сервером в proshop-server:
`scripts/seed-search-projection.ts --all --apply`, затем дождаться Kafka и outbox.
Иначе у уже принятых товаров галерея пустая до следующей ревизии;
одна пересборка индекса отсутствующие в PostgreSQL ключи не восстановит.

### Накопительные фасеты — контракт версии 9

`/search` принимает `tenantIds: string[]` вместо `tenantId`; публичный API —
`?tenant=A&tenant=B` (до 100 значений, повторы удаляются).
`groupId` требует ровно один магазин. Значения одного фасета объединяются через ИЛИ,
разные фасеты — через И. Выдача и total учитывают все фильтры.
Каждый фасет (tenant, inStock, price, attr.<code>) исключает только собственный
фильтр, включая обе границы диапазона. category остаётся навигацией и учитывает
все фильтры. Текст, категория, группа всегда ограничивают выборку.
Счётчики и min/max рассчитываются до пагинации; при total=0 могут остаться варианты.
Для фильтров цены, сортировки и фасетов используется одна публичная цена.

Выкатывать совместно с proshop-search контракта 10: проверить `/status`, несколько
магазинов и перекрёстные фасеты для гостя и вошедшего покупателя. Перестроение
нужно при `ready=false`/смене схемы по процедуре выше, а не из-за tenantIds само по себе.

Контракт 5 также принимает `trackQuery: bool`: учитывать текст в популярных запросах
площадки только для отправленного поиска. Публичный `GET /api/v1/catalog/offers`
включает его через `track=true` или `track=1`; отсутствие параметра выключает учёт,
прочие значения дают 400. После удаления пробелов пустой q или offset != 0 сбрасывают
флаг в false. Витрина передаёт track только при отправке поиска, не при подсказках
на каждое нажатие клавиши или изменении фасетов. Рекламный подбор всегда сбрасывает
флаг; внутренние подборки и рекомендации его не выставляют. Фейковый индекс
игнорирует trackQuery. Текущая версия контракта задана константой `contractVersion`
в `internal/infrastructure/searchapi/client.go`.

### Выбор фасетов — совместимое расширение 5.1

`/search` принимает необязательное поле `facets` со списком базовых кодов
`category`, `tenant`, `inStock`, `price`. Отсутствующее поле означает все прежние базовые фасеты;
`[]` — ни одного; непустой список — только выбранные. Неизвестные и повторные коды отклоняются.
Порядок фасетов в ответе остаётся прежним. Атрибутные фасеты по-прежнему определяет `facetFields`.
Без `price` не считаются ценовые границы и второй запрос гистограммы.

Порт `OfferQuery.Facets` сохраняет различие `nil`/`[]`/списка. Дополнительный код API
`attributes` разворачивается в `facetFields` таксономии и никогда не уходит кодом в движок.
Публичный API: `?facets=none` отключает все фасеты, `?facets=category,tenant` выбирает
только эти два, `?facets=category&facets=attributes` добавляет атрибутные фасеты.
Повтор кода, неизвестный код, пробелы, `none` с другими значениями — 400.
`facets=none` уходит как `"facets": [], "facetFields": []`, а без селекторов поле
`facets` не отправляется, прежние атрибутные поля сохраняются.
Выбор не ослабляет проверку и применение фильтров атрибутов.

Псевдоним PR44 `attributeFacets=true|false` нормализуется только на границе HTTP:
без facets false оставляет четыре базовых, true сохраняет все;
со списком true добавляет attributes. attributes + false и none + true несовместимы (400).
Устаревший `facets=` сохраняет атрибуты; с false отключает всё.
Частичный явный список без флага теперь отключает неуказанные атрибутные фасеты.
Без обоих параметров ответ `/catalog/offers` прежний при любом размере страницы.

В журнале успешного каталога `catalogFacetSelector` содержит только нормализованные коды,
`catalogFacetCount` и `catalogAttributeFacetCount` — фактические количества фасетов ответа.
Счётчик `marketplace_catalog_offers_total{selector="all|none|partial"}` классифицирует запрос,
а не число фасетов ответа: явные все пять кодов — all, пустая частичная выдача — partial.
Метрика относится только к успешным listOffers; внутренний рекламный поиск сюда не входит.
Длительность по селектору доступна в журнале, не в этом счётчике.
Рекламный подбор уже запрашивает пустые `facets` и `facetFields`, потому что читает только карточки.

Обновление API обязательно раньше витрины: API 5ae2d7a отклоняет новые none/attributes/повторы с 400.
После проверки совместимости и новых селекторов можно обновлять клиентов. Доля без полной панели
считается по none + partial; production-цель ≥50% и задержки проверяются через сутки,
а не выводятся из состава страниц или локальных тестов.
Рекомендации API используют PostgreSQL, а не этот поиск.

Сначала выкатить движок с поддержкой поля, затем API: строгий старый движок отвергнет `facets`.
Текущая версия контракта — 10, схема — 11. Требуется пересборка из PostgreSQL.
Цена одна для гостя и вошедшего покупателя.

### Искать как набрано — совместимое расширение контракта 9

Публичный `GET /api/v1/catalog/offers?q=...&exact=true` передаёт `OfferQuery.Exact`
через приложение и порт `OfferIndex` в служебный JSON `/search` как `"exact": true`.
Параметр принимается один раз, строго `true` или `false`; пустое, повторное или иное
значение — HTTP 400 с обычным телом ошибки и кодом `catalog.invalid_query`.
Отсутствие параметра и `false` сохраняют прежнее поведение и побайтовый JSON запроса:
поле `exact` не отправляется (`omitempty`). Рекламные и прочие маршруты не используют этот флаг.

При `exact=true` движок не подменяет набранный текст: не исправляет опечатки,
раскладку и транслит и не возвращает `correction` вида `typo`, `layout`, `translit`.
Персональный и общий словари, стоп-слова, контекст разделов и «раздел + слова»
с пометкой `partial`, фильтры, фасеты и сортировка работают как обычно.
Площадка передаёт решение движку и возвращает его выдачу без собственного исправления текста.

У выдачи площадки нет собственного кэша или дедупликации запросов. Кэш движка должен
различать `exact=true`; без поля и при `false` ключ остаётся прежним.
Сначала выкатывается движок с поддержкой `exact`, затем площадка начинает отправлять
поле по явному запросу покупателя. Текущую версию служебного контракта задаёт
`contractVersion` в адаптере; перестройка индекса из-за флага `exact` не нужна.

### Значения фасета характеристики

Служебный документ принимает необязательный `facetValues`:

```json
{"key":"color","value":"Сине-зелёный","facetValues":["Синий","Зелёный"]}
```

Массив содержит 1–8 непустых уникальных строк длиной не больше 1024 символов
и разрешён только у строковой характеристики (без `type`). При наличии поля фасет и фильтр `attr.<key>`
используют массив: документ считается один раз в каждом значении, а покрытие
фасета считает документы. Без поля используется прежний `value`. В ответе
поиска возвращается исходный `value`, без `facetValues`.

Движок не знает о цветах. Правила палитры и привязки живут в домене marketplace,
`Publication.attributeFacetValues` хранит производные значения вместе с проекцией,
а адаптер searchapi только кодирует их. Порядок палитры устанавливает
приложение marketplace после получения агрегаций. Подтверждённый цвет без привязки
не получает значений фасета: товар остаётся в выдаче, но не участвует в фасете
`attr.color` и отборе по цвету. Контракт поиска имеет версию 9.

Введение `facetValues` требует согласованного выпуска proshop-search и **reindex**:
меняется схема индекса. Удаление вычисляемой корзины в выпуске таксономии 14
контракт и схему индекса не меняет.


### Выкат публичной цены канала (00064–00065)

Поиск и площадка выкатываются одним окном с контрактом 10. Подтвердите
в `/status` версию поколения 11 и откройте каталог после штатной пересборки.
Новая площадка совместима со старым сервером: проверенный приёмкой `origin/master`
сервера (`src/modules/platform/service/marketplace.service.ts`, `check`) уже принимает
`{items, promoCode?}` и возвращает строки с `discounts`, а также `promoCode` и `promotions`.
Адаптер площадки игнорирует дополнительное поле `promotions`: строгого разбора ответа нет.
Он отправляет только `items` и непустой `promoCode`, без ценовых контекстов и buyerId.
Сервер, удаляющий `/pricing/contexts`, выходит не раньше новой площадки.

При остановленном трафике и обработчиках: подготовить согласованные версии поиска
и площадки → применить 00064/00065 → запустить новую площадку →
пересобрать поколение из PostgreSQL → открыть трафик после проверки поколения.
00064 переносит цены под блокировкой таблицы; 00065 строит три индекса
CONCURRENTLY вне транзакции с восстановлением невалидных индексов при повторе.
После миграций выполнить `VACUUM (ANALYZE) catalog_products` вне транзакции.
