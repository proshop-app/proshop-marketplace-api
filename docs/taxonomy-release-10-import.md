# Поставка 10 через админку маркетплейса

Это инструкция для стенда с установленной таксономией 9 и примерно 150
переназначаемыми карточками. Код API и админки должен быть обновлён вместе.
Данные на стенд в ходе разработки не загружались.

## До публикации

1. Сохранить текущий `GET /api/v1/operator/taxonomy`, три выгрузки YAML,
   правила dictionaryBindings и резервную копию PostgreSQL. Приостановить
   правки таксономии другими операторами и согласовать окно переназначения.
2. Выполнить `go run ./cmd/taxonomy check`. Сверить manifest и размеры файлов
   с отчётом. Каждый из трёх файлов меньше **2 097 152 байт**.
3. В разделе «Словари» последовательно загрузить из клона **sc-reference**:
   `exports/reference-taxonomy-10-closed.json` (16 прежних closed, 167 confirmed),
   `exports/reference-taxonomy-10.json` (78 новых словарей, 633 candidate и 3 confirmed),
   `exports/reference-taxonomy-10-empty.json` (32 пустых open: 14 базовых + 18 compat_*).
   Штатный `/reference/import` доработки 8 допускает `entries: []` только у open.
   Повтор того же файла ничего не меняет и не удаляет обученные записи.
   Для всех 196 ссылок должны существовать словари нужного kind: 17 closed, 179 open.
   Из закреплённого списка стенда 89 кодов используются 86; вместе с 78 + 32 это
   все 196. Сам список не доказывает kind и записи; сверить актуальную БД.
   В `deploy/reference` только 19 ссылок (16 closed и brand/country/material):
   сами старые entries.json не являются пакетом операторского импорта v1.
4. Проверить фактические confirmed по
   [точной таблице](taxonomy-dictionaries-needed.md#закрытые-словари-перед-http-публикацией-доработка-7).
   Все 18 ключей color.valuesMeta, «Женский»/«Мужской» в gender и target_gender,
   «Демисезон»/«Зима»/«Лето» в season обязаны быть confirmed; каждому прочему
   closed нужна хотя бы одна confirmed. Подготовительный closed-экспорт несёт
   весь прежний подтверждённый baseline, основной — новый target_gender
   (Женский, Мужской, Унисекс). Если запись защищена решением оператора,
   импорт её пропустит: отсутствие confirmed устраняется отдельным решением.
   Разные kind/содержимое того же release/более поздний release дают конфликт;
   не обходить его сменой номера без сверки. Временная комплектность файлов
   (`publicationReady` в sc-reference) не означает фактическую готовность БД.
5. Удалить через редактор привязок старые операторские правила на удаляемые
   разделы и правила, где поле больше не используется. Их сохранить для
   ручного согласования новых областей. HTTP-импорт частей сохраняет текущие
   dictionaryBindings; «висячая» привязка даст 400 и откат всей операции.

Публиковать только файлы deploy/reference недостаточно. Три экспорта sc-reference
закрывают комплектность данных при наличии 86 прежних словарей. Детальные источники,
обязательные значения и зависимости — `sc-reference/reports/taxonomy-release-10.md`.
Новые записи с внешних источников остаются candidate; пустым open заглушки не нужны.

## Три штатные загрузки

Открыть «Таксономия». Перед каждым шагом перечитывать текущую версию N;
номер версии снимка не равен номеру поставки. Выбирать правильную вкладку,
загружать файл, просматривать текущий/новый YAML, затем публиковать.

| Шаг | Вкладка и файл из `internal/infrastructure/taxonomydata/data/` | HTTP |
|---|---|---|
| 1 | Атрибуты — `attributes.yaml` | `PUT /api/v1/operator/taxonomy/attributes` |
| 2 | Схемы — `schemas.yaml` | `PUT /api/v1/operator/taxonomy/schemas` |
| 3 | Категории — `categories.yaml` | `PUT /api/v1/operator/taxonomy/categories?replaceCategories=true` |

Каждый запрос: `Content-Type: application/yaml`, операторская сессия или
Bearer-токен, `If-Match: "taxonomy-N"`. Успех возвращает новую версию и ETag;
следующий запрос использует их. Чужая публикация между просмотром и записью
даёт **409**: перечитать, заново сравнить и явно подтвердить. Автоповтора нет.
Это **три отдельные транзакции**, а не отложенная пакетная загрузка.
Каждая успешная запись сразу перепроверяет карточки и ставит задачи outbox;
с промежуточного шага часть товаров может быть скрыта.

Перед шагом 3 админка показывает локальное сравнение: число старых листьев
без прежнего кода, перемещённых листьев с сохранённым кодом и изменений
адресов. Это не количество автоматически перенесённых карточек. Для разрыва
оператор ставит отдельный флажок «Подтверждаю ломающую замену категорий»;
до этого кнопка публикации заблокирована. Без query-флага сервер запрещает
удаление листа, изменение/передачу slug. Флаг применим только к categories
и не отключает совместимость атрибутов или CAS.

Семь прежних ключей схем сохранены как совместимые extends-обёртки, на них
не ссылаются новые листья. Поэтому шаг 2 ещё согласован со старым деревом.
Go разворачивает extends и исключает abstract перед сохранением; API и
обратная выгрузка schemas содержат развёрнутые схемы. Повторная загрузка
выгруженного файла допустима, исходником поставки остаётся schemas.yaml.

## Привязки и карточки после замены

В редакторе привязок категорий применить все **19** правил из
`data/dictionary-bindings.yaml`: 18 источников `compatible_model` по
направлениям и одно `book_genre` на books. Это не четвёртый YAML PUT:
существующий маршрут записи —
`PUT /api/v1/operator/taxonomy/dictionary-bindings/{attributeCode}?categoryId={categoryId}`,
JSON-тело `{ "mode": "replace", "dictionaries": ["код_из_файла"] }` и
актуальный If-Match после каждого изменения. Удалить согласованные лишние
правила; сверить итог через `GET /api/v1/taxonomy/dictionary-bindings`.
Неизменившееся правило может сохранить версию — использовать возвращённый ETag.

У карточки с удалённым кодом сохраняются исходный `Marketplace.CategoryID`
и характеристики. Перепроверка выставляет `taxonomy.category_unknown`,
публикация становится ложной; outbox обновляет индекс и карточка исчезает
из публичной выдачи после обработки задачи. Автоматического выбора первого
`to` из миграции нет. По `category-migration.yaml` переназначить карточки,
при split выбрать вид/аудиторию по данным товара, заполнить новые обязательные
поля. Проверить операторскую диагностику публикации и дождаться outbox.
Код мог сохраниться, но схема измениться — такие карточки тоже перепроверить.

HTTP PUT частей меняет версии снимка, **не записывает историю CLI-поставок**
и не загружает manifest/category-migration. Внешний журнал оператора должен
содержать checksum поставки 10 и версии выполненных шагов. Не запускать
после этого бездумно CLI apply/rollback: для CLI действуют отдельные история,
CAS поставок и правила [taxonomy-releases.md](taxonomy-releases.md).

После перепроверки обновить снимок web и обработку унисекс-подборок по
атрибуту. Репозиторий web этой работой не изменялся; снимок админки обновлён
отдельным скриптом, описанным в её `docs/taxonomy-release-10.md`.

## Границы проверки

Настоящие три файла загружены через HTTP-handler на fake UnitOfWork,
начиная с неизменённого снимка 9. Проверены нехватка словаря и откат версии,
подтверждение, CAS, лимит, разворачивание и обратное кодирование.
Не проверялись реальные PostgreSQL-блокировки/откат, сохранение JSONB,
revalidation 150 стендовых карточек, доставка Kafka/outbox и обновление
поискового индекса. Нужна проверка стенда после импорта словарей.

## Проверка доработки 8

Поддержка пустого open добавлена только в операторский ImportPackage v1;
пустой closed, entries=null и отсутствие entries отклоняются. Старый импорт
Delivery без kind остаётся непустым. Миграция БД не нужна: заголовок имеет
ревизию 0, deliveries допускает диапазон 0→0. Номер пустой поставки сохраняется,
повтор не удаляет появившихся позже кандидатов и не создаёт новые события.

Проверено на fake UnitOfWork: HTTP-импорт и повтор, публикация атрибута с
пустым open, полный снимок ревизии 0, получение первого значения из порта
поиска, candidate/source=catalog в очереди оператора, дельта после 0,
outbox и публикация catalog.reference.changed (0→1) через fake Publisher.
Браузер админки: настоящий пакет 32 пустых словарей, повтор, нули в списке,
пустая очередь, клавиатура, Desktop/Mobile; без ошибок JavaScript.

| Репозиторий | Финальные проверки |
|---|---|
| API | go build ./..., go vet ./..., go test ./..., go run ./cmd/taxonomy check — успешно |
| Админка | yarn lint, typecheck, test, build — успешно; 429 тестов, 1 пропущен |
| sc-reference | build.py --check, validate.py, 37 unit-тестов, check_taxonomy10_export.py — успешно |

Экспорты: основной 861575 байт, пустой 4898 байт, подготовительный closed
163731 байт; каждый меньше 32 МиБ. Все 196 ссылок разрешены локально при
86 прежних словарях; обязательные confirmed несут подготовительный и основной
файлы. На момент доработки 8 таксономия и её checksum не менялись: 29 направлений, 3523 узла,
3132 листа, 432 схемы, 425 атрибутов.

Без настоящих PostgreSQL/Kafka/поиска не проверялись блокировки, атомарность
и сохранение пустой поставки в SQL, живой HTTP-импорт, текущие kind/confirmed
стенда, сбор значений из настоящего индекса, доставка outbox и применение
снимка/события потребителем поиска. Интеграционные Go-тесты с тегом integration
и полный набор e2e не запускались. Build админки сохраняет предупреждение
о крупном чанке статического снимка. Новых коммитов и push нет.

## Доработка 9: повторная загрузка непринятого черновика

Текущий checksum: `e0b0788645c21e0b101f3164ae9e4e74d2fe0a12c5b3e43de7fbd9d7bd29b70f`. Дерево содержит 3974 узла и 3555 листьев,
схем 468, атрибутов 432. Сначала словарные файлы по шагам выше, затем
attributes.yaml → schemas.yaml → categories.yaml; последняя загрузка
с `replaceCategories=true` и явным подтверждением оператора. Перед публикацией
повторить preview/check через актуальные бинарник и снимок админки. Переиспользовать
сохранённый до доработки checksum нельзя. Вложенные `extends` раскрывает API.

Ссылки на словари и их kind остались прежними, новые пулы не нужны. Входные
метаданные `sc-reference` и снимки admin/web следует обновить к этой редакции.
Товары со старыми кодами не переназначаются самим YAML: план 9 → 10 задаёт
оператору адресатов, а split требует выбора по карточке. Ни загрузка файлов,
ни переключение активной таксономии не доказывают правильность каталожных
значений и наличия всех confirmed-записей на стенде.
