# Продвижение на маркетплейсе

Решения владельца 2026-11-06 (оплата и маркировка — 2026-10-30). Документ описывает
платное продвижение как монетизацию MVP маркетплейса: что продаётся, как показывается,
как считается и как покупается из админки магазина. Акции магазинов как сущность —
[shop-sales.md](shop-sales.md), модель ранжирования — документ «Ранжирование магазинов
и секция „Маркетплейс“ в админке» (Claude Docs).

## Решения

1. **Без процента с продаж, без CPC и аукциона.** Фикс-цена за место и календарную
   неделю. Прайс мест ведёт оператор.
2. **Предмет продвижения.** Первый — товар: опубликованное и прошедшее модерацию
   предложение магазина. Следом той же сущностью — акция магазина, группа товаров,
   магазин. Код не завязан на один предмет: у размещения есть цель с типом.
3. **Слот это очередь, не место.** У позиции несколько слотов: продавцы в ротации,
   каждый запрос показывает одного, показы делятся. Отчёт — по каждому размещению.
4. **Лимиты.** Для мест категории лимит слотов считается на категорию. Для поиска
   лимит общий на площадку.
5. **Недели.** Размещение продаётся целыми календарными неделями с понедельника;
   начало — не раньше ближайшего понедельника.
6. **Остановка терминальна,** паузы нет. Остановить может магазин и оператор.
7. **Органика не продаётся.** Вид «буст» в админке убирается. Индексы S и Q, политика
   `marketplace-bounded-v1` и «Топ магазинов» от размещений не зависят. Клики по
   рекламе не входят в сигналы ранжирования и обучение.
8. **Реклама видна.** Карточка в рамке с подписью «Реклама», erid в данных карточки.
   В поиске показывается только то, что проходит запрос покупателя. Не больше двух
   рекламных карточек на страницу выдачи, ноль в корзине и оформлении.
9. **Счётчики показов и кликов — сразу,** по размещению и дням. Корзины, заказы и
   выручка по размещению — позже, когда появится привязка заказа к источнику.
10. **Оплата у оператора.** Счёт выставляет оператор, оплату отмечает в админке
    маркетплейса: статус, дата, сумма, документ — поле размещения, не статус.
    Маркировка (ОРД, erid) обязательна при одобрении.
11. **Покупка из админки магазина,** вкладка «Маркетплейс → Продвижение». Сначала
    дизайн в Figma «UNO — Админка магазина», затем реализация.

## Места

Коды мест совпадают с инвентарём админки оператора (`PlacementSurface`).

| Код | Где | Предмет | Лимит | Фаза |
|---|---|---|---|---|
| `category_slot` | карточка на позиции в выдаче категории (позиции из прайса, на макете 1 и 5) | товар | на категорию | **MVP** |
| `search_slot` | карточка на позиции в выдаче поиска | товар | общий | **MVP** |
| `home_top_banner` | первый экран главной | акция, товар | общий | после |
| `home_feed_banner` | между блоками ленты главной | акция, товар | общий | после |
| `category_banner` | над выдачей категории | акция, товар | на категорию | после |
| `home_stores` | рекламный ряд магазинов под «Топ магазинов» на главной | магазин | общий, равен числу карточек ряда | после |
| `store_card_slot` | слот «Реклама» в карточке магазина в «Топ магазинов» | товар | 1 на магазин | после |
| `showcase` | «Магазин недели» на главной | магазин | общий | после |

«Топ магазинов» и рекламный ряд магазинов показываются двумя рядами одновременно,
карточки ужимаются по высоте; у рядов свои подписи.

## Размещение

Сущность `promotion`. Поля совпадают с типами админки оператора (`Campaign`),
кроме убранного вида `boost`:

- `kind`: `sponsored_slot` | `banner` | `showcase`;
- `placementCode`, `position`;
- `target`: `{offerId}` для товара; `{saleId}`, `{categoryId}`, `{storeId}` — для
  следующих предметов;
- `period`: понедельник начала и воскресенье конца, целое число недель;
- `priceKopecks` — цена из прайса на момент заявки, `money.Money`;
- `marking`: рекламодатель, ИНН, erid (ставит оператор при одобрении);
- `creative` — только для баннеров; у товара креатив — его карточка;
- `payment`: статус, дата, сумма, документ, заметка;
- `status`, `version`, `createdAt`, `updatedAt`.

Статусы: `draft` (магазин сохранил) → `review` (заявка отправлена) → `approved`
(оператор, с erid) или `rejected` (с причиной) → `active` (с понедельника начала)
→ `finished`. `stopped` терминален. Свободных слотов на период нет — отказ при
отправке заявки, не оператором. Снятие товара с площадки (модерация, скрытие,
удаление) останавливает размещение.

## Показ

- **Категория.** Витрина запрашивает размещения страницы категории; маркетплейс
  выбирает по одному активному размещению на позицию ротацией и отдаёт `offerId`,
  позицию и erid. Витрина вставляет карточку в рамке с подписью. Размещение привязано
  к категории товара из таксономии; на подкатегории и родителей не распространяется.
- **Поиск.** Маркетплейс берёт активные размещения поиска и проверяет релевантность
  без изменения контракта поиска: товар подходит, если он входит в первые
  `PROMOTION_SEARCH_RELEVANCE_DEPTH` (по умолчанию 100) результатов того же запроса
  покупателя с теми же фильтрами. Подходящие вставляются на позиции из прайса ротацией.
  Нет подходящих — нет рекламы.
- **Только первая страница** выдачи, позиции из прайса.
- Органическая выдача не меняется: рекламная карточка вставляется, а не заменяет.

## Счётчики

Витрина шлёт маячки пачкой: `{promotionId, kind: view|click}`. Маркетплейс складывает
их в суточные счётчики по размещению (UPSERT, без Kafka). Показ считается один раз
на сессию покупателя в сутки. Отчёт продавцу и оператору — по дням и итого; CTR.

## Стык с админкой магазина

Сегодня админка магазина читает статусы участия через сервер
(`/api/v1/marketplace/status/*`), наполняемые событиями Kafka; сервер маркетплейс
по HTTP не вызывает. Покупка требует синхронного ответа (свободен ли слот, цена),
события не годятся.

Решение владельца 2026-11-06: **админка ходит через сервер.** Маркетплейс открывает
машинный API `/api/v1/internal/tenants/{tenantId}/promotion` под служебным
Bearer-токеном из окружения, как внутренние ручки реестра; сессий сотрудников
магазина он не знает. Сервер проксирует его в админку под сессией сотрудника и
правами магазина как `/api/v1/marketplace/promotion`, `tenantId` берёт из сессии
и подставляет сам. Список товаров для выбора — у сервера, он же обогащает ответ
названием, миниатюрой и статусом публикации. Серверу нужны адрес маркетплейса
и служебный токен в окружении.

Прямой вызов из браузера отклонён: пришлось бы дублировать проверку сотрудника
и права магазина в маркетплейсе и открывать CORS. События Kafka не годятся:
заявке нужен синхронный ответ о свободном слоте и цене.

## Контекст и порядок работ

Контекст `promotion` в marketplace-api: прайс мест, размещения, ротация, счётчики,
машинный API для сервера, операторские ручки (одобрение с erid, отказ, оплата,
остановка, инвентарь по неделям), публичные ручки витрины. Миграции — со следующего
свободного номера. Типы админки оператора — черновик контракта OpenAPI.

1. **Дизайн:** вкладка «Маркетплейс → Продвижение» админки магазина, бриф у владельца.
   До утверждения реализация не начинается.
2. **marketplace-api:** контекст `promotion`, ручки витрины, оператора и машинный API.
3. **proshop-marketplace-admin:** раздел «Продвижение» на живом API, убрать `boost`
   и паузу.
4. **proshop-server и proshop-admin:** прокси и вкладка по макету.
5. **Витрина:** рамка и подпись, вставка на позиции, маячки, два ряда магазинов.
6. **Следующие предметы:** акция (баннеры, страница акции), магазин (`home_stores`,
   `showcase`, `store_card_slot`).

## Открытые вопросы

- Показывать ли одобренное, но не оплаченное к началу размещение. Рекомендация и
  допущение реализации до решения: нет, оно ждёт оплаты и не входит в ротацию;
  слот за ним остаётся.
- Стартовый прайс и лимиты: пилотные пакеты по символической цене для первых
  магазинов, тариф выводится из измеренных показов.

## Решения после дизайна (2026-11-06)

Дизайн вкладки «Маркетплейс → Продвижение» утверждён владельцем: кадры М1–М5 в Figma
«Proshop Admin — концепт страниц UNO 3» (`zpZAnxLtEVk1CqkMVgME4v`, node-id 98:2,
98:396, 98:677, 98:938, 98:1214), спецификация у владельца.

1. **Свободные слоты продавцу** показываются как «есть места / остался один / нет мест»,
   без общего числа: загрузка позиции конкурентами не раскрывается. Оператор видит числа.
2. **Отклонённая заявка дорабатывается:** та же запись возвращается в черновик
   (`rejected → draft`), правится и подаётся заново. Причина отказа остаётся в журнале.
3. **Возврат при остановке.** По закону деньги за неиспользованные недели возвращаются
   по требованию; в MVP это ручная операция оператора: он отмечает возврат в размещении
   (сумма, дата, документ), система ничего не считает и не обещает в интерфейсе.
4. **Реквизиты рекламодателя** (юрлицо или ИП, ИНН) берутся из настроек магазина,
   в форме не вводятся; без них заявку подать нельзя, продавца ведут в настройки.
   `erid` ставит только оператор.
5. **Один счёт на размещение.**
6. **Скругление кнопок в файле UNO 3** приводится к правилу владельца: 12 у кнопок
   высотой 40, 10 у мелких.

Требование владельца к вкладке «Маркетплейс» в целом: **карточка магазина** на площадке
собирается из настроек магазина, пока обязательные данные не заполнены, магазин не
считается рабочим на площадке, а во вкладке есть предпросмотр карточки, какой её увидит
покупатель. Это отдельный поток по документу модели ранжирования (раздел «Карточка
магазина на маркетплейсе»): дизайн, профиль магазина на сервере, проекция и предпросмотр.

## Контракт M1 в marketplace-api

Реализованные машинные маршруты используют базу
`/api/v1/internal/tenants/{tenantId}/promotion` (единственное число), операторские —
`/api/v1/operator/promotion`. Точные тела и ответы — в `api/openapi.yaml`.
В машинных PATCH используется `{expectedVersion, changes}`, в submit/stop —
`{expectedVersion, note?}`. Проверка доступности `category_slot` требует `categoryId`:
одного кода места недостаточно для определения независимого лимита категории.
Окончательная категория заявки всегда берётся из карточки товара, а не из запроса.

При одобрении можно передать `erid` в решении или предварительно записать его
в `marking.erid`. Операторский `finish` разрешён после окончания оплаченного периода;
для досрочного снятия используется терминальный `stop`.
В журнале фонового перехода используется дополнительное действие `activate` с
`actor=system`; входящий операторский запрос с этим действием не принимается.

Трактовка дневной выручки M1: полная цена активного или завершённого размещения
распределяется по календарным дням его периода; остаток копеек добавляется первым
дням. Сумма дневных долей равна полной цене. Для обзора берутся только дни запроса.
Эта трактовка, `categoryId` в availability и действие `activate` в журнале приняты
при приёмке M1 как детали реализации; адаптер админки оператора должен знать
действие `activate` в журнале и отсутствие `boost` и паузы.

## Контракт после решений 06.11 (M1.1)

1. Магазин или оператор действием `revise` возвращает отклонённую заявку в черновик.
   `rejectionReason` очищается, причина остаётся в журнале; повторный `submit` проверяет ёмкость.
2. Магазин передаёт `marking: {advertiser, inn}` при создании или правке черновика.
   Оба поля обязательны при `submit` (`invalid`, `promotion.marking_required`); ИНН — 10 или 12 цифр.
   Поле `erid` в машинном API запрещено, его задаёт оператор при `approve`.
3. Возврат автоматически не рассчитывается. Оператор действием `refund` записывает
   `{amountKopecks, on, document?, note?}` в `payment.refund` для `stopped` или `finished`.
   Сумма положительная и не больше `payment.amountKopecks`; других действий система не выполняет.
4. Машинный `availability` возвращает по неделям `free: many | one | none`
   (два и более, один, ноль). Операторский календарь сохраняет числовые значения.

### Дополнение M1.2

- Категория площадки обязательна для обоих товарных мест, включая `search_slot`:
  товар без неё не может продвигаться. Перед показом сверяем текущую категорию;
  при её смене Tick останавливает размещение от `system` с пояснением.
- После воскресенья конца периода заявки `review` и `approved` переходят в `stopped`
  от `system` с заметкой «период прошёл без оплаты/решения». Резерв освобождается.
  Истёкшие `active` переходят в `finished`. Цикл — `PROMOTION_TICK_INTERVAL`, по умолчанию 15m.
- `PROMOTION_SEARCH_RELEVANCE_DEPTH` принимает 10–100, по умолчанию 100.
  Верхняя граница совпадает с `MaxLimit` каталога.
- `DELETE …/campaigns/{id}` доступен магазину (только свой черновик) и оператору.
  Удаляет `draft` вместе с журналом; другой статус — `promotion.conflict`, чужой id — 404.
- Оба списка кампаний принимают `productId`; машинный API ограничивает выборку магазином
  из пути. Ответ `{items, total, limit, offset, counts}` содержит все семь ключей
  `counts: {draft, review, approved, rejected, active, finished, stopped}` (включая нули).
  Счётчики используют те же фильтры, включая `status`, без пагинации. Сортировка —
  `createdAt DESC`, затем id для стабильного порядка. В каждой строке есть итоги
  `stats: {impressions, clicks, ctr}`, CTR в процентах, ноль при отсутствии показов.
- Машинный `GET …/promotion/placements` возвращает `{items, nextMonday}`.
  `nextMonday` — ближайший понедельник в `PROMOTION_TIMEZONE`, строго после сегодняшней даты;
  запрос в понедельник возвращает дату через неделю. Операторский ответ остаётся массивом.
- `PUT placements/{code}` требует `expectedVersion`; несовпадение — `promotion.conflict`.
  `position` обязателен и при создании оператором. Цена пересчитывается только в `draft`;
  смена периода, места или позиции вне `draft` — конфликт. Операторская правка реквизитов
  `review`/`approved` сохраняет цену и повторно проверяет ёмкость.
- `changes` разбирается строго: неизвестные поля отклоняются. Машинные и операторские
  DTO разделены. Для `stats` обязательны обе даты `from`/`to`; в `/catalog/sponsored`
  категория передаётся параметром `category`. Примечание оплаты — `payment.note`.
- Показы и клики независимо дедуплицируются по `(campaign, day, visitor, kind)` в
  `promotion_views`. При сессии покупателя посетитель определяется сессией, тело его
  не переопределяет. Redis ограничивает число маячков (включая элементы пачки) по адресу клиента:
  `PROMOTION_EVENTS_PER_MINUTE`, по умолчанию 120 в минуту. Janitor удаляет дедуп-записи,
  когда конец периода размещения старше 30 дней; накопленные счётчики сохраняются.
- Миграция `00036_promotion_m12.sql` добавляет `kind` в дедуп, `product_id`, `created_at`
  и `updated_at`, переносит значения из прежнего jsonb и включает каскадное удаление журнала.
  Формат jsonb закреплён отдельными DTO хранения, совместимыми с M1.1.

Отправка заявки (`submit`) требует серверной готовности карточки участника.
При `card.ready=false` возвращается 409 `promotion.card_not_ready`; заявку и журнал
не меняем. Проверка действует и для уже подключённого магазина, утратившего готовность.
