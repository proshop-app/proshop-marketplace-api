# Панель оператора

Шлюз работает внутри процесса marketplace. Контракт —
[marketplace.openapi.yaml](api/marketplace.openapi.yaml), его канонический файл —
[api/openapi.yaml](../api/openapi.yaml). Ранний черновик панели заменён этим контрактом.

## Учётная запись и подключение

Для MVP используется отдельная учётная запись оператора платформы из окружения:
таблицы операторов и управления их жизненным циклом в сервисе пока нет.
`OPERATOR_TOKEN` остаётся обязательным машинным Bearer-токеном; браузеру он не нужен.

- `OPERATOR_EMAIL`, `OPERATOR_NAME` — логин и отображаемое имя.
- `OPERATOR_PASSWORD_HASH` — PHC-строка Argon2id: `v=19`, `m=65536,t=3,p=4`,
  соль 16–64 байта, результат 32 байта, base64 без padding.
  Это профиль 64 MiB из [RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html#section-4).
  Открытый пароль не хранится. Формат проверяется до подключения сервисов.
- `OPERATOR_ORIGIN` — HTTPS origin панели без пути и завершающего `/`,
  например `https://admin.example`. Для локального браузера также нужен HTTPS reverse proxy.
- `OPERATOR_SESSION_TTL` — абсолютный срок сессии, по умолчанию `8h`, максимум `24h`.

Email, хеш и origin задаются вместе. Если они отсутствуют, браузерный вход выключен,
машинные ручки продолжают работать. Хеш можно получить утилитой `argon2`, передавая
пароль через stdin: `argon2 <случайная_соль> -id -t 3 -m 16 -p 4 -l 32 -e`.
Пароль не передавать аргументом командной строки. В Docker Compose `$` в хеше
нужно экранировать как `$$` либо передавать через окружение процесса.

SPA и `/api/v1` публикуются на одном origin. Запросы панели используют
`credentials: same-origin`; изменения, включая вход и выход, передают точный
`Origin` и `X-Requested-With: KvazarOperator`. Тело — `application/json`;
DELETE сессии не требует тела. CORS для сторонних origin не включён.

`POST /api/v1/operator/session` принимает `{email,password}`, возвращает
`{id,name,email,role:"operator"}` и устанавливает
`__Host-kvazar_operator=<opaque>; HttpOnly; Secure; SameSite=Lax; Path=/` без Domain.
`GET` возвращает текущего оператора; `DELETE` отзывает серверную сессию и удаляет
cookie с теми же атрибутами и `Max-Age=0`. Токен в JSON не выдаётся.
В Redis лежит только SHA-256 токена в отдельном пространстве `operator:session:`.
Повторный вход отзывает представленную прежнюю сессию и создаёт новый токен.
Смена email/имени/хеша конфигурации отзывает прежние сессии при следующем запросе.
Покупательская cookie не даёт операторского доступа.

Роль проверяется сервером на всех операторских маршрутах, включая существующие
участников, таксономии и покупок. Нет сессии — 401, чужая роль/ошибка CSRF — 403.
При входе Redis ограничивает 10 попыток на логин, 20 на IP и 100 на сервис за 10 минут;
превышение — 429. Логины/IP в ключах хешируются, счётчики имеют TTL.
Одновременно выполняются не больше двух проверок Argon2 на процесс.
За доверенным прокси IP берётся по существующему `HTTP_TRUST_PROXY`.

## Доставка

`PUT /api/v1/operator/participants/{tenantId}/delivery`:

```json
{"version":12,"delivery":{"regions":["RU-MOW"],"carriers":["cdek","yandex"]}}
```

Возвращается Participant; несовпадение версии, включая повтор старого тела, — 409.
Нужно перечитать участника и повторить решение. PATCH участника меняет только `name`.
Оба списка обязательны и непусты. Регионы — существующие ISO 3166-2 RU,
перевозчики — `cdek`, `yandex`; `fake:abc` и прежние `cdek:81` запрещены.
Источник перечня RU — пакет Debian iso-codes, данные ISO 3166-2, сохранённые в `pkg/regions`.
Сервер магазина остаётся источником настроек участия (§3 server-contract): очередная
сверка заменяет локальное покрытие его актуальными настройками. Операторская правка
не меняет настройки в магазине и не включает согласие магазина автоматически.

Миграция 22 сохраняет прежние зоны в `participants.legacy_delivery_settings`, очищает
непереносимое покрытие, выключает `shop_enabled`, повышает версию и ставит переиндексацию.
Субсидия, минимум заказа и операторский `enabled` сохраняются. После обновления сервера
магазина ISO-настройки придут обычной сверкой. Для оператора перечень затронутых участников
сохранён в `operator_delivery_migration_report` (tenant_id, прежние доставка, согласие и статус,
время миграции); команда миграции пишет каждого участника в журнал с tenantId.
При откате 22 → 21 прежние доставка, согласие и статус восстанавливаются из отчёта
до удаления архива, версия снова повышается и ставится переиндексация.
В ответе участника без настроенного покрытия `regions` и `carriers` — пустые массивы `[]`.
Команда изменения доставки по-прежнему требует непустые списки.
Индекс предложений получает новое поколение схемы и перестраивается из PostgreSQL.
Старые числовые region_code ПВЗ очищаются; неизвестный регион запрещает доставку.

Нативные зоны ПВЗ требуют явного полного соответствия:
`CDEK_REGION_CODES` — JSON-объект `location.region_code → ISO`,
`YANDEX_REGION_CODES` — `address.geoId → ISO`. По умолчанию оба `{}`;
неизвестные зоны остаются пустыми. Значения проверяются на старте, угадывания по
названию города нет. После настройки выполнить `make refresh-pickup-points`.
Это конфигурация справочника, не прежний формат `delivery.regions`.

## События

`GET /api/v1/operator/events` возвращает **`{items,total,limit,offset}`**, а не массив
раннего черновика панели. По умолчанию limit=50, максимум 200; offset≥0, порядок id DESC.
Точные фильтры: `tenantId`, `status` (`parked`, `queued`, `resolved`), `type` (полное имя
Kafka-топика), `reason`. По умолчанию видны все статусы; для очереди ошибок указать `status=parked`.
При поступлении новых событий offset-пагинация требует обновления первой страницы.
`occurredAt` — время парковки, `attempts` включает попытки повторной обработки.

`POST /api/v1/operator/events/{eventId}/retry` и `/resolve` принимают `{expectedVersion,note}`:
1–2000 символов, после trim заметка непустая. Решение допустимо только из `parked`;
`expectedVersion` обязателен и должен совпадать с версией последнего прочитанного события.
Без сохранённого ключа повтор, параллельное или задержавшееся решение — 409 с текущим снимком
`{error:{code,message},event:ParkedEvent}`, в том числе после возврата queued → parked.
Чтобы принять новое решение, панель перечитывает состояние и отправляет новую версию.
Ответ при успехе — обновлённый ParkedEvent.
Оператор, время, статус и заметка записываются в `parked_event_decisions` внутри
той же транзакции, что переход и задача outbox. Аудит хранится до удаления события
по существующей политике retention. События в queued retention не удаляет.

Retry ставит задачу в существующий outbox с ID события и версией решения.
Ключ задачи включает эту версию: у каждого решения собственный бюджет из пяти попыток.
Задача с устаревшей версией завершается без обработки и изменения события, с записью в журнал.
Обработчик вызывает тот же Kafka Router
с исходными topic/partition/offset, ключом, заголовками и временем публикации;
новые сообщения в топики сервера не публикуются. Дедуп остаётся в processed_events.
Успех переводит queued в resolved; невалидный конверт или пять неудач возвращают
событие в parked. Ошибки зависимостей до этого повторяются с backoff. После сбоя
между обработкой и отметкой завершения повтор безопасен благодаря исходному inbox ID.
У старых записей без исходного времени повтор не выдумывает время: нужно исправить
источник и получить новый снимок, старую запись можно разобрать через resolve.

Payload в ответе ограничен метаданными версии/ревизии/операции/идентификаторов;
сырые конверт, заголовки и текст исключения остаются в служебном хранилище.
`error` — только ключ причины парковки. Секреты и телефон покупателя не выдаются.
Статус queued означает постановку на повтор, а не успешную обработку.

Ошибки всех ручек имеют вид `{error:{code,message}}`; коды стабильны.
При 401 панель очищает состояние и открывает вход, при 403 показывает отказ доступа.

Ключ `Idempotency-Key` для retry/resolve необязателен. Успешный ответ хранится в
`operator_event_idempotency` вместе с отпечатком запроса 24 часа (`messaging.DecisionTTL`).
Ключ ограничен оператором; событие, действие, `expectedVersion` и исходная `note`
составляют запрос (порядок полей JSON несущественен). Повтор возвращает первоначальный
200 и снимок решения, даже после выполнения outbox. Изменение запроса с тем же
ключом даёт 409 `IDEMPOTENCY_KEY_REUSED`. Ошибки не кешируются; без ключа и после
истечения срока действует обычная проверка версии. Запись результата, решение,
аудит и outbox атомарны; параллельные запросы сериализуются блокировкой ключа в БД.
