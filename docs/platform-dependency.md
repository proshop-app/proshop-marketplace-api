# Зависимость покупательских страниц от сервера магазинов

Обновление 2026-11-12: контексты показа вынесены в [асинхронный кэш покупателя](price-contexts.md).
Каталог, рекомендации, реклама, карточка и панель не ждут `price_contexts` вообще;
промах немедленно выбирает публичные профили. Корзина и checkout остаются строгими.

Проверено по маршрутам `internal/interfaces/http/server.go`, сценариям приложения и всем HTTP-клиентам
`internal/infrastructure`. Единственный клиент cell-api — `infrastructure/platformapi`, адрес `PLATFORM_API_URL`.
`searchapi` обращается к отдельному `proshop-search`; identity-hub, перевозчики, DaData и sms.ru — другие зависимости.
Готовность `/health` не проверяет cell-api и не исключает площадку из обслуживания при отказе ячейки.

## Найденные зависимости и поведение

Все пути ниже имеют префикс `/api/v1`. `PC` — `PlatformAPI.PriceContexts`,
POST `/api/v1/internal/marketplace/pricing/contexts`, выбор профилей цен, пачки до 100 магазинов.
Он вызывается только для вошедшего покупателя; гости используют публичный профиль из проекции без cell-api.
`R` — собственный бюджет чтения 300ms, `S` — бюджет строгого вызова 5s.
Раньше клиент ждал до `PLATFORM_API_TIMEOUT=5s`; общего ограничения и предохранителя не было.

| Маршрут | Синхронный вызов и назначение | Таймаут раньше → сейчас | Отказ раньше → сейчас |
|---|---|---|---|
| GET `/catalog/offers` (включая поиск, раздел, магазин, группу вариантов, фасеты) | Кэш снимка покупателя; обновление PC только в фоне | Без ожидания сервера | 200, публичные профили при промахе/истечении |
| GET `/recommendations?context=home` | Кэш снимка покупателя; обновление PC только в фоне | Без ожидания сервера | 200, публичные профили при промахе/истечении |
| GET `/recommendations?context=offer` | Кэш снимка покупателя; обновление PC только в фоне | Без ожидания сервера | 200, публичные профили при промахе/истечении |
| GET `/catalog/sponsored` (поиск/раздел) | Кэш снимка покупателя; обновление PC только в фоне | Без ожидания сервера | 200, публичные профили при промахе/истечении |
| GET `/catalog/offers/{offerId}` | Кэш снимка покупателя; обновление PC только в фоне | Без ожидания сервера | 200, публичные профили при промахе/истечении |
| GET `/catalog/offers/{offerId}/reviews` | `Queries.Reviews → ProductReviews`, GET `tenants/{tenant}/products/{product}/reviews` | 5s → R | 503 → 200, последняя страница либо `{items:[],total:0}` |
| GET `/cart` | Было `Cart.Verify → PriceGroups → PriceGroup`, актуализация цен/скидок/наличия | 5s → нет вызова | 503 → 200, сохранённый снимок; проверка отдельной командой |
| GET `/buyer/favorites` | Кэш снимка покупателя; обновление PC только в фоне | Без ожидания сервера | 200, публичные профили при промахе/истечении |
| GET `/buyer/price-watches` | Кэш снимка покупателя; обновление PC только в фоне | Без ожидания сервера | 200, публичные профили при промахе/истечении |
| GET, PATCH `/buyer/profile` | Кэш снимка покупателя; обновление PC только в фоне | Без ожидания сервера | 200, публичные профили при промахе/истечении |
| GET `/shops`, `/shops/{slug}` | Нет cell-api: готовые `StoreCards`, подписки из БД | нет → нет | Не зависят от отказа cell-api |
| GET `/taxonomy/*`, `/delivery/settings`, `/delivery/carriers`, `/buyer/subscriptions/shops`, `/orders`, `/me` | Нет cell-api: локальные проекции/настройки/другие порты | нет → нет | Поведение не меняется |

Для панели поиска отдельного backend-маршрута нет: она читает `/recommendations?context=home`, `/shops`
и таксономию; поисковая выдача читает `/catalog/offers`. Их зависимости перечислены выше.
Неперсональные сведения магазина, доставки, рейтинга и основной карточки уже поступают из проекций событий,
а не из синхронного `MarketplaceSettings`. Добавлять второй сетевой источник для них не требуется.
Скрытое/отсутствующее предложение по-прежнему даёт 404 до чтения отзывов; ошибки входных параметров — 400.
Ошибки БД, индекса и авторизации не маскируются как отказ cell-api.
Для публичной карточки при холодном отказе видимость повторно проверяется по актуальной проекции:
отставший индекс не раскрывает уже скрытого продавца или товар.

## Строгие операции

| Маршрут | Вызов и назначение | Таймаут | Отказ |
|---|---|---|---|
| POST `/cart/verify`, POST `/cart/lines`, PUT `/cart/lines/{offerId}`, PUT `/cart/groups/{tenantId}/promo-code` | `PriceGroup`, цены, наличие, промокод | S | 503 `cart.seller_unreachable`; старые цены не подтверждаются |
| DELETE `/cart/lines/{offerId}`, DELETE `/cart/groups/{tenantId}/promo-code` | `PriceGroup`, перепроверка оставшейся группы | S | Удаление сохраняется даже при отказе; нет ложного подтверждения оформления |
| POST `/checkout`, `/checkout/{id}/confirm` | `PriceGroup`, строгая проверка перед покупкой | S | 503 `cart.seller_unreachable`; бизнес-ошибки цены/остатка сохраняются |
| POST `/checkout/{id}/delivery/quotes` | `QuoteDelivery`, договор продавца | min(S, `QUOTE_TIMEOUT`) | Отказ конкретной группы, без выдуманной стоимости; остальные группы продолжаются |
| GET `/delivery/pickup-points` | `PickupPoints` при промахе часового кэша | min(S, `QUOTE_TIMEOUT`) на попытку | Переход к следующему магазину до `PICKUP_MAX_ATTEMPTS` |
| POST `/checkout/{id}/orders` | `MarketplaceSettings`, `QuoteDelivery`, `CreateOrder`, свежая доставка и создание | S на вызов; доставка также `QUOTE_TIMEOUT` | Прежние коды `checkout.delivery_changed`, отказ/состояние группы `seller_unreachable`, ограниченные повторы; заказ не подменяется кэшем |
| GET `/checkout/{id}` | Только снимок из базы; `GetOrder` выполняет отдельное фоновое задание | Без ожидания сервера | Сохранённое состояние; сверка сохраняет backoff группы |
| POST `/payment-stub/{id}/confirm` | `StubPayment`, подтверждение серверного заказа | S | 503 `checkout.payment_unavailable`, прежняя идемпотентность |

Порт при дедлайне возвращает `unavailable / platform.timeout`, при открытом предохранителе или переполненной
очереди — `unavailable / platform.unavailable`. Сценарии сохраняют свои публичные коды, перечисленные выше.
Бизнес-отказы (`PRICE_CHANGED`, `OUT_OF_STOCK`, отказ участия и т. п.) не открывают предохранитель.
Фоновые настройки используют пул чтений; сверки заказов — пул оформления.

## Реализация и ограничения

`application/platformguard.Client` декорирует `ports.PlatformAPI`; сборка в `cmd/marketplace/server.go`.
Приложение получает часы и порт метрик, Prometheus реализован в `infrastructure/telemetry`.
Ни сценарии, ни тесты приложения не зависят от HTTP-клиента, конфигурации или инфраструктуры.

Для процесса сохраняется общий потолок исходящих вызовов. Места разделены на независимые пулы:
оформление и чтения. Пулы не заимствуют места друг у друга.
Доля магазина тоже разделена пропорционально пулам, минимум по одному месту каждому классу.
При умолчаниях магазин занимает не больше 4 мест оформления и 4 чтений, суммарно 8.
`PriceGroup`, `MarketplaceSettings` и `PickupPoints` выбирают класс по типизированной метке контекста
`ports.PlatformCallClass`, которую явно задаёт вызывающий сценарий: корзина, покупка и выбор ПВЗ — checkout,
`participant.Settings.SyncOne` (плановый проход и outbox) — read. Без метки используется read.
Имя операции служит только метрикам и журналу. Отзывы и ценовые контексты всегда read;
расчёт доставки, создание, сверка заказа, болванка оплаты и отмена всегда checkout.
Дедлайны прежние: смешанные операции сохраняют StrictTimeout, включая фоновую сверку настроек.
`participant.ResyncingPlatform.PriceGroup` оборачивает покупательский вызов и ставит задачу настроек при отказе;
самостоятельного фонового вызова PriceGroup сейчас нет. Переклассификация не добавляет обращений к базе или HTTP.

При занятых местах запрос ждёт в ограниченной очереди своего класса в рамках исходного бюджета:
min(контекст запроса, `PLATFORM_READ_TIMEOUT` или `PLATFORM_API_TIMEOUT`), без нового таймаута после ожидания.
Ожидающие магазины получают доступ по кругу; очередь насыщенного магазина не задерживает другие.
Отмена немедленно удаляет ожидающий запрос. Ограничены общая очередь класса и очередь одного магазина.
Ни опроса свободных мест, ни дополнительных горутин/повторов на вызов нет.

Размыкатель магазина учитывает только его технические ошибки. Общий размыкатель учитывает типизированные
отказы соединения и 502/503/504 шлюза. Таймаут ответа и 503 с кодом приложения не считаются общим отказом.
Быстрый путь — 5 последовательных отказов. Независимо от него размыкатель открывается при 50% отказов
из минимум 20 завершённых вызовов за 30s: обычный успех не обнуляет это окно. Магазин и общий сервер
имеют отдельные окна. Общий отказ не начисляется магазину; ответ магазина подтверждает доступность сервера.
Отмена и истечение более короткого бюджета вызывающего кода нейтральны для обоих окон;
таймаут собственного бюджета guard после допуска учитывается только у магазина, кроме доказанного отказа соединения.
После паузы допускается одна проба; успешная проба начинает чистое окно. Старое поколение не закрывает размыкатель.
Активные и ожидающие состояния закреплены; неактивные вытесняются LRU за O(1), устаревшие заменяются при обращении.
Общий предел памяти не зависит от общего числа магазинов или товаров. Окно — 32 временные корзины
по два 64-битных счётчика, плюс итоговые счётчики; это 512 байт корзин на состояние, около 4,9 МиБ при TenantStateSize=10000.
Служебные поля состояния и очереди учитываются отдельно. Цена допуска ограничена фиксированным числом корзин:
при смене времени вычитаются только истёкшие корзины, максимум 31; после долгого простоя окно сбрасывается целиком.
Истории отдельных вызовов нет; оценка границы окна имеет погрешность меньше FailureWindow/32.

`PriceContexts` сохраняет один пакетный вызов. Для пачки из нескольких магазинов ошибка не содержит виновника:
она не начисляется ни одному магазину и не открывает общий размыкатель без признака отказа сервера.
Все такие пачки имеют общую долю в пуле чтений (по умолчанию 4 места и 32 ожидающих), без магазинного размыкателя.
Пачка из одного магазина использует обычную долю и размыкатель этого магазина.
Полная изоляция ошибок внутри пачки требует изменения договора: поэлементных результатов с ошибкой и tenantId.
Дробление пачки на отдельные запросы увеличило бы число обращений до 100 раз; guard его не выполняет.

Кэш контекстов — отдельный порт: Redis с резервом в ограниченной памяти процесса,
одна запись на покупателя. TTL 60s, stale по умолчанию 0; синхронного обновления на странице нет.
Подробности, события и новые настройки — [price-contexts.md](price-contexts.md).
Ограниченный LRU guard теперь кэширует только отзывы (магазин/товар/страница),
с прежним синхронным бюджетом чтения и ограниченным stale при отказе.
Кэш не подтверждает покупку: `PriceGroup`, доставка, создание и оплата всегда обращаются к серверу заново.
Прежний кэш отзывов перенесён из адаптера в обёртку порта: лимит и TTL теперь едины и настраиваются.
Адаптер не снимает дедлайн вызывающего блока и не продолжает загрузку после его истечения.

LRU отзывов использует карту и двусвязный список: попадание и вытеснение O(1), отдельный `cacheMu`
не блокирует допуск, очереди и размыкатели. Число записей ограничивает также текущие загрузки;
поздний ответ вытесненной загрузки не возрождает запись и не заменяет новую.
Для 285 просмотров/с и доли карточек 35% максимум уникальных страниц за TTL + stale:
`ceil(285 * 0.35 * (30 + 300)) = 32918`; умолчание округлено до 33000 записей на процесс.
1024 записи покрывали лишь 10,3s такого потока. При равномерном распределении по R репликам достаточно
`ceil(32918/R)` записей каждой; разные limit/offset одного товара занимают отдельные записи.

Замер Go 1.23.2, linux/amd64, `BenchmarkReviewCacheFootprint -benchtime=1x`: страница из одного отзыва
с полями фикстуры `platformapi/testdata/reviews.json` — 120 байт JSON; 20 таких отзывов (обычный limit) —
2002 байта JSON и около 3266 байт удерживаемой памяти на запись, включая карту, LRU, срезы и строки.
33000 таких записей — около 103 МиБ на процесс; 100 отзывов — 9923 байта JSON, около 13250 байт на запись
и 417 МиБ на процесс. Это контрольные страницы с коротким текстом, не среднее по продакшену;
реальное среднее неизвестно. Для планирования памяти: `R * CacheSize * измеренный heapBytesPerEntry`,
плюс состояния магазинов, очереди, активные HTTP-буферы и копии ответов. С миллионами товаров память
не растёт после заполнения лимита, но доля попаданий зависит от числа уникальных страниц за окно.

## Ценовые контексты покупателя

`pricecontexts.Service` загружает полный снимок после входа/обновления сессии и при промахе, неполноте или
истечении TTL в каталоге, карточках, рекомендациях и панели. Сам просмотр HTTP к магазину не ждёт;
одновременные загрузки покупателя склеиваются внутри процесса. При 1000 публичных магазинах полный проход —
11 запросов `PublicTenants` к PostgreSQL и 10 последовательных HTTP-пачек по 100 магазинов.
Для N постоянно активных покупателей при успешном обновлении раз в минуту это 10N HTTP/мин и около
3000N чтений Mongo/мин при трёх чтениях на магазин на сервере. Это оценка работы, не замер на 1000 магазинов.
Общий бюджет загрузки 1s требует в среднем менее 100ms на пачку; бюджет guard каждой пачки — 300ms.
При ошибке снимок не сохраняется, следующий промах может повторить работу раньше минуты.
Витринный `catalog.PriceContexts` без фильтра также проверяет все публичные магазины: те же 11 запросов
видимости на просмотр вошедшего покупателя даже при свежем Redis-снимке. Это отдельная сохраняющаяся
стоимость O(магазины), которую будущая проекция должна устранять с сохранением актуальной видимости.

Повтор входа или пополнение свежего снимка обращается только за отсутствующими магазинами:
HTTP `10 → 0` при полном свежем снимке, `10 → ceil(M/100)` при M отсутствующих профилях.
Обход видимости остаётся 11 запросами; избранное и наблюдения проверяют только магазины показанных товаров.
Атомарный `Begin` кэша возвращает снимок вместе с новым токеном за тот же Redis EVAL; событие до `Begin`
исключает старый снимок, событие после него запрещает запись результата. Добавление магазина не продлевает
`LoadedAt` существующих профилей. TTL и публичный режим при неполноте сохраняются.

Текущий `pricing.buyer.context-changed` — сигнал сброса: в нём нет нового профиля, потребитель удаляет весь
снимок покупателя. Он не заменяет источник истины сервера. Отказ от TTL требует отдельного договора:
версионированного снимка/дельт назначений, удаления членства и персональных условий, гарантированного
восстановления после пропуска событий и адресного получения контекста. Тогда площадка сможет хранить проекцию
назначений, а HTTP использовать для первичного наполнения и восстановления конкретных магазинов.
До этого холодный обход всех магазинов и стоимость пачки на сервере остаются нерешёнными ограничениями.

## Настройки

Все настройки читаются в `internal/config`, проверяются при старте. Длительности и целые числа положительные.
`PLATFORM_READ_TIMEOUT` не больше `PLATFORM_API_TIMEOUT`; размер кэша не больше 100000, параллельность — 2–1000.
Сумма пулов равна общему потолку; доля магазина — от 2 до общего потолка. Неуказанные доли вычисляются
от общего потолка: чтения — половина, оформление — остаток, магазин — 1/16 (минимум 2).
Очередь магазина не больше очереди класса. Число состояний не меньше суммы общего потолка и двух очередей,
не больше 100000; срок неактивности не меньше паузы размыкателя и окна оценки ошибок. Это проверяется до сборки клиента.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `PLATFORM_API_TIMEOUT` | `5s` | Строгий вызов и предел HTTP-клиента |
| `PLATFORM_READ_TIMEOUT` | `300ms` | Собственный бюджет необязательного чтения |
| `PLATFORM_CACHE_TTL` | `30s` | Срок свежести отзывов |
| `PLATFORM_STALE_TTL` | `5m` | Дополнительное окно stale после срока свежести |
| `PLATFORM_CACHE_SIZE` | `33000` | Общий предел записей LRU отзывов |
| `PLATFORM_MAX_CONCURRENT` | `128` | Общий предел одновременных исходящих вызовов |
| `PLATFORM_CHECKOUT_MAX_CONCURRENT` / `PLATFORM_READ_MAX_CONCURRENT` | `64` / `64` | Резервы оформления и чтений |
| `PLATFORM_TENANT_MAX_CONCURRENT` | `8` | Общая доля магазина, разделяется на 4/4 |
| `PLATFORM_QUEUE_SIZE` / `PLATFORM_TENANT_QUEUE_SIZE` | `1024` / `32` | Ожидающие на класс / магазин внутри класса |
| `PLATFORM_TENANT_STATE_SIZE` / `PLATFORM_TENANT_IDLE_TTL` | `10000` / `10m` | Ограничение состояний и срок неактивности |
| `PLATFORM_FAILURE_THRESHOLD` | `5` | Быстрый путь по последовательным отказам |
| `PLATFORM_FAILURE_WINDOW` | `30s` | Окно доли отказов, от 1s до 5m |
| `PLATFORM_FAILURE_MIN_CALLS` | `20` | Минимум завершённых вызовов в окне, до 1000000 |
| `PLATFORM_FAILURE_PERCENT` | `50` | Порог доли отказов, от 1 до 100 процентов |
| `PLATFORM_OPEN_INTERVAL` | `5s` | Пауза до единственной пробной попытки |
| `PLATFORM_LOG_INTERVAL` | `30s` | Минимальный интервал журнала для пары операция/причина |

## Профиль на 1000 магазинов

Для утверждённого пика 1,6 заказа/с и 285 просмотров/с на всю площадку при R репликах стартовый профиль
на реплику: `PLATFORM_CHECKOUT_MAX_CONCURRENT=max(2,ceil(64/R))`,
`PLATFORM_READ_MAX_CONCURRENT=max(1,ceil(64/R))`, `PLATFORM_MAX_CONCURRENT` — их сумма,
`PLATFORM_TENANT_MAX_CONCURRENT=max(2,ceil(8/R))`, `PLATFORM_QUEUE_SIZE=max(1,ceil(256/R))`,
`PLATFORM_TENANT_QUEUE_SIZE=min(32,PLATFORM_QUEUE_SIZE)`; остальные настройки — из таблицы выше.
Это стартовые лимиты защиты сервера, не обещание пропускной способности на границе таймаутов. Пересчёт:
`lambda_checkout=1.6*(g*(7+a)+p)`, `C_checkout>=ceil(2*(lambda_checkout*L_c+b_c)/R)` и
`C_read>=ceil(2*(285*f*L_r+b_r)/R)`, с теми же минимумами.
Здесь g — магазины в покупке, a — среднее число изменений/проверок корзины на группу перед покупкой,
p — HTTP к ПВЗ на покупку после часового кэша (0 при попадании, до PICKUP_MAX_ATTEMPTS на промах),
f — реальные чтения магазина на просмотр после кэша, L — длительности в секундах,
b_c/b_r — средняя параллельность фоновых вызовов соответствующего класса на всю площадку:
в checkout входят сверки/отмены заказов, в read — сверки настроек и загрузки ценовых контекстов.
Семь вызовов на группу без повторов: PriceGroup в Create и Confirm (2), MarketplaceSettings (1),
QuoteDelivery при выборе и перед созданием (2), CreateOrder (1), StubPayment (1).
Каждое изменение корзины добавляет PriceGroup; истёкший quote, ошибки, смена ПВЗ и повторы увеличивают счётчик.
Тест `TestPurchaseClassesAndCallBudget` фиксирует 9 обращений: один магазин, одна правка корзины, холодный ПВЗ.
285 просмотров не означают 285 HTTP к магазинам: каталог читает снимки, отзывы используют кэш.
Лимиты независимы в процессах: общий потолок равен R*C, очередь — R*Q, доля магазина — R*tenantLimit
с учётом округлений; 10000 состояний и окна размыкателей тоже приходятся на каждую реплику.

Подстановка 17.11.2026 для одной реплики (g=1, двойной запас уже в формуле). Замер времени ответа сервера на
простаивающем стенде: отзывы p95 5 мс, настройки p95 15 мс, ценовые контексты p95 167 мс; расчёт, создание и чтение
заказа не замерялись. Чтения: единственное синхронное чтение сервера на публичный просмотр — отзывы карточки
(доля карточек в просмотрах принята 35%, кэш не учитывается: f=0,35); ПВЗ кэшируются на час, ценовые контексты
загружаются в фоне. При b_r=2 и L_r=50 мс `C_read>=ceil(2*(285*0,35*0,05+2))=14`;
при L_r=300 мс — 64. При a=1, p=1, b_c=1 поток оформления — 14,4 вызова/с:
L_c=0,5 с требует 17 мест с двойным запасом, L_c=5 с — 146. Поэтому 64 места оформления не покрывают
все вызовы длительностью 5s с двойным запасом; при этом профиле покрывают среднее до 2,15s.
146 — консервативная оценка каждого HTTP отдельно. У MarketplaceSettings и следующего QuoteDelivery
общий QUOTE_TIMEOUT=5s: на этом пути сумма бюджетов девяти вызовов не больше 40s, то есть 130 мест
с двойным запасом. Уточнённая формула использует сумму средних длительностей всех вызовов вместо `9*L_c`.
Для подтверждённой нагрузки на этой границе профиль — checkout `max(2,ceil(130/R))`,
read `max(1,ceil(64/R))`, общий потолок — сумма; увеличение требует проверки мощности сервера магазинов.
Фоновые b_c/b_r и длительности под нагрузкой пока не измерены, 1/2 — предположения для подстановки.
Умолчания 64 / 64 сохранены; перенос операций меняет распределение нагрузки, не её число.

Холодный поиск ПВЗ пока читает участников страницами и вызывает Registry.Get для каждого кандидата
до ограничения HTTP-попыток. При 1000 подходящих магазинах это 1000 чтений реестра плюс 5 страниц участников
с COUNT и SELECT (итого 1010 SQL, без изменения после переноса класса);
попадание в часовой кэш этой работы не делает. Это существующий N+1, требующий отдельного пакетного отбора;
перенос класса его не устраняет, при оценке задержек холодного ПВЗ его нужно учитывать.

При превышении пула запрос ждёт места в очереди своего класса, сохраняя один бюджет на ожидание и HTTP:
до 300ms для необязательных чтений, до 5s для строгих операций, либо до более раннего дедлайна вызывающего кода.
Переполнение общей или магазинной очереди даёт `platform.unavailable`, истечение ожидания — `platform.timeout`;
отмена сразу освобождает место, отзывы возвращают допустимый stale или пустую страницу.
Фоновые задания сохраняют существующий backoff и ключи идемпотентности, 15-секундный срок создания не продлевается.
Отказы в окне открывают только магазин либо доказанно недоступный общий сервер; после паузы идёт одна проба.
Наращивание R умножает допустимую нагрузку на сервер магазинов и не ускоряет его: перед повышением лимитов
нужно измерить L, f, g и фон, проверить его ёмкость; пул исполнителя создания остаётся 16 на реплику.

## Наблюдаемость

`marketplace_platform_calls_total{operation,class,outcome}` и
`marketplace_platform_call_duration_seconds{operation,class,outcome}` используют операции
`price_contexts`, `reviews`, `price_group`, `settings`, `pickup_points`, `quote`, `create_order`, `get_order`,
`stub_payment`, `cancel_order`; классы — `checkout` и `read`.
Исходы: `ok`, `timeout`, `error`, `queue_full`, `queue_timeout`, `tenant_breaker`, `server_breaker`,
`canceled`, `short_circuit`, `stale`. Время обращения включает очередь и серверный вызов.
`short_circuit` означает только уже идущее обновление того же ключа отзывов; переполнение и размыкатели
учитываются отдельными причинами. Свежий cache hit не считается исходящим обращением.
Возврат stale учитывается дополнительно: эти ряды нельзя суммировать как число сетевых запросов.

`marketplace_platform_queue_wait_seconds{class,outcome}` измеряет только запросы, попавшие в очередь:
`admitted` либо причина отказа/отмены. `marketplace_platform_rejections_total{class,reason}` отдельно считает
`queue_full`, `queue_timeout`, `timeout` серверного вызова, `tenant_breaker`, `server_breaker`, `canceled`.
Метки имеют фиксированный набор значений, без покупателей, магазинов, URL и сырых ошибок.
Журнал ограничен по паре операция/исход, содержит класс операции и `tenantId`, когда магазин известен.
Публичные деградированные ответы не попадают в журнал HTTP 5xx.
