# Зависимость покупательских страниц от сервера магазинов

Состояние на 2026-11-21. Публичная цена канала marketplace одна для всех.
Показ цен не обращается к API сервера, Redis или списку магазинов.
Отказ сервера не влияет на выдачу, карточку, варианты, рекламу, избранное
и наблюдения за ценой. Ошибки PostgreSQL и поискового сервиса остаются ошибками.

## Источники и число обращений

Считаются SQL-запросы данных, без BEGIN/COMMIT и служебной настройки соединения.
N — магазины в каталоге, K — карточки страницы (не больше 100), G — магазины корзины.

| Действие | PostgreSQL | Поиск / сервер магазина | Redis для цены |
|---|---|---|---|
| Выдача `/catalog/offers` | Таксономия: 1 запрос версии, ещё 1 при смене/холодном кэше; 0–1 пакетный подсчёт продавцов | 1 запрос поиска, 0 вызовов сервера | 0 |
| Карточка | 0–1 подсчёт продавцов | 1 Get поиска | 0 |
| Карточки по идентификаторам | 0–1 подсчёт продавцов | K Get поиска, параллельность 5 | 0 |
| Варианты | 0 | 1 Group поиска | 0 |
| Рекомендации home | 1 запрос интересов для вошедшего, 1 категорий при viewed, 0–2 отбора кандидатов, 0–1 продавцов | 0 | 0 |
| Рекомендации offer | 1 исходное предложение, 0–1 кандидаты, 0–1 продавцы | 0 | 0 |
| Избранное | 2 запроса страницы (count + список), 1 пакет текущих предложений для непустой страницы | 0 | 0 |
| Наблюдения | 1 список, 1 пакет текущих предложений для непустого списка | 0 | 0 |
| Профиль / счётчик снижений | 1 профиль + 1 SQL count по наблюдениям | 0 | 0 |
| Проверка корзины / промокода | Сохранённый сценарий чтения и условной записи корзины | G `items/check`, параллельность 8 | 0 |

Гостевые кандидаты рекомендаций кэшируются локально; интересы авторизованного
покупателя определяют подбор, но не цену. При пустом персональном подборе
повторяется запрос популярных кандидатов. Реклама поиска повторно готовит запрос
(таксономия), ищет релевантные товары и читает кампании/предложения из PostgreSQL;
реклама раздела получает цену из того же ComposeOffer. Дополнительных обращений
ради цены ни в одном рекламном пути нет.

## Что остаётся в GET /catalog/offers

- `PrepareQuery` проверяет категорию, типизирует фильтры и подбирает фасеты по
  текущей таксономии. На каждом запросе перечитывается её версия; определение
  хранится в локальном кэше. Работа с деревом растёт с размером таксономии.
- `populateSellers` читает число разных продавцов для ключей моделей страницы
  одним SQL. Количество запросов постоянно, но объём совпадений растёт с числом
  продавцов и товаров этих моделей. Это оставшееся узкое место вне изменения цен.
- `annotateDelivery` проверяет настройки доставки уже полученной карточки;
  БД, Redis и внешние сервисы не вызываются. Работа пропорциональна K.
- `rememberCatalogFacets` записывает счётчики в контекст запроса для журнала;
  БД, Redis и внешние сервисы не вызываются.

Прямой переход витрины на служебный поиск требует переноса проверки таксономии
и подсчёта продавцов, публичной границы авторизации/лимитов, преобразования денежных
единиц и ответа. Служебный токен поиска браузеру не выдаётся. Доставка и сбор
метрик сами по себе не требуют backend-обращения к данным.

## Строгие операции и остальные зависимости

Проверка корзины, оформление и промокоды используют один метод `PriceGroup`:
`POST /api/v1/internal/marketplace/tenants/{tenantId}/items/check`.
Запрос содержит только строки и непустой промокод; buyerId не передаётся.
Цена определяется типом канала, затем базовым типом; группы покупателей площадки отсутствуют.
Создание заказа и проверка доставки продолжают передавать проверенного покупателя.

`platformguard` сохраняет бюджеты чтения и строгих операций, ограничение
параллельности и предохранитель по магазину. Отзывы используют локальный кэш:
при отказе — последняя страница либо пустой блок. Корзина и оформление
не подтверждают устаревшие цены при отказе сервера. GET корзины читает снимок,
явная проверка и изменения вызывают сервер.

ПВЗ используют отдельный сценарий перевозчика, магазинные настройки и Redis-кэш;
настройки магазина сверяются фоном и после отказа участия. Identity-hub,
перевозчики и sms.ru — отдельные зависимости. `/health` не проверяет
сервер магазинов и не исключает площадку из обслуживания из-за его отказа.
